# Every agent shell command opens a visible CMD window on Windows

Research question: *Why does the shipped Windows build pop a new console window each time the agent runs a command, what is the exact Win32 mechanism, and what is the correct lever?*

Filed as an issue against `danielcherubini/archimedes`. Symptom reported by a user: several blank Windows Terminal windows titled `C:\WINDOWS\system32\cmd.exe` stacking up during a session.

## Executive summary

The app is a **GUI-subsystem** binary in release (`src-tauri/src/main.rs:2`), so its process has **no console to hand down**. Every child it spawns is a **console-subsystem** program (`cmd.exe`, `fd`, `rg`, an `npx.cmd` shim). Windows' documented rule is that a console child which is not "executed inside an existing console session" is **allocated a new console**, and "creating a new console results in a new console window". So: one `bash` tool call → one `cmd.exe` → one window.

**No spawn site in this crate sets a Windows creation flag.** `grep` over the whole repo for `creation_flags`, `CREATE_NO_WINDOW`, `DETACHED_PROCESS`, `STARTUPINFO` returns **0 hits**, and the app crate names no `windows`/`windows-sys`/`winapi` dependency at all. The lever that prevents it — `creation_flags(CREATE_NO_WINDOW)` (`0x0800_0000`) — exists on the exact `tokio` version we pin and has never been called.

The windows are **blank** and titled with the exe path for the same reason: `std` sets `STARTF_USESTDHANDLES` (we pipe stdout/stderr), so the new console's screen buffer is never substituted into the standard handles — the window is created *and* receives nothing. `STARTUPINFO.lpTitle` is NULL, so the title falls back to the executable name.

This is the single most-reported Windows bug class in the Rust/Tauri agent-app ecosystem and is **never** closed as wontfix. Tauri's own `shell` plugin sets `CREATE_NO_WINDOW` on every command; **we do not use that plugin**, so we do not inherit its behaviour, and we reimplemented the spawn surface without the flag.

Two consequences for triage, both verified:
- **Invisible in `tauri dev`.** The subsystem attribute is `cfg_attr(not(debug_assertions), …)`, so a dev build owns a console and children simply inherit it. CI builds Windows in **debug** only (`ci.yml:28`); `release.yml` is the only thing that ever produces the affected binary.
- **Every shipped Windows build is affected** — NSIS `Archimedes_x64-setup.exe`, v0.1.0 → v0.3.0, fresh installs and auto-updates alike.

## Findings

### 1. The rule that creates the window (Microsoft, primary)

| Claim | Source |
|---|---|
| A `IMAGE_SUBSYSTEM_WINDOWS_CUI` image *"will be allocated a console, unless it's executed inside an existing console session"*; GUI images are never allocated one and never block in a shell. | [Console Allocation Policy](https://learn.microsoft.com/en-us/windows/console/console-allocation-policy) |
| *"the system creates a new console when it starts the command processor `cmd.exe`"*; *"Creating a new console results in a new console window"*; *"GUI processes are not attached to a console when they are created."* | [Creation of a Console](https://learn.microsoft.com/en-us/windows/console/creation-of-a-console) |
| With `dwCreationFlags == 0`: *"The process inherits both the error mode of the caller and the parent's console."* | [`CreateProcessW`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) |
| `CREATE_NO_WINDOW 0x08000000` — *"The process is a console application that is being run without a console window."* Ignored for non-console children, and ignored with `CREATE_NEW_CONSOLE` or `DETACHED_PROCESS`. | [Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags) |
| `"console"` subsystem: *"If a console process is run from an existing console then it will be attached to that console; otherwise a new console window will be created."* | [Rust Reference — `windows_subsystem`](https://doc.rust-lang.org/reference/runtime.html) |

`std`'s default is the degenerate branch. `library/std/src/sys/process/windows.rs` initialises `Command { flags: 0, … }` and at spawn computes `let mut flags = self.flags | c::CREATE_UNICODE_ENVIRONMENT;` — i.e. **nothing** console-related is ever passed unless the caller opts in. `self.detach` would add `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP` but is *"not currently exposed in std::process"*.

### 2. Why the window is blank — and why redirecting more streams cannot help

Console allocation is decided by image subsystem + `dwCreationFlags`, with **no handle condition anywhere** in the docs. Redirection therefore does not suppress it. What redirection does do is starve the window:

- `std` sets `STARTF_USESTDHANDLES` whenever any stdio stream is non-null (`si.dwFlags |= STARTF_USESTDHANDLES` in the same file — ours always is, we pipe stdout/stderr).
- [GetStdHandle](https://learn.microsoft.com/en-us/windows/console/getstdhandle): *"standard handles are always replaced with console handles **unless `STARTF_USESTDHANDLES` was specified** during process creation."* So our pipes stay, and the new console's buffer is never wired in.
- [STARTUPINFOW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-startupinfow): the screen-buffer default applies only when `STARTF_USESTDHANDLES` is absent; and a NULL `lpTitle` means *"the name of the executable file is used as the window title"*.

Net: an empty black/`cmd.exe`-titled window for the child's whole lifetime. The blankness is a *symptom of our own piping*, which is why it reads as "the window does nothing".

**Not every row is a window.** `CREATE_NO_WINDOW` is documented *"ignored if the application is not a console application"*, and the self-exec runs **the same exe** — which in release is `IMAGE_SUBSYSTEM_WINDOWS_GUI`. A GUI child of a GUI parent is never allocated a console, so `worker/client.rs:258` and `update.rs:596` cannot pop a window in the shipped build. The sites that actually do are the **console-subsystem** ones: `cmd.exe`, `fd.exe`, `rg.exe`, and `npx.cmd` shims. That matches the screenshot exactly (`cmd.exe` windows, nothing else), and it closes the "which sites pop windows" question analytically rather than by reproduction. The flag still belongs on all six sites — it is *not* ignored in the debug build, where the exe is console-subsystem.

`main.rs:1-2` is the only place in the entire repo — code, docs, tests — that acknowledges console windows at all:

```rust
// Prevents additional console window on Windows in release, DO NOT REMOVE!!
#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]
```

That attribute governs the **parent's own** console ([rust-lang/rust#90674](https://github.com/rust-lang/rust/issues/90674)). It was doing its job; nothing was ever done about the **children's**. `tauri-build` 2.7.2 and `tauri-winres` never set a subsystem — the attribute is user-authored template boilerplate, so no dependency will ever fix the child side for us.

`tokio::process::Command` **does** expose the lever: the pinned `tokio-1.53.1` has `pub fn creation_flags(&mut self, flags: u32)` inside `cfg_windows!` at `tokio/src/process/mod.rs:675`, delegating straight to `std`. It is a **setter, not an OR** — a later call by any wrapper silently clobbers it ([rust-lang/rust#96794](https://github.com/rust-lang/rust/issues/96794) tracks the missing `current_creation_flags`).

### 4. Frequency, and the second window source

One `bash` tool call is one window (`exec.rs:381`, reached from `agent/harness/loop.rs:1659`). MCP stdio clients spawn **once per server per session** (`manager.rs:137` memoises `ensure_connected`) but re-spawn after an exit or a turn-cancel, plus a fresh one per Settings → Test click (`manager.rs:306`), and every subagent dispatch owns its own `McpManager`. A `.cmd`/`.bat` shim is *itself* a `cmd.exe` invocation, so an `npx`-based MCP server can cost two windows per spawn. There is **no** `.cmd`/`.bat`/`PATHEXT` handling anywhere in `src-tauri/src` (grep: 0 hits).

The Rust idiom is a small `#[cfg(windows)]` helper — [Codex `background_command`](https://github.com/openai/codex/blob/main/codex-rs/utils/process/src/lib.rs#L11-L17), [Zed `crates/util/src/command.rs:38`](https://github.com/zed-industries/zed/blob/main/crates/util/src/command.rs#L38), [WezTerm `spawn-funcs`](https://github.com/wez/wezterm/blob/main/lua-api-crates/spawn-funcs/src/lib.rs#L41), [Lapce `dap.rs:172`](https://github.com/lapce/lapce/blob/master/lapce-proxy/src/plugin/dap.rs#L172). There is **no** maintained crate for this (`no_window_cmd` does not exist on crates.io — it is ~10 lines vendored by folklore into ~30 Tauri repos). Five other runtimes expose a *named* API for the same intent: Node `windowsHide`, CPython `STARTF_USESHOWWINDOW`+`SW_HIDE`, Go `SysProcAttr.HideWindow`, .NET `CreateNoWindow`. Hiding the child window is standard practice, not a hack.

### 6. Residual risks the fix must respect

- `CREATE_NO_WINDOW` gives a **windowless console**, not a console-less child. A child that calls `AllocConsole` still gets a window ([AllocConsole](https://learn.microsoft.com/en-us/windows/console/allocconsole)); `cmd /c start …` starts a new window regardless (`/b` is the documented no-window variant).
- Do **not** reach for `DETACHED_PROCESS` instead: it suppresses `CREATE_NO_WINDOW` (documented ignore), and leaves the child free to `AllocConsole` later. `CREATE_NEW_PROCESS_GROUP` is orthogonal and disables CTRL+C group-wide via an implicit `SetConsoleCtrlHandler(NULL, TRUE)`.
- `creation_flags` is a **replace**, so a central helper must own it (Codex documents exactly this constraint in its own comment).
- A hidden child is an **invisible** child: anything waiting on stdin now deadlocks behind nothing. `exec_bash` currently leaves stdin *inherited*, so the confined tier and any interactive child need deciding alongside the flag.
- Reported in the wild (secondary source, low confidence): `CREATE_NO_WINDOW` under a **write-restricted token** can fail the child at loader init (`0xC0000142` `STATUS_DLL_INIT_FAILED`). Our confined tier **fails closed off-Linux** (`exec.rs:400`), so there is no Windows sandbox today for it to bite — but it becomes live the day Windows confinement lands.

- **REMAINS, narrowed but not closed (2026-10-29, `dda2356`) — `timeout /t` still cannot wait; what changed is that it no longer fails *misleadingly*.** The mechanism §6 predicted is exactly what ships: a Tool child gets stdin at EOF (`childproc::closed_stdin`) plus `CREATE_NO_WINDOW`, so it has no console input, and `cmd` answers `timeout /t` with `ERROR: Input redirection is not supported` and exits at once — the documented Tool-child policy, not a defect, but a bare sentence that reads like one, and the residual ask was that it be DIAGNOSABLE. `exec_bash` now runs the captured text through `cmd_input_redirection_diagnostic` (`src-tauri/src/agent/tools/exec/bash.rs`) and **prepends** the translation, so the FIRST LINE the model reads names the no-console-input policy and restates the `ping -n 20 127.0.0.1 > NUL` workaround; `cmd`'s own sentence is kept below it, never replaced, and no exit-report note is added — the run stays an `is_error` on its real non-zero code through `bash_exit_report`'s plain `(Some(n), None)` arm. **The underlying need is untouched:** nothing here gives a Tool child console input, and `timeout` still cannot sleep. The proof is split the way this doc's whole Windows story is split — the translator is pure and keys on a byte match of `cmd`'s own sentence, so `cmd_input_redirection_is_diagnosed_as_the_no_console_input_tool_policy` proves it on any host (negatives included: an unrelated line, and a failing run carrying no trigger sentence, both stay untranslated — it never keys on the exit code, which stays `bash_exit_report`'s decision), and `a_run_whose_text_carries_the_cmd_redirect_error_gets_the_diagnostic_as_its_first_line` proves the **wiring** on any host by having the child `printf` `cmd`'s sentence. Neither proves Windows prints that sentence. That half is `bash_timeout_t_reports_a_no_console_input_diagnostic`, which spawns a real `timeout /t 1` and is `#[cfg(windows)]` — it **runs only on CI's `windows-latest` leg**, and locally its ceiling is `cargo check --target x86_64-pc-windows-gnu --all-targets`: a compile gate, not a run. The same ceiling as the two `cmd.exe` quoting tests above, for the same reason — there is no Windows machine here. **And the workaround that sentence recommends is no longer merely a string:** `bash_ping_workaround_actually_waits_without_console_input` (this PR) runs the real `ping -n 3 127.0.0.1 > NUL` on that same console-less child and asserts it WAITS (a ≥1200 ms elapsed FLOOR — the only assertion that separates a real sleep from `timeout`'s exit-at-once failure mode), EXITS 0, needs NO console input, and finishes before the deadline, so the tool is provably not pointing the model at a second dead end; that test is `#[cfg(windows)]` too, so its proof leg is CI's `windows-latest` run, and locally only its compilation is verified. **CI has since run it (PR #140) and the floor HELD** — `ping -n 3 127.0.0.1 > NUL` waited on a console-less child, exited 0 and needed no console input, so the workaround this tool recommends to the model is now proven on the platform it is recommended for, not merely asserted there.
- **REMAINS — `start /B`'s file-lock is RECORDED and still UNEXPLAINED.** `start` of a batch file can fail with *"The process cannot access the file because it is being used by another process"*. `dda2356` put that symptom into the Windows `bash` tool description — the verbatim message, labelled a known and not-yet-understood limitation, and explicitly **not** proof the command failed — and the assertion that the description still carries it lives in the `#[cfg(not(unix))]` arm of `the_bash_description_names_the_shell_this_platform_actually_runs`, so it fires on the Windows CI leg only (`not(unix)` is false on macOS as well as Linux, so neither the Linux nor the macOS run evaluates that assertion at all). **No mechanism was invented and no locking code was written**, deliberately: guessing at a lock owner from a Linux box would ship a comment nobody can falsify, and the sentence the model now reads asserts only what was observed. Whoever reproduces it on a real Windows box owns the question — and §6's standing caveat travels into that repro: `cmd /c start` allocates its own window regardless of `CREATE_NO_WINDOW` (`/b` is the documented no-window variant), so this is a handle-ownership question, not another face of the window bug this doc is about.

  **What has changed since (this PR): the repro harness now EXISTS, and it does not guess a mechanism.** `bash_start_b_does_not_report_success_without_starting_something` (`src-tauri/src/agent/tools/exec/tests/bash.rs`, `#[cfg(windows)]`) is the first thing in this repo to drive `start /B` at all: it writes a `marker.bat` (explicit `\r\n` — `cmd` does not reliably parse a bare-LF batch file) that appends `RAN` to `marker.txt`, runs the issue's own command shape verbatim as `start /B marker.bat` (no `""` title slot — with no quoted operand, `start`'s title rule is not in play, and adding one would change what is measured), polls the scratch dir for ~5 s because `start /B` is asynchronous, and asserts the mechanism-free contract as a **material implication**: `exitCode != 0 || marker_exists`. That fails on exactly one state — **exit 0 with nothing started** — which is the false success #79 reported (`Access is denied.` after the agent's echo marker, `exitCode: 0` reported, no log file, no process). When the marker DOES exist its CONTENTS are asserted, so a phantom zero-byte `marker.txt` cannot stand in for the batch having run; the failure message carries the text, the details, and a `read_dir` listing of the scratch dir, because a marker written OUTSIDE it would mean `start` changed the working directory — a different finding, equally worth having; and what used to be its third assertion — a guard of the shape `if text.contains(X) { assert!(!text.trim().is_empty() && text.contains(X)) }`, which **cannot fail**, because `text.contains(X)` is the condition that produced `X` and a text holding a non-empty sentence is non-empty — has been DELETED and its claim moved to `the_bash_tool_passes_issue_79_error_sentences_through_verbatim` (this PR), which pins the real requirement: when a run's output carries *"The process cannot access the file because it is being used by another process"* or *"Access is denied."*, `exec_bash` passes the sentence through to the model VERBATIM, as the whole body (line 1 then line 2), on a run that still reports exit 0 and `is_error: false` — #79's exact shape, where the text is the only thing contradicting the code. Unlike the `start /B` test, **that proof is CROSS-PLATFORM: it runs here, on Linux and macOS, not only on CI's `windows-latest` leg**, because it needs no `cmd.exe` at all — the child prints both sentences with `echo`, a builtin on `sh` and on `cmd` alike, so this PR gains a locally-EXECUTED proof where its sibling contributes only a compiled one. **What the two tests do not do:** neither asks `exec_bash` to PROMOTE an exit-0-with-error-text run into an error — that promotion would be a `bash_exit_report` change (its `(Some(n), None)` arm — "a normal non-zero exit needs no note — the code IS the report") and is out of scope on both sides of the move; the cross-platform test asserts `!is_error` only because `echo` genuinely exits 0, which is what makes the run #79's shape (a clean code riding alongside an error sentence). The `start /B` test never touches `is_error` at all. **The two platforms do not print byte-identical output, and the assertion knows it:** both shells print both sentences verbatim, but `cmd`'s `echo` keeps the space that precedes `&&` in its argument (`sh` discards it), so line 1 carries ONE TRAILING SPACE on Windows and nothing else differs — our layer is byte-exact (`childproc::cmd_c_tail`, via `raw_arg`), so the space is `cmd`'s own argument parsing. The sentence-survival proof is therefore STRUCTURAL, not exact-equality: the two `contains` checks pin the sentence BYTES, and the shape check pins `lines().len() == 2` (ruling out a prepend and an append) with each line compared after `trim_end` (forgiving only the shell's own trailing whitespace). `&&` is deliberately NOT softened to a bare `&` — the usual `cmd` idiom for dodging that space — because in `sh` `&` BACKGROUNDS the first `echo` and the two writes to the shared pipe race, making the line order non-deterministic. Note the truth table's deliberate slack: `code == None` (a `null` `exitCode` — an unobserved status) satisfies the left side without consulting the marker, because an unobserved status is not a *clean success* and the contract does not apply to it — and that slack is only safe because the test first asserts `cancelled == false` AND that the captured text carries no deadline note: a run that hung to its deadline would otherwise land in exactly that `None` cell and pass vacuously. `cancelled` alone does NOT cover the deadline (measured on this branch: a deadline run reports `{"cancelled": false, "exitCode": null}` — the deadline sets a separate `timed_out` flag that reaches the model-facing note but never `details`), which is why the second guard is there. The narrow claim is all this test makes: it is NOT the detector for a hypothetical "`exec_bash` always reports 0" bug, which the many existing asserts on specific codes already pin.

  **The proof leg is CI's `windows-latest` run — locally the ceiling is `cargo check --target x86_64-pc-windows-gnu --all-targets`, a compile gate, not a run** (no host can run this: not Linux, not wine). **That leg will show ONE of two outcomes, and BOTH are findings — nobody must "fix" a red run of this test.** Either (a) it is **RED**, the lock reproduced, and then the verbatim output and the exit code belong in this bullet — that is the first observed repro this issue has ever had, the artefact a fix needs, and the answer is to record it, not to weaken the assertion, add a retry, or invent a mechanism; or (b) it is **GREEN**, the lock does not reproduce in CI's DEBUG build, which narrows R1 to the packaged RELEASE bundle — the GUI-subsystem binary (`src-tauri/src/main.rs:2`, `cfg_attr(not(debug_assertions), windows_subsystem = "windows")`) that CI never builds, the same debug-vs-release blind spot this doc's §Gaps already records for the window bug — and #79's remaining life is then gated on a release-bundle run on real hardware, not on this repo. **Which of the two it is: now ANSWERED, and it is outcome (b) — GREEN on CI's `windows-latest` debug build, the lock did not reproduce (PR #140; the squash commit lands on `main`).** Both `#[cfg(windows)]` tests genuinely executed there — real `test … ok` lines in the job log, not skipped — on a Windows suite reporting `1563 passed; 0 failed; 1 ignored`. So R1 is narrowed exactly as (b) predicted: to the packaged **release** bundle, the GUI-subsystem binary (`src-tauri/src/main.rs:2`, `cfg_attr(not(debug_assertions), windows_subsystem = "windows")`) that CI never builds, and #79's remaining life is gated on a release-bundle run on real hardware, not on this repo. **What GREEN does NOT mean: it does not mean the lock does not exist.** It means *does not reproduce in a **debug** build on a CI runner* — not a machine where the symptom has ever been seen — so the symptom remains unexplained and unreproduced anywhere it could actually be reproduced, and because no repro artefact exists there is no verbatim output to record: the harness ran and found nothing, which is not the same artefact as a harness that found the thing. **The two-outcome contract above is not spent — it is a standing instruction, retargeted at whoever eventually runs the release bundle.** The RED half has still never been observed anywhere; if that run reddens, the verbatim output and the exit code belong in this bullet, and the answer is to record them, not to weaken the assertion, add a retry, or invent a mechanism.

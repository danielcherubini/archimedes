# A model-hidden Skill is unadvertised and unresolvable by name — and that is the whole guarantee

A `SKILL.md` may carry the Agent Skills frontmatter key `disable-model-invocation: true` to ask that the **Agent** not pull it in on its own; pi honors it by omitting the skill from `formatSkillsForPrompt`. The desktop advertised every discovered skill on every surface (ADR 0013) — `SkillInfo` never carried the key, so the flag was parsed away and the request ignored. We decided: adopt the key verbatim as `SkillInfo::disable_model_invocation`, call the class **model-hidden** (vs **model-visible**), and ENFORCE it on every model-facing surface — the skill is absent from the `<skills>` system-prompt section, absent from `list_skills`, and REJECTED BY NAME by `read_skill` — while `discover_skills` itself stays total and unfiltered, so the user's `$name` **Mention** route is untouched and cannot be broken by this feature. The invariant: **to the Agent, a model-hidden Skill is not in the catalog.**

**Why:** the surfaces that must agree are the ones that hand skills *to the model*, and they are exactly two functions — `format_skills_for_prompt` (pi filters inside its own version of this function, so filtering in the port preserves the port) and `skills_for`, the single seam feeding BOTH skill tools (ADR 0029's "the tool's catalog cannot drift from the prompt's catalog" survives because there is still one discovery call per tool). Filtering only the prompt is pi's *observable* behavior and would be decoration: `list_skills` re-prints the `description` one tool call later, and the description IS the routing hint being suppressed. The one place we deliberately do NOT filter is discovery — the **Client** (the Skills dialog, the `$` picker, `expandMentions`) reads the same `discover_skills`, and a model-hidden Skill is fully, deliberately available to the user.

**This is attention control, not confidentiality, and the ceiling is documented rather than closed.** `boundary::read_roots` grants the **Boundary** the Skill discovery roots themselves — ADR 0030 did that precisely so a skill still loads at `Reads = Sandboxed` — and inside the Boundary every **Beyond-boundary policy** allows. So `read`/`grep`/`find` on a model-hidden skill's `SKILL.md` stay IN BOUNDS and silent in every policy, and `ls ~/.agents/skills` prints the hidden directory's NAME whatever we do to the skill tools. A skill is user-authored local config in a filesystem the model already shares; the flag exists to keep a skill out of the model's attention (pi's own reason: routing noise), not to hide secrets. Stating a strong guarantee we cannot deliver would be the actual defect.

**Considered Options**

- **Advisory, prompt-only (pi's observable behavior)**: rejected — hides the advertisement while `list_skills` still prints name + description + scope, so the flag reads as broken the moment the Agent lists its skills.
- **Prompt + `list_skills` hidden, `read_skill` still resolves**: rejected — a name learned from anywhere (the user's own prose, a `?` completion, an `ls` of the skill root) loads the full body, which is hiding with a documented bypass.
- **Narrow the read Boundary for model-hidden skill dirs**: rejected — makes the Boundary depend on skill frontmatter, when it is computed ONCE per session as the Space's **Boundary** (ADR 0030); and it still cannot suppress a parent `ls`'s name column, so it buys grep-level silence at the cost of the seam that every file tool is judged against.
- **A read-direction deny-list for hidden skill dirs**: rejected — ADR 0030 grants those roots *because* ADR 0029 needs them; a deny-list aimed at the same paths re-litigates that, introduces the read-direction counterpart to `protected_dirs` for one flag, and still leaks the name in a parent listing.
- **Answer a hidden name with the existing `unknown skill` message** (hidden indistinguishable from absent — the strongest possible statement of the invariant): rejected — a user who just set the flag gets a transcript claiming the skill does not exist, and the Agent dead-ends instead of doing the one useful thing: asking the user to send `$name`. The cost of the distinct message is revealing *which* skills are hidden, and `ls` of the skill root already prints every one of them.
- **Filter in `discover_skills` with an `include_hidden` escape hatch**: rejected — inverts the default, so every future consumer of discovery (almost all of them user-facing) must remember the hatch; a missed one silently removes the user's route to their own skill.

**Consequences**

- **`read_skill` filters per HIT, not on the list.** To distinguish *hidden* from *unknown* it needs the unfiltered set, so `exec_read_skill` resolves against `skills_for` (unchanged, and the `skill_roots` test seam stays there) and checks `model_visible()` on the hit, while `exec_list_skills` takes `model_skills_for`. The hidden branch runs BEFORE any `FsBackend` is built: a hidden skill's `SKILL.md` and its bundled files are both unreachable and neither is read. The failure names ONLY what the model sent — ADR 0029's path-disclosure rule is untouched.
- **`format_skills_for_prompt` needs pi's SECOND guard.** pi guards twice (`skills.length > 0`, then `if (skillsPrompt)` on the filtered output); the port had only the outer one, evaluated pre-filter. Filtering inside without adding the inner check ships an empty `<skills><available_skills/></available_skills></skills>` block for a Space whose skills are all model-hidden, violating `build_main_prompt`'s own promise that an omitted section leaves no trace.
- **`list_skills` can now print `none` where it printed a count**, and a Space can present an empty catalog to the Agent while the Skills dialog shows a full one. Both are the feature.
- **Truthiness is the unquoted literal `true`, and that is pi parity, not a preference.** pi parses frontmatter as YAML and tests `=== true`, so `yes` / `True` / `1` / `"true"` leave a skill model-visible; the tolerant hand-rolled reader matches that with `rest.trim() == "true"`. A user who writes `yes` gets a silently-advertised skill — accepted, because a divergent truth-table would make the desktop disagree with pi on the same file.
- **Subagent children inherit the filter for free.** A child gets no `<skills>` section at all (ADR 0017's reduced message — the unfixed advertisement gap ADR 0029 records), but it does get `read_skill`/`list_skills`, and both filter, so a model-hidden skill is unreachable from a child too.
- **The flag takes effect on a NEW session only, in both directions.** A native session's system prompt is persisted as the transcript's seq-0 message and replayed VERBATIM on resume (ADR 0017), so a running or resumed session keeps whatever catalog it was born with — set the flag and an existing session still advertises the skill; clear it and an existing session still can't see it. `read_skill` is the one live surface: it re-discovers per call, so a session born before the flag will refuse a name it was told about in its own prompt. Transient and accepted — rebuilding the `<skills>` section mid-session is the `diffSystemPromptSections` work ADR 0017 already deferred.
- **ADR 0029's `superseded-by` stays EMPTY deliberately.** This decision supersedes one sentence of 0029 — the `prompt.rs` note that `SkillInfo` has no `disableModelInvocation` field "so no filtering in v1" (a code comment, editable) — but 0029's per-skill containment, name-as-allowlist, and path-disclosure rules all stand, and `docs/decisions/` is append-only.
- **The `read_skill` tool description is corrected in the same change.** It told the model that `read` on a skill path "always fails with `path escapes the session sandbox`", which died with ADR 0030's `read_roots`; it is a `ToolSpec.description`, so it is printed into every session's `<tools>` section — a claim the model acts on (it will avoid a `read` that succeeds).
- **The flag crosses IPC** (`disableModelInvocation`) so the Skills dialog can mark a model-hidden row. The row stays clickable — clicking inserts `$name`, which is the sanctioned route to a hidden skill — and the composer's own `$` picker is unchanged: picking there is already a deliberate act on a skill the user knows.

# A model-hidden Skill is unadvertised and unresolvable by name — and that is the whole guarantee

A `SKILL.md` may carry the Agent Skills frontmatter key `disable-model-invocation: true` to ask that the **Agent** not pull it in on its own; pi honors it by omitting the skill from `formatSkillsForPrompt`. The desktop advertised every discovered skill on every surface (ADR 0013) — `SkillInfo` never carried the key, so the flag was parsed away and the request ignored. We decided: adopt the key verbatim as `SkillInfo::disable_model_invocation`, call the class **model-hidden** (vs **model-visible**), and ENFORCE it on every model-facing surface — the skill is absent from the `<skills>` system-prompt section, absent from `list_skills`, and REJECTED BY NAME by `read_skill` — while `discover_skills` itself stays total and unfiltered, so the user's `$name` **Mention** mechanism is untouched and the catalog it reads stays whole (the per-name condition on that route is recorded in the Consequences below, not claimed here). The invariant: **to the Agent, a model-hidden Skill is not in the catalog.**

**Why:** the surfaces that must agree are the ones that hand skills *to the model*, and they are exactly two functions — `format_skills_for_prompt` (pi filters inside its own version of this function, so filtering in the port preserves the port) and `skills_for`, the single seam feeding BOTH skill tools (ADR 0029's "the tool's catalog cannot drift from the prompt's catalog" survives because there is still one discovery call per tool). Filtering only the prompt is pi's *observable* behavior and would be decoration: `list_skills` re-prints the `description` one tool call later, and the description IS the routing hint being suppressed. The one place we deliberately do NOT filter is discovery — the **Client** (the Skills dialog, the `$` picker, `expandMentions`) reads the same `discover_skills`, and the flag NEVER removes a model-hidden Skill from a user-facing catalog: discovery stays total, deliberately and in full. That is a claim about DISCOVERY only — whether a given name can then be *reached* with a `$` token is a separate question, owned by the Consequences bullet on the mention grammar, not by this paragraph.

**This is attention control, not confidentiality, and the ceiling is documented rather than closed.** `boundary::read_roots` grants the **Boundary** the Skill discovery roots themselves — ADR 0030 did that precisely so a skill still loads at `Reads = Sandboxed` — and inside the Boundary every **Beyond-boundary policy** allows. So `read`/`grep`/`find` on a model-hidden skill's `SKILL.md` stay IN BOUNDS and silent in every policy, and `ls ~/.agents/skills` prints the hidden directory's NAME whatever we do to the skill tools. A skill is user-authored local config in a filesystem the model already shares; the flag exists to keep a skill out of the model's attention (pi's own reason: routing noise), not to hide secrets. Stating a strong guarantee we cannot deliver would be the actual defect — and the guarantee is the Agent's ATTENTION, never containment: the read-side list above is not exhaustive, because at `Shell = Allow` (the DEFAULT direction) `bash` reaches anything on the filesystem. Nothing in this decision is a filesystem containment claim.

**Considered Options**

- **Advisory, prompt-only (pi's observable behavior)**: rejected — hides the advertisement while `list_skills` still prints name + description + scope, so the flag reads as broken the moment the Agent lists its skills.
- **Prompt + `list_skills` hidden, `read_skill` still resolves**: rejected — a name learned from anywhere (the user's own prose, a `?` completion, an `ls` of the skill root) loads the full body, which is hiding with a documented bypass.
- **Narrow the read Boundary for model-hidden skill dirs**: rejected — makes the Boundary depend on skill frontmatter, when it is computed ONCE per session as the Space's **Boundary** (ADR 0030); and it still cannot suppress a parent `ls`'s name column, so it buys grep-level silence at the cost of the seam that every file tool is judged against.
- **A read-direction deny-list for hidden skill dirs**: rejected — ADR 0030 grants those roots *because* ADR 0029 needs them; a deny-list aimed at the same paths re-litigates that, introduces the read-direction counterpart to `protected_dirs` for one flag, and still leaks the name in a parent listing.
- **Answer a hidden name with the existing `unknown skill` message** (hidden indistinguishable from absent — the strongest possible statement of the invariant): rejected — a user who just set the flag gets a transcript claiming the skill does not exist, and the Agent dead-ends instead of doing the one useful thing: asking the user to send `$name` whenever the mention token can carry it. The cost of the distinct message is revealing *which* skills are hidden, and `ls` of the skill root already prints every one of them.
- **Filter in `discover_skills` with an `include_hidden` escape hatch**: rejected — inverts the default, so every future consumer of discovery (almost all of them user-facing) must remember the hatch; a missed one silently removes the user's route to their own skill.

**Consequences**

- **`read_skill` filters per HIT, not on the list.** To distinguish *hidden* from *unknown* it needs the unfiltered set, so `exec_read_skill` resolves against `skills_for` (unchanged, and the `skill_roots` test seam stays there) and checks `model_visible()` on the hit, while `exec_list_skills` takes `model_skills_for`. The hidden branch runs BEFORE any `FsBackend` is built: a hidden skill's `SKILL.md` and its bundled files are both unreachable and neither is read. The failure names ONLY what the model sent — ADR 0029's path-disclosure rule is untouched.
- **`format_skills_for_prompt` needs pi's SECOND guard.** pi guards twice (`skills.length > 0`, then `if (skillsPrompt)` on the filtered output); the port had only the outer one, evaluated pre-filter. Filtering inside without adding the inner check ships an empty `<skills><available_skills/></available_skills></skills>` block for a Space whose skills are all model-hidden, violating `build_main_prompt`'s own promise that an omitted section leaves no trace.
- **`list_skills` can now print `none` where it printed a count**, and a Space can present an empty catalog to the Agent while the Skills dialog shows a full one. Both are the feature.
- **Truthiness is pi's YAML boolean resolution, not a hand-picked literal — and not, as an earlier draft of this bullet claimed, the unquoted lowercase `true` alone.** pi parses frontmatter as YAML with its `yaml` dependency and tests `frontmatter["disable-model-invocation"] === true` (`dist/core/skills.js`), so the truth table is whatever the **YAML 1.2 core schema** that package implements produces. HIDES: `true`, `True`, `TRUE` (all three are the core-schema boolean), and any of those followed by a comment — a `#` preceded by a space or a tab ends a plain scalar, so `true # keep this out of the agent's way` is the boolean `true` too. MODEL-VISIBLE: `yes` and `on` (the core schema dropped YAML 1.1's word-booleans, so they are strings), `1` (a number), `"true"` / `'true'` (quoted ⇒ strings), `true#no-space` (one plain scalar, hence a string), an empty value (`null`), and a `>` / `|` block scalar (folds to the string `"true\n"`). The tolerant hand-rolled reader mirrors that — core-bool spellings, a whitespace-preceded `#` comment stripped. **We mirror pi's YAML bool resolution rather than inventing a friendlier truth table**: a user who writes `yes` gets a silently-advertised skill, and that is deliberate, because a divergent truth-table would make the desktop disagree with pi on the same file. (Each row above was checked against pi's own `yaml@2.9.0`.) The residual gap is YAML the tolerant reader does not model at all — a value written tagged (`!!bool true`), as an anchor (`&a true`) or as an alias to one (`*a`) resolves to the boolean in pi and to a plain string here, which fails OPEN (the skill is advertised). The same fail-OPEN direction covers the KEY shapes the reader cannot see: a value folded onto the next line (`disable-model-invocation:` with `true` indented beneath it), a space before the colon (`disable-model-invocation : true`), a quoted key (`"disable-model-invocation": true`) and the explicit-key form (`? disable-model-invocation` / `: true`) all resolve to the boolean in pi's `yaml` and leave the Skill model-visible on the desktop where pi would hide it. Stated rather than closed: those spellings are not what a hand-written `SKILL.md` carries, and recognizing them means the reader learning YAML, which is the dependency this reader exists to avoid. One shape belongs in that list but does NOT fail open, because YAML itself refuses to parse it: a glued `disable-model-invocation:true` (no space after the colon) throws `MISSING_CHAR` in pi's `yaml`, so pi drops the whole file, while our `disable-model-invocation:` prefix match reads the key and HIDES the Skill — so, like the duplicate-key case below, it is a disagreement about whether the file EXISTS at all rather than about the flag (pinned by `glued_colon_flag_shape_hides_where_pi_drops_the_whole_file`, which is deliberately NOT in the stay-visible list above).
- **A duplicate frontmatter key is the clearest place the readers genuinely diverge, deliberately.** pi's YAML parser throws `DUPLICATE_KEY`, so its frontmatter parse fails and pi **skips the whole `SKILL.md`** — the skill does not exist for pi at all. The desktop's tolerant reader is forgiving: first occurrence wins, the skill is kept. So `true`-then-`false` keeps the Skill model-HIDDEN and `false`-then-`true` keeps it model-VISIBLE (the reader takes the FIRST value it sees and ignores the rest). Only the second order is a model-facing disagreement with pi: for the first, the outcome already coincides with pi's, because pi publishes no skill at all from a file whose YAML it refuses to parse and a model-hidden Skill is likewise never advertised — while `false`-then-`true` means we advertise a Skill pi will not read. Both orders are pinned by `duplicate_flag_key_first_occurrence_wins_in_both_directions`. Accepted: silently dropping a file the user can see in their editor is the worse failure, and the disagreement is about whether the file EXISTS, not about the flag — a file pi rejects on `DUPLICATE_KEY` contributes no skill to pi's catalog either way, so the two readers never hold opposite views of the flag on a file both of them publish.
- **Subagent children inherit the filter for free.** A child's REDUCED message carries no `<skills>` section (ADR 0017's reduced message — the unfixed advertisement gap ADR 0029 records), and a child whose reduced message resolves to `None` — `build_child_system_message` gets no launch/definition prompt AND the resolved child tools exclude `manage_todo_list` — falls through to the main-prompt arm (`worker/core.rs`'s `(StartMode::Fresh, None)`), whose section is filtered the same way: so the flag holds either way, and no child shape advertises a model-hidden Skill. Both shapes get `read_skill`/`list_skills` too (unless the child's own `tools:` list drops them, which is ADR 0020's allowlist working), and both filter, so a model-hidden Skill is unreachable BY NAME from a child too — the same `read` ceiling ADR 0030 creates for the parent (`boundary::read_roots` grants the Skill discovery roots) applies to a child, so `read`/`ls`/`grep` on its path stay in bounds for a child exactly as they do for a parent.
- **The PROMPT is frozen until a NEW session, in both directions; BOTH skill tools are live.** A native session's system prompt is persisted as the transcript's seq-0 message and replayed VERBATIM on resume (ADR 0017), so a running or resumed session keeps whatever catalog it was born with — set the flag and an existing session still advertises the skill; clear it and an existing session still can't see it. So THREE surfaces move on TWO timings: the `<skills>` section is the only frozen one, while `list_skills` and `read_skill` BOTH re-discover per call (`exec_list_skills` resolves through `model_skills_for`, `exec_read_skill` through `skills_for`), so a session born before the flag already refuses the name AND no longer lists it, while its own prompt still advertises it. Transient and accepted — rebuilding the `<skills>` section mid-session is the `diffSystemPromptSections` work ADR 0017 already deferred.
- **ADR 0029's `superseded-by` stays EMPTY deliberately.** This decision supersedes one sentence of 0029 — the `prompt.rs` note that `SkillInfo` has no `disableModelInvocation` field "so no filtering in v1" (a code comment, editable) — but 0029's per-skill containment, name-as-allowlist, and path-disclosure rules all stand, and `docs/decisions/` is append-only.
- **The `read_skill` tool description is corrected in the same change.** It told the model that `read` on a skill path "always fails with `path escapes the session sandbox`", which died with ADR 0030's `read_roots`; it is a `ToolSpec.description`, so it is printed into every session's `<tools>` section — a claim the model acts on (it will avoid a `read` that succeeds).
- **The flag crosses IPC** (`disableModelInvocation`) so the Skills dialog can mark a model-hidden row. The row stays clickable — clicking inserts `$name`, the sanctioned route to a hidden skill whenever the mention token can carry it; for a name the token CANNOT carry, the click still inserts a dead token, because the row's own `onClick` does not branch on mentionability — the **tooltip** is the surface that tells the truth there — and the composer's own `$` picker is unchanged: picking there is already a deliberate act on a skill the user knows.
- **A `$name` route is promised ONLY when the mention grammar can carry the name, and exactly two surfaces check.** The `$` token is `[a-z0-9]+(?:-[a-z0-9]+)*` (ADR 0031) while discovery screens a name merely for tag-safety, so `has space` and `a_b` are legal, DISCOVERED names that no token can ever carry: `read_skill`'s refusal says the Skill must be loaded explicitly and the Skills-dialog tooltip emits no `$` glyph at all, instead of sending the model — and the user, through the tooltip — to a token that silently expands NOTHING. The check is `skills::is_mentionable_name` and its matched TS pair `isMentionableSkillName`, each side tested over the same name set. The `$` SKILL catalog is deliberately NOT filtered by it — unlike the `@` and `#` catalogs, which drop unmentionable names — because this decision's own premise is that the Client's skill catalog stays TOTAL, and filtering the picker would delete rows the user still owns. So the tools and the `$` picker CAN disagree for such names: the picker offers a row whose token expands nothing. Accepted with it the harder case — **a model-hidden Skill whose name sits outside the ASCII grammar has no route the Rust side will PROMISE**: not the prompt, not `read_skill`, not a composer token ("ASCII" is load-bearing, and it is the same hedge `read_skill`'s refusal was rewritten to carry: the predicate is ASCII-strict while the Client resolves a token by a JS case-FOLD, so the one name class that folds INTO the grammar — a name written with U+212A KELVIN SIGN, which JS `toLowerCase()` turns into `k` (`kernel` with a KELVIN first letter expands from `$kernel`) — can still reach the Agent client-side even though the Rust side refuses to promise it). Proportionate, because the hiding is the user's own request and the untypeable name is the user's own choice, and the surfaces state the dead end rather than hiding it; the fix is the user's own one-line edit (the frontmatter `name`, else the directory name it falls back to).

> **Amended 2026-10-23 (the row stops inserting a dead token).** Two statements above are now false and are corrected from inside this decision, which is why `superseded-by:` stays EMPTY and no new ADR is written for it. The bullet *"The flag crosses IPC"* said that for a name the token CANNOT carry "the click still inserts a dead token, because the row's own `onClick` does not branch on mentionability — the **tooltip** is the surface that tells the truth there"; and the closing clause of *"A `$name` route is promised ONLY when the mention grammar can carry the name, and exactly two surfaces check"* said "the picker offers a row whose token expands nothing" and counted TWO checking surfaces. Shipped instead (issue #10): a Skills-dialog row whose name fails `isMentionableSkillName` is **listed and inert** — `aria-disabled="true"`, out of the tab order, click and Enter both inert, the dialog stays open, and the reason sits in a native tooltip that carries **no `$` glyph** — while `insertSkill` guards the same predicate before it dispatches, so the row and the tooltip one node away finally agree. The row's affordance is the seam, NOT the catalog: the premise that the `$` SKILL catalog stays TOTAL is untouched and stands, because the same catalog feeds model-facing discovery, and the `@` / `#` pickers filter only because they exist solely to offer a mention token — this dialog does not, so deleting a row would destroy a discovery the user owns instead of an offer they could not use. The composer's own `$` picker is exactly as this decision left it: unfiltered, still able to offer a name whose token expands nothing, so "the tools and the picker CAN disagree" survives verbatim for that surface. `manualOnlyTooltip`'s two rules are unchanged, including the rule that the unmentionable shape emits no `$` glyph at all — the new row tooltip carries the same rule and reuses the badge's phrase `This name can't be typed as a mention` so the two surfaces cannot drift.

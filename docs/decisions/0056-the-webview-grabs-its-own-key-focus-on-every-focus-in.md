# The webview's key focus is asserted at the webview level, because the window's focus does not imply it

On Linux (WebKitGTK) the app ignored every key until the user clicked inside the window — not just a chord: the composer took no typing and `Escape` could not stop a turn. GTK has two focuses. `tauri-plugin-window-state` reveals our `visible: false` window with `show()` + `set_focus()`, and that call is **window-level** all the way down (`WebviewWindow::set_focus` → `Window::set_focus` → `WryWindowDispatcher::set_focus` → tao's `WindowRequest::Focus` → `present_with_time()`) — it never touches the WebKitGTK **widget**, which is the thing whose key focus decides whether WebKit dispatches a key event into JS at all. So the fix is to assert it at that level: `Webview::set_focus()` (`grab_focus()` under the hood) from the existing `run` callback, on `RunEvent::Ready` and on focus-in (`RunEvent::WindowEvent { event: WindowEvent::Focused(true), .. }` — there is no `RunEvent::Focused` variant), through one `grab_webview_key_focus` seam.

## Measurement, not mechanism, carries this decision

An earlier draft of this decision asserted a mechanism — that wry's creation-time `grab_focus()` "lands on an unmapped widget" because the window is `visible: false`. **That claim is refuted, and recording the refutation is most of this ADR's value**, because the theory is very easy to fall into again. `WebviewAttributes::from(&WindowConfig)` (`tauri-runtime/src/webview.rs`) copies `config.focus` and **never sets `visible`**; `tauri-runtime-wry` chains `.with_focused(..)` with no `with_visible`; wry defaults `visible: true`. So wry's creation path runs **both** `show_all()` and `grab_focus()`, on a realized widget, and the hidden-window compensation runs *after* that (`wry-0.57.0/src/webkitgtk/mod.rs:178-189, 383-389`).

What remains true is weaker and needs a measurement to carry it: the widget is given key focus at creation, nothing ever re-asserts it after the window has been through tao's `hide()` and the plugin's `show()`/`present_with_time()`, and the symptom is real and reproduced. So Step 0 of the plan measures it on a real Linux build before any of this is implemented, with three verdicts: `Ready` fixes it / only focus-in fixes it / **neither fixes it**. If neither does, this decision is withdrawn and superseded by the actual diagnosis — the fix is not written, because an unverified focus call would be a placebo that also closes the symptom's report.

## Considered Options

- **`Ready` only (rejected).** Fixes one reproducible state. Every other path that maps the window without re-establishing a focus widget — minimise/restore, a Wayland re-map — re-creates the bug, and those paths are not enumerated, so each returns as a fresh "the keyboard stopped working".
- **Native menu items with accelerators (rejected).** Registers a visible menu bar on every platform, and it is the wrong layer: it routes one chord while typing and `Escape` stay dead at launch. Missing widget focus is the cause; a menu is a second way to ask for one key.
- **A frontend workaround — focus a DOM element on mount (rejected).** DOM focus inside a webview widget that holds no GTK key focus receives nothing, so the renderer cannot fix this from inside itself.

## Consequences

- **The decision is conditional on a measurement, and says so.** A reader must not treat "we do this because the widget never got focus" as settled — that sentence is false as written. The claim this ADR supports is only: *the window's focus does not imply the widget's, and the widget's is the one that gates key events.*
- **The `Focused(true)` arm is Linux-only, and the reason is upstream.** `WindowEventWrapper::map_from_tao` returns `Self(None)` for `Focused(true)` on `#[cfg(windows)]` when the window has no children and `webviews` is non-empty — our exact shape — so Windows never delivers it and runs on `Ready` alone (as does macOS, where wry marks `focused` unsupported). A Windows reader debugging "the self-healing doesn't" is debugging the wrong thing; the arm's comment says this.
- **On Linux the arm also fires for *webview* focus changes**, because tauri synthesises `WindowEvent::Focused(true)` from the webview alongside tao's `connect_focus_in_event`. So the honest safety statement is not "it can never steal focus" — it is that the re-assert moves focus between **widgets of the same GTK window**, and this app has exactly one (`decorations: false`, no native menu bar, no tray). Adding a second focusable widget or a native menu is what would make this arm misbehave.
- **`Ready` is chosen for one verified reason, and not for a second tempting one.** Verified: tauri's own `setup()` — which creates the config window — runs inside the `Ready` arm *before* the user callback (`tauri/src/app.rs`), so the call cannot precede window creation. ⚠ Do **not** claim it is "strictly after the plugin's reveal": the plugin's `on_window_ready` runs via `run_on_main_thread`, which executes inline, so that ordering is a property of the inline queue and not a guarantee.
- **Reach the webview through `WebviewWindow`, not `Manager::get_webview`.** `get_webview`, `webviews` and `get_focused_window` are all `#[cfg(feature = "unstable")]` and the feature is off; `AsRef<Webview<R>> for WebviewWindow<R>` is ungated and is the only such impl, so `window.as_ref().set_focus()` needs no disambiguation. Note `WebviewWindow::set_focus` exists too and is the **wrong** (window-level) sibling — a grep for `set_focus()` finds both.
- **The match must bind `&event`, and the `..` is mandatory.** The `run` callback owns the `RunEvent` and `label` is a `String`, so a by-value `if let RunEvent::WindowEvent { label, .. } = event` partially moves `event` and breaks the existing `RunEvent::Exit` arm with E0382. `RunEvent` and its `WindowEvent` variant are `#[non_exhaustive]`, so `..` is required cross-crate (E0638).
- **No mock app in the Rust unit tests, on pain of a macOS-only failure.** A second `generate_context!()` in the lib unit-test binary duplicates `embed_plist`'s `#[no_mangle] static _EMBED_INFO_PLIST` (already emitted once by `lib.rs`) — a **link** error, so `cargo clippy`/`check`, which emit metadata only, stay green while macOS `cargo test` reddens. This is the same hazard class that forced `src-tauri/tests/ipc.rs`'s `#![cfg(target_os = "linux")]` gate (`docs/research/tauri-mock-runtime-test-crashes.md`). Instead the seam is split the way `focus_probe_trace` already splits in the same file: a pure `Option<Result<(), String>> → Option<String>` reduction, unit-tested with no `App`, plus the `#[ignore]`d human-read check for behaviour. A future contributor should expect no green test to point at the behaviour itself.
- **The ungated call stays cross-platform on purpose.** WebView2's `focus()` is `MoveFocus(PROGRAMMATIC)` (which moves focus *within* an already-focused CoreWebView2 and does not call Win32 `SetFocus`) and macOS's is `makeFirstResponder`; gating to Linux was rejected because "the webview holds no key focus" is not obviously Linux-specific and the call costs nothing where focus already works. Narrow it on a platform that demonstrably misbehaves rather than pre-emptively.

# A deny-list entry that does not exist yet is KEPT and compared leniently — because a failed compare is a silent non-match, and one half alone is a no-op

A write deny-list entry whose directory had not been created yet was **silently absent from the list**, and the comparison that consumes the list could not have matched it even if it had been there. We decided two things, in one commit (`fc7b635`, issue #92), and the decision is that **they are one change**: (1) `boundary::protected_dirs()` builds its entries through `push_protected` → `fs_backend::canonicalize_lenient`, so a directory that does not exist yet is **KEPT** as its canonical nearest-existing ancestor plus the re-applied trailing components, instead of being dropped; and (2) `tools::exec::access::protected_refusal_text` canonicalizes the **ENTRY** through that same lenient primitive, replacing `dir.canonicalize().is_ok_and(…)`. Keeping an entry that the comparison refuses to compare is a **silent no-op** — the entry sits on the list, matches nothing, and the harness reports a protection it does not have.

This is the third of the four ADRs this branch's spec promised. The spec's framing is verbatim: *"That framing is also what makes one PR defensible to a reviewer: four commits, one thesis, and the ADRs are four applications of it rather than four unrelated rulings."* Only two were ever scheduled as tasks (0079 for #93, 0080 for #94); 0081 (#92) and the fourth (the session cost figure, #87) were **owned by no task** and existed only as a landing order in the branch's follow-ups doc — *"Numbers by landing order: 0079 #93, 0080 #94, 0081 #92, 0082 #87"* — until **T06** — the branch's label for the Rust task that shipped `fc7b635` — found the gap and declined to fix it, correctly: widening an implementer's owned set to a markdown file is the wave owner's call, not the implementer's. `fc7b635`'s own message closes with *"Also unowned still: ADR 0081 for #92."* #92 earns its place in that framing more squarely than the other three: the protection existed in exactly one of the two places that had to hold it, and the report said otherwise. The fourth application is **#87** by issue number and by that landing order — this ADR does **not** cite it as a document, because whether its file exists when this one lands is not something this ADR can see.

## Why one half is not a fix

The mechanism is short enough to state in four lines, and it is the whole reason a previous attempt at #92 failed.

The comparison used to be:

```rust
let hit = protected.iter().find(|dir| {
    dir.canonicalize()
        .is_ok_and(|canon| resolved.starts_with(canon))
})?;
```

and it is now, as shipped:

```rust
let hit = protected
    .iter()
    .find(|dir| resolved.starts_with(crate::agent::fs_backend::canonicalize_lenient(dir)))?;
```

`is_ok_and` on a **failing** `canonicalize()` is `false`, and `false` inside a `find` predicate is **indistinguishable from "this entry is not the one"**. So change (1) alone — keeping the entry — hands change (2) an entry it then refuses to compare: the entry is on the list, the strict canonicalization fails on it because the directory still does not exist, and the entry matches **nothing**. The write is refused exactly as often as before the fix. That is what "a failed compare is a silent non-match" means mechanically, and it is why the two halves are one change. The shipped comment says the same thing where a refactorer will read it:

> BOTH sides lenient (issue #92): the entry may name a dir that does not exist yet, and a strict `canonicalize()` on it fails — which under `is_ok_and` matched NOTHING, silently no-opping the deny-list for exactly the entry `protected_dirs()` now keeps. `hit` stays the CALLER's entry so the message names the directory as registered.

and the rewritten paragraph above it states the design:

> So each entry goes through the SAME lenient canonicalization as the compared path (issue #92). A strict `canonicalize()` on an entry that does not exist yet simply FAILS, and a failed compare is a silent NON-MATCH — which is the very hole `boundary::protected_dirs` now keeps the entry to close, so the two halves are one change and neither alone is a fix.

**The asymmetry that made this possible was documented and unacted.** The *compared* side already went through the lenient primitive — `let resolved = crate::agent::fs_backend::canonicalize_lenient(resolved);` is the first line of `protected_refusal_text` — while the *entry* side used strict `dir.canonicalize()`. Worse, the primitive's own doc named the caller: `peel_to_existing`'s doc points at *"[`crate::agent::tools::exec::protected_refusal_text`], the one caller that leans on this without the probe"*, and measured with `git log -S` that sentence arrived at **`f3836e1`** (2026-10-15). The primitive's documentation named this caller **before** that caller ever used it on both sides. The asymmetry was not overlooked; it was written down and left.

This is the measured reason an earlier attempt at #92 shipped without fixing #92, and it is why the design decision was corrected **before any planning** — the branch's status log's Decisions entry is titled *"D3 corrected after grounding, before any planning"* and its body reads *"The lenient deny-list needs TWO changes, not one"*, with the reason as *"The entry side silently no-ops a still-missing entry, so the first change alone fixes nothing."* Both halves are in one commit because a reviewer reading only `boundary.rs` would see protection that does not exist.

**And it is the branch's thesis, in its purest form.** #93 reports `Edited <path>` for a call that did something else; #94 reports "timed out" for a command that exited 0; #92 reports "these directories it can never rewrite" for a guard-rail that a `cp` walks straight through **and** silently drops a directory that does not exist yet. A deny-list entry that cannot match is the harness reporting a protection it does not have — the same property, at a different seam.

## The half-fix is falsified, not asserted away

**Attribution first, because it matters.** Every mutation result in this section is **T06's implementer's measurement**, carried by `fc7b635`'s commit message and the branch status Changelog. **This ADR ran no `cargo` and no `pnpm`** — it is a docs-only task sharing a wave with another docs-only task, and putting a Rust toolchain into it would destroy the only reason that wave has width. 0080 sets exactly this precedent ("recorded here as attributed measurements, not re-run by this ADR, which ran no `cargo` at all") and this ADR follows it. If the counts below do not reproduce, this ADR's central evidentiary claim weakens; re-running them is cheap for whoever holds a Rust task.

**The compare-revert mutation — change (2) reverted, change (1) kept: exactly ONE test reddens**, and its signature is the point. `a_write_into_a_still_missing_protected_dir_is_refused` (`exec/tests/policy.rs`) fails with its **premise assertion GREEN** and its **`is_error` assertion RED**: the snapshot really does carry the entry (change (1) worked) and the write really does land (the entry matched nothing). Premise passing and refusal failing *in the same test* is what turns "and yet it matched nothing" from an assumption into a measurement. The test's own doc comment says which half it owns:

> So: the session-snapshot tests pin change (1); THIS test pins change (2). A run where only change (1) landed reddens exactly this one test.

**Which test pins which half, and why the other two cannot see it.** `a_recreated_protected_dir_is_refused_without_a_new_session` (executor) and `a_recreated_protected_dir_is_refused_by_the_gate_without_a_new_session` (gate) pin **change (1)**: their fixture creates `.pi/agent/agents` *before* the compare, so at compare time a strict `canonicalize()` on the entry **succeeds** and they stay green under the half-fix. `a_write_into_a_still_missing_protected_dir_is_refused` never creates the directory, so the entry is still missing when the comparison runs — it is the only test that hands the old `is_ok_and` a failing canonicalization, and therefore the only test that can see change (2) go missing.

**The premise asserts the SPECIFIC entry, and never `!protected.is_empty()`.** The shipped form is:

```rust
assert!(
    protected.contains(&home.path().canonicalize().unwrap().join(".pi/agent/agents")),
    "the snapshot must carry the not-yet-existing dir — that is the premise: {protected:?}"
);
```

placed **before** the write attempt, for a reason the shipped comment states: *"a premise check belongs ahead of the thing it makes non-vacuous, and because `assert!` panics this ordering is what makes the HEAD red report the premise instead of `is_error`."* And the specificity is load-bearing: *"a `!protected.is_empty()` check passes on a list carrying the WRONG entries, and the test would then pass on a refusal for an unrelated reason while claiming to pin #92."*

**The ancestor-peel mutation — `fc7b635` calls it *"A third mutation"* (it counts a mutation this ADR does not restate), and it is the second one recorded here: keep the entries but peel to the canonical ANCESTOR** (drop the re-applied trailing components): **three tests redden** and the failure is **on the premise, with a non-empty and WRONG list** — the snapshot carries `…/.pi/agent` where `…/.pi/agent/agents` is expected. Under the weak `!is_empty()` premise that mutation would have sailed through the premise assertion and been caught, if at all, by something far away. So the two mutations discriminate on different axes: **the compare-revert is caught by `is_error`; the ancestor-peel is caught by the premise's specificity.** That pairing is the measurement that proves the strengthened premise earns its keep — it is not stylistic strictness.

## The two seams, which discriminate DIFFERENTLY — and cannot be collapsed into one rule

Both seams call the same `protected_refusal_text`, so a reader will try to unify their tests. They assert different things because the seams fail differently.

**The executor seam: `is_error` is the discriminator, because the failure mode is the write LANDING.** Under `writes: Allow` the boundary admits an absolute out-of-`cwd` target, so when the deny-list no-ops there is **no refusal text at all** — `FsBackend::write` runs, `create_dir_all` fires, and the file exists. That is why both new executor tests assert `is_error` **and** a did-not-land assertion (`!target.exists()` in the recreated test, `!agents.exists()` in the still-missing one — the second checks the directory itself, since nothing under it may be created either) **and** `ends_with(PROTECTED_WRITE_ROUTE)`, and why the shipped comment puts it this way:

> 5. Refused — on `is_error`, NOT on the text alone: a test that asserted
>    only the wording stays green through this bug, which is the whole
>    reason the bug survived.

**The gate seam is the exception, and its own doc comment says so.** In `a_recreated_protected_dir_is_refused_by_the_gate_without_a_new_session`, `is_error` and `!target.exists()` were **GREEN at HEAD** — with an empty deny-list the write is still refused, as a **boundary escape** — so the discriminating assertions are the **wording** ones:

> WHICH ASSERTION DISCRIMINATES, stated because it is not the obvious one:
> `is_error` and `!target.exists()` are GREEN at HEAD — with an empty
> deny-list the write is still refused, as a BOUNDARY escape. The
> discriminating assertions are the WORDING ones: the refusal comes back
> `write: path escapes the session sandbox: …` instead of the deny-list
> sentence, so the `protected agent-definition directory` assertion fails.
> The wording is the bug's second half — a model sent hunting for a boundary
> that is not the problem — so an `is_error`-only test would be green before
> and after.

**The rule that explains both, so neither seam's test gets "consolidated" into the other's shape:** a protected write is refused by the **executor in every mode** — both executors call `protected_refusal` unconditionally, *"straight after `validate` and with no test of `ctx.file_policy.writes`"* — and by the **gate only on a `Deny` verdict**, because under `Allow` the verdict is `Allow`, `dispatch_tool` runs, and `deny_tool_result` (which only answers a `Deny`) never fires. The same bug is therefore visible on `is_error` at one seam and only on the wording at the other. `access.rs` names this as the paragraph the obvious story gets wrong: *"What that mismatch costs is worth stating exactly, because the obvious story is wrong."*

**Why the gate checks the deny-list before the boundary** (the shipped ordering comment in `loop/gate.rs`, and the reason the wording is a correctness property and not cosmetics):

> The deny-list is a WRITE-floor question (`protected_dirs` are dirs a WRITE may not enter), and it is checked BEFORE the boundary: the refusal is true in every policy, so its wording must win over "escapes the sandbox", which would send the model hunting for a boundary that is not the problem.

**`PROTECTED_WRITE_ROUTE` is the one contract both seams assert against the same const**, so the two families cannot drift into two literals: *"Both live in [`PROTECTED_WRITE_ROUTE`] so the executor-side and gate-side test families assert the SAME value rather than two literals that can drift, and the gate gets them for free — it calls this function, which is the whole reason the split exists."* The gate asserts it **by its full path, no re-export**. Its value, as shipped:

> This is by design: these directories are the agent's own instructions. Write the file under your session directory instead and ask the user to move it into place (the `ask` tool).

and issue #33's rule is pinned **negatively** by `write_into_a_protected_dir_is_refused_under_every_policy`: the route must NOT name a shell or an elevated route, because *"naming an elevated route there is what sent the reporting agent reaching for one over a markdown file"*.

## How the bug survived, measured — and the one shipped sentence that needs scoping

`fc7b635`'s message says: *"The tests key on `is_error`, not on the refusal TEXT — a test asserting only the text stays green through this bug, which is exactly how it survived."* Keep the first clause; **scope the second**, because as an unscoped universal it is false at one of the two seams. At the **executor** seam a no-op deny-list means the write **lands**, so a wording-only assertion there would have gone red too — there is no refusal to read. The sentence's real, and true, content is (i) the new tests key on `is_error` so the half-fix is *observable*, and (ii) at the **gate** seam, where a refusal still exists but is worded as a boundary escape, an `is_error`-only test genuinely stays green before and after.

**The measured reason the bug survived is a fixture fact, not a counterfactual.** For every protected-dir test that pre-dates #92, does the fixture *create* the entry directory? Re-run at execution time (counting `create_dir_all` inside each test body): `write_into_a_protected_dir_is_refused_under_every_policy` **1**, `write_a_new_file_under_a_protected_dir_is_refused` **1**, `a_raw_protected_entry_still_refuses_a_canonical_path_under_it` **1**, `a_raw_argument_still_refuses_against_canonical_protected_entries` **1**, `a_gate_denial_of_a_protected_dir_uses_the_protected_wording` **1**, `protected_dirs_are_the_four_user_level_dirs` **1**, `protected_dirs_never_include_a_space_level_dir` **1**, and `tests/skill_tools_boundary.rs` — which uses the **real** `protected_dirs()` and asserts `protected.contains(&real.path().join(".agents/skills").canonicalize().unwrap())` — creates its skill dir too. **Every pre-#92 fixture creates its entry.** So no test ever handed the comparison a missing entry, lenient and strict were identical on every existing path, and the whole suite was blind to the hole by construction. That is the reason the bug survived, and it is why the two new tests' *fixtures* (not just their assertions) are the contribution.

## What survives of the strict canonicalizer: the read side is strict ON PURPOSE

0079's "what survives / what falls" idiom, applied in the positive: almost all of the strict canonicalizer survives, and the part that survives does so **because it is the opposite policy**, not by accident.

**The direction argument is the whole reason.** A lenient **deny-list** entry can only ever add refusals — `push_protected`'s doc: *"Here the leniency only ever DENIES more."* A lenient **read** root **widens what is readable**, to directories that do not exist yet — a security widening #92 never asked for. So the two sides are not inconsistent; they are opposite deliberately, and that is why the leniency is a separate function and not a parameter:

> This is the reverse of [`push_roots`], deliberately, and it is a separate function rather than a flag on that one because the flag would select a SECURITY policy: a lenient READ root silently WIDENS what is readable, and a seventh `push_roots` call could opt into it by accident. Here the leniency only ever DENIES more.

That quoted sentence is shipped text, and the arithmetic behind the word "seventh" is **this ADR's analysis, not shipped text**. Measured at HEAD: `push_roots(` has **four** call sites, all four inside `read_roots` (the user- and space-level skills and agents roots); `push_protected` has **two**. A flag design would have absorbed those two deny-list calls into `push_roots`, giving six call sites — so "a seventh" is the next one anyone adds after the two policies have already been merged into one signature. The claim is about how a flag spreads, and the count is consistent with it; the number itself is derived here.

**The proof, re-run at execution (not inherited from T06 — and this is a *stronger* claim than T06's, because four commits landed after `fc7b635`).** Six read-side helper **bodies** in `boundary.rs`, extracted with `sed` between the `fn` line and its closing brace and hashed, compared `fc7b635^` → HEAD (`54ba649`):

| Helper | Hash (both sides) | Verdict |
|---|---|---|
| `canon` | `ae015d29` | SAME |
| `push_roots` | `2c9da05b` | SAME |
| `read_roots` | `55f28c0e` | SAME |
| `write_roots` | `16ab538d` | SAME |
| `executor_roots` | `fc8295c8` | SAME |
| `unrestricted_floor` | `5471f9c5` | SAME |

**Enumerated deliberately: those six helpers, and nothing broader.** "Byte-identical" here means *these six function bodies hash equal across `fc7b635^ → 54ba649`*. It does **not** mean `boundary.rs` is unchanged — `fc7b635` added **178 lines and deleted 6** in that file (`push_protected`, two new doc paragraphs, two new tests) — and it must not be quoted as "all of `boundary.rs`". Corollaries of the same measurement: `push_roots` keeps **all four** of its call sites, all inside `read_roots`, and **no parameter was added to it**.

**The pin: `a_nonexistent_root_is_dropped` passed UNMODIFIED**, and it pins both halves of the surviving rule — with the four user dirs absent the boundary is exactly `[canonical cwd]`, and with a missing `cwd` the boundary is **empty**, which the `FsBackend` treats as an error, i.e. fail closed. The two shipped sentences that state the opposite rule are unchanged and are the record of the decision: `read_roots`'s doc — *"Every root is canonicalized; a root that fails to canonicalize (a missing dir) is simply not part of the boundary"* — and `canon`'s own — *"dropping it when it fails (a missing dir is simply not part of the boundary — the boundary is allowed to name dirs that do not exist, and a nonexistent dir contains nothing)"*. Both are still true of the **boundary**, and that is exactly the point of the split.

**The accepted gap this leaves: read-boundary staleness.** A directory created mid-session under a read root is not readable until restart. It was recorded on the branch's follow-ups list as *"recorded, not open work"* — and that file is deleted on ship, so **this section is its durable copy**. Say the consequence plainly: after #92 the **deny-list is fresher than the read boundary**. A directory that appears mid-session is immediately protected from writes and still unreadable until restart. That asymmetry is accepted, not overlooked, and it is the direction the two helpers encode.

**The Landlock consumer, and its status label.** `sandbox.rs` feeds `protected_dirs()` straight into `Sandbox::rule_write_root`, whose arms are plain string comparisons over the entries (`root == p || root.starts_with(p)`, then `canonical.starts_with(p)`, then `p.starts_with(&canonical)` before falling through to `rule_root_around_protected`), so entries that do not exist now participate in a **ruleset** decision. T06 measured the classification difference — a fresh install's write root `$HOME` with nothing under it, ruled against a not-yet-existing `$HOME/.agents/skills`, moves from the full read-write arm into the carve-out-around arm (`READ_WRITE` on `/tmp`-style temp roots becomes the `rule_root_around_protected` path) — by **re-implementing the three predicates in a throwaway program**, not by building a Landlock ruleset and confining a process. Label it what it is: **classification by re-implementation, not behavioural proof.** And no sandbox test changed state: `a_session_cwd_inside_a_protected_dir_cannot_write_there` creates its root (so it hits the "root is inside a protected dir" arm identically under strict and lenient), and `a_write_root_containing_a_protected_dir_stays_writable_around_it` already reached the carve-out arm under strict.

> **Naming note, so nobody greps for a symbol that does not exist.** `CARVE_AROUND` is **not a code symbol** in this tree — measured, it appears nowhere outside the gitignored planning docs. The real names are `READ_WRITE`, `READ_EXECUTE`, `Sandbox::rule_write_root` and `Sandbox::rule_root_around_protected`; the arm is described here in prose ("the carve-out-around arm") rather than by a label.

**The `/tmp`-under-`$HOME` hazard — and this paragraph is its only durable home.** If `$HOME` itself lives **under `/tmp`**, the lenient entries make the ruleset demote `/tmp` from read-write to read+execute, which would redden the two confined tests that write there — `a_confined_command_works_normally_inside_the_boundary` and `a_confined_shell_can_still_do_ordinary_things`, both of which run `TMPDIR=/tmp mktemp`. Neither pins `$HOME`, and Linux CI leaves `HOME` at the runner's real home, so the expectation is green — but a developer running the suite with `HOME` under `/tmp` would see two reds that look unrelated to anything. Measured: grepping the tracked tree (outside `docs/roadmap/`) for a `$HOME`-under-`/tmp` hazard, or for the arm label the planner used, returns **nothing** — the gitignored T06 plan was the only carrier and it dies on ship. **If those two tests ever redden, check `$HOME` before re-diagnosing Landlock.** That is the difference between understanding it in a minute and diagnosing it from scratch.

## The recorded residue: an entry that cannot be resolved at all comes back RAW

`canonicalize_lenient`'s `Err` arm returns `path.to_path_buf()` — the path **unchanged** — when nothing on it resolves. Such an entry is still **kept**, and a raw entry **cannot prefix-match a canonical path**, so on macOS (`/var` → `/private/var`) or Windows (a verbatim `\\?\C:\…` against a bare `C:\…`) a write into such a directory is **NOT refused**. Shipped, in `access.rs`:

> The recorded residue (#92, D3): an entry whose whole path cannot be resolved at all comes back RAW, and a raw entry cannot prefix-match a canonical resolved path — so on macOS (`/var` → `/private/var`) or Windows (`\\?\C:\…`) a write into such a dir is NOT refused. That is strictly better than the pre-#92 behaviour, where the dir was dropped from the list outright, and nothing fixes it by peeling harder because there is nothing to peel to. Pinned by `protected_dirs_keeps_an_unresolvable_entry_raw`.

**Strictly better than what it replaces** — that comparison is the reason the residue is acceptable rather than merely tolerated: pre-#92 such a directory was dropped outright and the session carried **no deny-list entry at all**; now it carries one that names the directory and refuses whenever the two spellings agree.

**The pin has two halves and one of them is deliberately green.** `protected_dirs_keeps_an_unresolvable_entry_raw` asserts (i) the four entries **SURVIVE with their raw spelling** (RED before the fix) and (ii) that `protected_refusal_text` returns **`None`** for a canonical target elsewhere — **GREEN before AND after the fix**. The shipped doc comment names that second half as a pin that must not be "fixed":

> WHAT IT DOES NOT PROVE (the GREEN half, before AND after the fix — a pin, deliberately not a failure, so the next reader does not "fix" it into one): a RAW entry cannot prefix-match a CANONICAL resolved path, so a write into such a dir is NOT refused. That is the residue D3 names, stated as an assertion so it cannot be quietly forgotten. It is not fixed here because there is nothing to peel to.

Turning that `None` into a failure would assert something the code cannot deliver.

**D3's stated trigger does not fire on unix — the correction, and its source.** The approved design text says the raw path arrives *"if NO ancestor of a protected dir exists at all when the list is built (`~/.pi` itself absent)"*. Measured, and recorded by T06 as its Finding 1 (the ADR is its named durable home): with `~/.pi` absent and `$HOME` present, the peel **succeeds** at `$HOME` and re-applies three components — the entry is **not** raw — and on Linux the re-applied spelling is **textually equal to the input**, so a naive "did it come back raw?" check **reads as raw and tests nothing**. On unix an absolute `$HOME` always peels to at least `/`, so the "no ancestor at all" `Err` arm is unreachable from it. The `Err` arms a real `$HOME` can actually reach are a **relative `$HOME` that does not exist relative to the process `cwd`**, and on Windows a **`USERPROFILE` on an unmounted drive** (`Path::pop` on `Z:\` returns `false`). The fixture is built on exactly the relative-`$HOME` shape so the path is exercised for real, and its comment explains why that is safe: the unlocked `$HOME` readers in the suite either canonicalize-and-discard or use the value for an existence probe whose answer is already "absent" in CI, and there is deliberately **no `set_current_dir`** because the suite is multi-threaded and `cwd` is process-global. Quote-worthy, because it is the reason nobody "simplifies" the fixture into something vacuous: *"A future UNLOCKED reader that JOINS onto `$HOME` and writes would be the one to break."*

**Windows honesty, per 0060's standard.** The mingw target **type-checks** this code; nothing Windows-behavioural was run here or in `fc7b635`, and the Landlock module is not even compiled for Windows. Everything above about macOS and Windows spelling mismatch is an **argument from source plus ADR 0064's verbatim-path story**, not an observation.

## The over-refusal found by mutation and deliberately NOT fixed

Peeling an entry to its canonical ancestor is **coarse**, and the comparison is a plain `starts_with` on the re-applied trailing components. So an entry `…/.pi/agent/agents` that does not exist is kept as `…/.pi/agent` + `agents`, and a comparison deliberately made **over-broad** — matching at the ancestor and ignoring the trailing components — **survives the entire suite**. Measured: there is **no fixture anywhere** that writes into a protected directory's own **parent** and asserts success. `grep -rn 'join(".pi/agent")|join(".agents")'` over `src-tauri/src` and `src-tauri/tests` returns four hits: three `create_dir_all` calls **inside the #92 fixtures themselves**, which build `.pi/agent` purely as the peel ANCHOR and never write into it, plus `worker/core.rs`'s unrelated `.pi/agent` data path. Nothing pins that a legitimate write next to a protected entry stays allowed.

**Why it was left, in the shipped code's own terms** — the comparison's only power is to deny, so slop at this seam errs toward refusing, never toward permitting:

> At THIS seam that only ever errs toward a FALSE POSITIVE — an over-refusal — because the comparison's only power is to DENY (a deny-list match refuses; nothing here can grant anything).

**The cost that made it not worth paying in this commit was measured, not assumed:** pinning it moves the suite's test count by **five, not four**, and `fc7b635`'s gate was planned as A0 + exactly four (the fifth test would have had to land in a commit whose delta was pre-committed). `fc7b635` records exactly this: *"It is an over-refusal, not a hole, and pinning it would move the test count by five, not four."* A deliberate trade with its arithmetic stated, not an oversight.

**The missing pin, concretely** (this is a **Rust** task's work — it cannot ride this ADR, which runs no `cargo`): an executor test with `writes: Allow` whose target is `$HOME/.pi/agent/allowed.md` — the **parent** of a protected entry, with the entry itself missing — asserting `!is_error` and that the file lands. It belongs in `exec/tests/policy.rs`, beside the two session-snapshot tests whose fixture shape it reuses minus the recreation.

**The stale comment this finding exposes.** `rule_write_root`'s comment still reads *"Compare CANONICAL paths: `protected_dirs` is canonicalized"*. After #92 an entry may be **non-canonical** — trailing components re-applied, or fully raw. The comparison still behaves; the **claim** needs scoping. `sandbox.rs` is not this ADR's file, so it is a Consequences line.

## The copy half of #92: the two bugs meet only here

#92 was **two bugs in two languages**, landed in two commits in two waves: `665731c` (frontend copy) and `fc7b635` (Rust). No other document joins them — measured, **no page in `docs/features/` mentions the protected dirs, the deny-list, or the guard-rail wording at all** (`grep -rn -iE "protected|deny-list|guard-rail" docs/features/ docs/css-theme-tokens.md` → empty; the same command shape over `docs/decisions/` returns four files at the base commit, so the empty result is armed and real), and the roadmap family is deleted on ship. This ADR is therefore the only durable place that says **why** the copy and the deny-list are one issue.

The Settings Writes row told the user the protected agent-definition directories are ones the agent *"can never rewrite"*. That is false under `shell: allow` — the shipped default — and false for `sudo_exec`, which is not policed. Because issue #33 **forbids** the refusal from naming the bypass route, that row is the **only** disclosure surface for the limit, and it stated the opposite of what 0030 decided. `665731c`'s message records the failure mode, and it is the same failure mode as the deny-list's: **"No test pinned the copy; that is how it came to be wrong."** Both halves of #92 are the harness reporting a protection it does not have — one to the model and the transcript, one to the human.

The corrected row is deliberately **list-scoped**, and the shipped comment names itself as the sole disclosure: *"the refusal is scoped to the protected LIST, not to a path: a directory is covered because the list names it, which is what the code actually does."* The copy itself: *"the guard-rail follows that list rather than the folder, so a directory the list does not name is not covered by it."* `665731c` called that framing an *"Interim gap, disclosed rather than papered over"* for the window in which the list could go stale — **and #92's Rust half closes that window**: the list no longer goes stale when a protected directory is created mid-session. That is the sentence that belongs to no other document, so it is here.

The pin is `the_writes_row_discloses_the_carve_out_is_a_guard_rail_not_a_boundary`, and its three-way claim checks out against `SettingsPage.test.tsx`: matcher **(d)** must FAIL on the old copy (which matched `never rewrite`), FAIL on the rejected overclaiming draft (which matched `under any policy`), and PASS on the shipped copy. The shipped comment gives the reason: *"a pin that passes on the copy it exists to police is worse than no pin"* (`665731c` states the same rule as *"a matcher that passes on the overclaim it exists to veto is worse than no pin"*).

## What refutes this

**The refuting observation: a write into a recreated protected directory is ever observed SUCCEEDING.** Concretely: a session that started before `~/.pi/agent/agents` existed, where the user (or the agent's own first write) creates it, and a subsequent `write`/`edit` into it returns success and lands the file. That is #92's exact repro shape, and if it happens with **both** halves shipped then the two-sided fix is **incomplete**, not merely regressed.

**What would count as observing it:** a real session's transcript showing a successful write result naming a path under `~/.pi/agent/…` — the success sentence `FsBackend`'s write path builds (`format!("Wrote {bytes} bytes to {path}")`) — in a session whose deny-list snapshot predates the directory.

**Three near-misses that are NOT the refutation**, so nobody closes the issue on a lookalike:

1. **A write that reaches those directories through `bash` or `sudo_exec` is by design.** 0030 says the carve-out is a guard-rail and not a security boundary, and issue #33 *forbids* the refusal from naming that route — which is precisely why the Settings row is the only disclosure surface (`665731c`). A shell write into `~/.agents/skills` is the design working, not failing.
2. **A write into a directory whose whole path could not be resolved** is the **recorded residue**, already pinned as a `None` by `protected_dirs_keeps_an_unresolvable_entry_raw`. It is a known, accepted non-match, not a regression of the two halves.
3. **A write refused with "escapes the session sandbox" instead of the protected wording** is the **gate wording** bug, which `fc7b635` closed. It refuses correctly; only the sentence was wrong.

**What changes if it is observed** — and this is what makes the falsifier costed rather than rhetorical: the rejected option becomes the requirement. The deny-list stops being a session constant and is **recomputed per guarded write**, or the frozen `ctx.protected` is refreshed. The artifacts that would have to move, all named: `AgentLoop::new`'s single `protected_dirs()` call; `ToolCtx::protected`'s doc (*"frozen at session start; `vec![]` in tests"*); `AgentLoop`'s own `protected` field doc (*"frozen with the boundary"*); `protected_dirs`'s doc sentence *"this list is frozen for the Session's life (`AgentLoop::new`)"*; and the premise sentences of both session-snapshot tests, which exist to pin "no restart".

**Stated as live, not discharged** (0079's standard, and 0080's). Nothing in this tree observes real sessions. The closest available evidence points the right way — both session-snapshot tests build the snapshot while the directory is missing and refuse after it is recreated — but **a green fixture is not an observation of the wild**. "No such write has been seen" may not be upgraded into "none exists."

**The glossary, credited first and corrected second.** `CONTEXT.md`'s **Lenient deny-list entry** entry (corrected at `c801445`, before this code shipped) already states the two-sided design, and its sentence *"the comparison that consumes it must canonicalize BOTH sides leniently — a strict `canonicalize()` on an entry that is still missing simply fails, and a failed compare is a silent non-match"* **is this ADR's central claim**, written into the glossary before the implementation landed. That is house doctrine, not this ADR's discovery, and it is credited here in 0080's idiom. **Where it over-claims, by exactly one clause:** it states the protection unconditionally — *"so a Session that recreates `~/.pi/agent/agents` is refused writing into it immediately, with no restart"* — with no room for the residue (an entry whose whole path cannot be resolved is kept raw and does **not** refuse), and no hint that the ancestor peel errs toward over-refusal. One clause deserves scoping — the unconditional refusal should become conditional on the entry actually resolving (something like "… unless nothing on its path resolves"), and it goes to follow-ups as a one-clause amendment. `CONTEXT.md` is **not edited by this ADR**: reading it is free, editing it is not.

## Considered Options

- **Keep only change (1) — keep the entries, leave the comparison strict**: rejected — a **silent no-op**, the exact failure mode being fixed. This is the option a reader is most likely to re-propose ("the list is what matters"), so the rejection names the mechanism: `is_ok_and` on a failing `canonicalize()` is `false`, and `false` in a `find` predicate is indistinguishable from "not on the list". Pinned by `a_write_into_a_still_missing_protected_dir_is_refused`.
- **Recompute `protected_dirs()` per guarded write**: rejected — `ctx.protected` is computed **once per session** at `AgentLoop::new` and cloned per tool call, so per-write recomputation replaces a constant with a filesystem walk on the hot path and turns a session constant into a live query. **Named here as the option the falsifier resurrects** — a rejection with a stated revival condition, not a closed door.
- **Make `push_roots` lenient for `read_roots` too — a flag, or one shared lenient helper**: rejected — leniency on a read root **widens read access** to not-yet-existing agent directories, a security widening #92 never asked for; and a flag puts that choice in the signature of a shared helper where, in the shipped words, *"a seventh `push_roots` call could opt into it by accident"*. Hence a **separate function**, whose name is the policy.
- **Peel harder to close the residue — compare the entry's canonical ancestor so a raw entry matches**: rejected — it does not fix the residue (an unresolvable path has nothing to peel to) and it **widens the refusal** into the ancestor, which is exactly the unpinned over-refusal recorded above. **These two rejections are the same argument from opposite sides**, and it is worth saying so: peeling less would have kept the hole, peeling more would have broadened a refusal nothing asked to broaden.
- **Assert the refusal TEXT as the discriminator**: rejected — at the executor seam the failure mode is the write **landing**, where there is no refusal text at all to assert; and at the gate seam the wording is needed **in addition to** `is_error`, not instead of it. Both seams above.
- **Strengthen the premise to `!protected.is_empty()`** (or add it alongside): rejected — it passes on a non-empty list of **wrong** entries, which is precisely what the ancestor-peel mutation produces. That mutation is the measurement that proves the rejection.
- **Set `superseded-by`, or append a *Partial:* note to ADR 0030**: rejected — 0030 is the deny-list's host and **every decision it wrote survives re-affirmed**; it never stated the drop or the entry canonicalization, so there is nothing to narrow, and it is merged to `main` hence append-only (0033 states the convention: *"Stated here rather than in 0031 because that ADR is merged, hence append-only."*). The fallen claims were two source doc-comment sentences, both already deleted in `fc7b635`.

## Consequences

- **The two halves are ONE change, and a refactor can re-open #92 without touching either test's name.** Any change that moves the entry-side `canonicalize_lenient` back to a strict `canonicalize()` — or that canonicalizes the entries at build time and then compares them strictly — silently re-opens the hole, and **only** `a_write_into_a_still_missing_protected_dir_is_refused` will see it. If that test is ever edited, edit it in the direction of *more* specificity, never less.
- **A new deny-list entry means a new `push_protected` call; a new READ root means a new `push_roots` call.** Never the reverse, and never a unified helper. The two functions **are** the security policy — one only ever denies more, the other only ever grants more reach — and they are not interchangeable.
- **The deny-list is now fresher than the read boundary, deliberately.** A directory created mid-session is protected from writes immediately and still unreadable until restart. Recorded, accepted, and this is the durable copy of a line that otherwise dies with the branch's follow-ups file on ship.
- **The residue is permanent, not deferred.** There is no fix for an unresolvable path. `protected_dirs_keeps_an_unresolvable_entry_raw`'s `None` assertion must stay **green**; converting it into a failure would claim protection the code cannot deliver, and the test's own comment warns against exactly that.
- **`a_recreated_protected_dir_is_refused_by_the_gate_without_a_new_session` is the only test that drives the real `AgentLoop::new` snapshot** for this bug. It is not a duplicate of its executor twin — different seam, different discriminator (`is_error` there, wording here) — and deleting or "consolidating" it leaves the gate's copy of the wording unpinned against a session-start snapshot.
- **Five of the new/renamed tests pin `$HOME`, and that carries a blast radius worth naming.** Measured by counting the `$HOME` writes inside each new test body: `protected_dirs_keep_a_missing_dir` pins it through the `pin_empty_home` helper (a temp dir), and `a_recreated_protected_dir_is_refused_without_a_new_session`, `a_write_into_a_still_missing_protected_dir_is_refused` and `a_recreated_protected_dir_is_refused_by_the_gate_without_a_new_session` each call `set_var("HOME", …)` to a temp dir, while `protected_dirs_keeps_an_unresolvable_entry_raw` pins it to a **relative, deliberately non-existent** path. All five hold `env_lock` for the whole set→assert→restore span. The shipped comments name the unlocked `$HOME` readers that make this safe; **the thing that would break them is a new unlocked reader that joins onto `$HOME` and writes.** That is a standing hazard for anyone adding tests, and this ADR is the only durable place it is written down.

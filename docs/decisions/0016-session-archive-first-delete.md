# Session archive-first delete, and delete removes the desktop's copy only

Deleting a stored Session is offered **only from the Archived section** of the sidebar, never from a Space group's session rows. A stored row's hover action is **Archive** (hide from the Space group, keep in storage, still openable/resumable); the Archived section offers **Unarchive** and **Delete** (confirm dialog). The pattern is taken from ZCode: the main list's action is archive, so a transcript is never destroyed by a single misclick — deletion is two deliberate steps away (archive → find in Archived → confirm).

Deleting a session removes **the desktop's copy only**: the `sessions` row and its `messages` / `native_messages` rows (the existing `delete_session` cascade). The agent's own on-disk session file (the `piSessionFile` capability, e.g. under `~/.pi/`) is **left untouched**.

**Considered Options**

- **Delete directly on main-list rows** (a trash icon beside Archive, confirm dialog): rejected for v1 — one click away from destroying a transcript, and it makes Archive a redundant affordance. Archive-first is the ZCode pattern and the safer default; a direct delete can be added later without breaking the archive flow.
- **Delete the agent's session file too** (truly permanent): rejected — the file lives in the user's pi home directory, which they may use from the pi CLI directly; the desktop deleting files out from under another tool's home dir is surprising, and a bug in the delete path (the path is a string from a JSON blob) could delete the wrong file irrecoverably. Orphaned pi session files are small; "purge agent files" is a separate, future feature if ever wanted.
- **Archive = a separate table / soft-delete flag with no UI view**: rejected — without search, an archived session with no way to find it is a dead end; the Archived section is what makes archive a real state instead of a tombstone.

**Consequences**

- The `sessions` table gains an `archived` flag (one-time `ALTER TABLE` migration, same pattern as `spaces.trusted`); `list_sessions` filters on it. The flag is **sticky** — it survives resume/pause and changes only via explicit Archive/Unarchive.
- Archiving hides a session from its Space group but NOT from resumability: an archived session opens and resumes exactly like a stored one.
- Orphaned agent-side session files accumulate on disk after deletes. They are unresumable from the desktop (resume reads the desktop's DB) and harmless; cleanup is out of scope.
- Live sessions are never archived: a live row's hover action stays Pause; pause → stored → archive is the two-step path.

## Amendment (2026-10-20) — Archive reaches a live Session and stops it on the way in; the Pause consequence is corrected

**AMENDED 2026-10-20 — the reach of Archive, and one Consequences bullet that stopped being true two days after this ADR was written.** What stands unchanged: delete stays two deliberate steps from a transcript — **only** the Archived section offers it, behind a confirm — Archive stays hide-not-destroy (the `sessions` row and its transcript survive, the session stays openable and resumable), and the flag stays **sticky**. This ADR is NOT superseded and its `status` is unchanged; the Consequences bullet about live rows is deliberately left standing above as written, and corrected here rather than edited, because it is the record of what was true when the decision was taken.

**What changed.** A live Session can now be archived directly: `SessionRow` (`src/components/SpacesList.tsx`) no longer branches on `isLive`, so every row swaps its time slot for actions on hover — a live row offers **Stop** then **Archive**, a stored row offers **Archive** alone. `archiveSession` (`src/store/sessions.ts`) accepts a live id (it used to return early unless the id was in `historySessions`, so a live id never even reached the backend), commits the `archived` flag, moves the row into `archivedSessions`, and THEN — only if the id was live at click time (`wasLive`, captured before the `await`) — closes the Session, so its **Worker process** is reaped. Archiving is therefore still a *view* property of a **stored** Session and now a lifecycle act on a **live** one; `CONTEXT.md`'s "Archived session" entry says exactly that.

**The order is flag-then-close, and it is load-bearing.** Nothing was added to the close path to route an archived row into the Archived section: `handleSessionClosed` already refuses to file a closing Session under `historySessions` when its id is in `archivedSessions` (the `!state.archivedSessions.some(…)` guard in its `historySessions:` arm, `src/store/sessions.ts`) — that is the sticky rule this ADR's first Consequences bullet already promised. Committing the flag and moving the lists FIRST is what lets that existing guard do the landing, so the row surfaces in Archived and nowhere else. Close-first would race the async `session-closed` event against the store move and flicker the row through its **Space** group on its way out. No Rust change was needed either way: `set_session_archived` is an id-only `UPDATE` with no liveness condition, and `record_session`'s upsert never touches `archived`, so a re-record on resume cannot clobber the flag.

**The close is best-effort; the flag is not.** A close that fails (a delete winning the mid-await race, say) is logged and swallowed, and the flag is NOT rolled back — Archive's one durable job, hiding the row from the next boot, has already been done. The asymmetry with **Stop** below is deliberate: `stopSession`'s rejections PROPAGATE, because Stop has no durable effect behind it, so a Stop that reported success while the Worker kept running would be a lie the row cannot correct.

**One accepted transient.** Between the store move and the arriving `session-closed`, the row still reads as a live row in its **Space** group, because `ArchivedSection` view-filters live ids out of the Archived list. The row therefore makes ONE visual move rather than appearing in Archived and then again. Dropping that filter to close the gap is forbidden by the sticky rule — it is what stops a resumed archived Session from rendering twice.

**Stop is a second action, not a second name for Archive.** `stopSession` (`src/store/sessions.ts`) decides at click time from `inTurn` — never from a render-time status, because paint and click are not the same tick: a turn in flight → `cancelSession`, which keeps the Worker so the Session stays live and immediately re-promptable; live and idle → `closeSession`, which reaps the Worker and drops the row to stored (an archived row that is live — the sticky pair — lands back in Archived rather than in the Space group, which is the guard above doing its job). A non-live id gets neither command. The branch is safe in both directions, and that is what makes one button honest: `close_session` marks the in-flight turn a cancel (`cancel_requested = true`) BEFORE it detaches the Worker, so the close arm cannot leave a turn running even if a turn started in between, and `cancel_session`'s abort is a documented no-op when there is no in-flight turn, so the opposite interleaving is merely a no-op. Archive hides the row; Stop never does — an idle Stop leaves it in the Space group as a stored row.

**The Consequences bullet "Live sessions are never archived: a live row's hover action stays Pause; pause → stored → archive is the two-step path" no longer holds, and has been false since `874a7b7` (2026-10-03)** — two days after this ADR — which deleted the Pause button from the sidebar row; there is no pause affordance in the UI to walk. "Live sessions are never archived" was the sentence that quietly left a running Session with no way to be stopped or put away short of opening it first. It is replaced by: **a live row's hover actions are Stop and Archive; Archive on a live row archives and stops it in one act, and Stop stops without archiving.** "Pause → stored → archive is the two-step path" is gone with it — the path is now one step, and the two-step path this bullet was contrasting it against (archive → find in Archived → delete) is unchanged.

**Delete is still two deliberate steps away, and nothing above weakens that.** Delete remains offered only from the Archived section, only through `ArchivedSessionRow`, still behind `DeleteSessionDialog`'s confirm. What a single misclick on a live row can now cost is one stopped Session whose transcript is intact and whose row is resumable from the Archived section — never a destroyed one. The archive-first guarantee, which is this ADR's actual decision, is intact.

## Amendment (2026-10-21) — the Archived section is Space-scoped, and Settings → Sessions becomes the second door to Delete

**AMENDED 2026-10-21 — the reach of the Archived section, and the sentence "Delete is offered only from the Archived section."** What stands unchanged: deleting a Session removes **the desktop's copy only**, still cascading `messages` / `native_messages` and leaving the agent's own session file untouched; per-row Delete is still behind a confirm; the flag is still **sticky**; and Archive is still hide-not-destroy. This ADR is NOT superseded and its `status` is unchanged.

**What changed.** `ArchivedSection` (`src/components/SpacesList.tsx`) had been flat and cross-Space since it was written — its own comment said so, citing the ZCode `WorkspaceArchivedTasksFlatSection` model, and the row carried a `· {spaceName}` suffix to disambiguate it. It now filters on the active Space (`s.cwd === activeSpacePath`), keeping the live-id filter that carries the sticky rule. So the header count is per-Space and the `· {spaceName}` suffix is gone: in a Space-scoped list the row can never belong to another Space, so the suffix was either redundant (`titleFor` already falls back to the Space name, which `showSuffix` suppressed) or noise on a generated title.

**Why this needed a second door rather than just a filter.** Closing a tab **forgets** the Space and deletes nothing (ADR 0043 — `closeSpace` → `removeSpace` touches no `sessions` row), so the flat section was the only place a stored Session of a closed Space appeared anywhere in the UI, and this ADR made it the only door to Delete. Filtering it would have made those rows unreachable — not hidden, unreachable — turning "delete is two deliberate steps away" into "delete is impossible unless you remember which folder it came from". So **Settings → Sessions** (`src/components/settings/SessionsSection.tsx`) lists every **Detached** Session — a stored Session whose `cwd` matches no Space row, archived or not — and offers **Reopen Space** (the existing `addSpace`, so the row returns to the sidebar as a normal row) and **Delete** (the existing `deleteSession`, the existing confirm). The archive-first guarantee is intact for every individual row: a transcript is still never destroyed by one incidental action, and a misclick on a sidebar row still costs one stopped Session, never a deleted one.

**"Only from the Archived section" becomes "from the Archived section, or from Settings → Sessions".** Those are the two doors, and both are confirms. The second is not a shortcut around archive-first: a Detached row is one you cannot reach from the sidebar at all, so requiring it to be archived first would mean re-opening the folder to archive it before deleting it — busywork in service of a protection the row does not need.

**Clear all is the one bulk door, and it is deliberate.** Settings → Sessions carries a **Clear all** that deletes every Detached transcript behind one confirm. That is the widest blast radius in the app and it is exactly what this ADR's Considered Options rejected for the *main list* — so it is worth stating why it is accepted here and not there. The main list is where a user works, an incidental click lands there, and its rows are individually reachable, so a bulk control there would put a mass deletion in the path of ordinary use. A Detached Session is by definition not in that path: it has no tab, no row, and no way to be worked on, so the section that lists them exists solely for housekeeping and is reached only by opening it on purpose. The confirm is required to name the count and the folders (`Delete N sessions from M folders?` plus the folder names), because N is the number that matters and the folders are what tell you whether this is the sweep you meant — `ClearDetachedSessionsDialog`, `showCloseButton={false}`, so Cancel/Escape are the only exits.

**Considered, and rejected:** a This-Space / All-Spaces toggle on the Archived section — rejected as a mode the user has to remember is on, needing persisted UI state no other control in that pane owns; and a separate ADR superseding this one — rejected because nothing above reverses this ADR's decision, only its stated reach.

# The webview asserts its own key focus ungated, because Linux and macOS both deliver the focus-in that triggers it

At fresh launch — the window revealed by `tauri-plugin-window-state` and never clicked — no key event reaches the renderer: not the `⌘/Ctrl+N`/`⌘/Ctrl+O` chords, not typing, not `Escape`; clicking a neutral area makes all of them work. The plugin's reveal asks for the **window's** focus and never touches the webview **widget** whose key focus gates key dispatch (`WebviewWindow::set_focus` → tao's `WindowRequest::Focus` → `present_with_time()`). We decided: assert it at the webview level — `Webview::set_focus()` through one `grab_webview_key_focus` seam (`src-tauri/src/lib.rs`) — from the existing `run` callback on `RunEvent::Ready` **and** on `RunEvent::WindowEvent { event: WindowEvent::Focused(true), .. }`, with **no `cfg` gate on any platform**, and carry that event's per-platform delivery matrix as a first-class consequence rather than a footnote.

This supersedes ADR 0056 — pushed to `origin/main`, so the append-only rule binds and its body stands untouched — because its platform claims are false, and a false platform claim here is not inert: it is what invites a reader to narrow the call, or to leave the real risk out of a review. Two corrections, verified against the resolved crates (`tauri-runtime-wry` 2.12.1, `tao` 0.37.1, `wry` 0.57.0):

1. **`Focused(true)` is not Linux-only.** `WindowEventWrapper::map_from_tao` opens with `#[cfg(not(windows))] return Self(Some(WindowEvent::Focused(*focused)));` (`tauri-runtime-wry/src/lib.rs:522-524`) — the early return runs on every non-Windows platform, so macOS delivers it too. The `Self(None)` fall-through for "no children, non-empty `webviews`" (`:563-565`), our exact shape, sits inside the `#[cfg(windows)]` block that follows: **Windows alone** drops the event. 0056 also marshalled wry's note that the `focused` **creation attribute** is unsupported on macOS (`wry-0.57.0/src/lib.rs:769-774`) as if it were about event delivery; a build-time attribute and a runtime event are different things.
2. **On Linux the arm does not "also fire for webview focus changes".** tauri's synthesised webview `Focused(true)` comes from `add_focus_change_listeners`, which is `#[cfg(windows)]` (`:5333-5336`) and called from a `#[cfg(windows)]` block (`:5226`). On Linux the only source is tao's `connect_focus_in_event` (`tao-0.37.1/src/platform_impl/linux/event_loop.rs:641`) — a **GtkWindow** focus event, i.e. window activation, never an intra-window widget focus change. So 0056's safety argument ("it only moves focus between widgets of the same GTK window, and we have one widget") defends a mechanism that does not exist on the platform it discusses, and misses the hazard that does: on **macOS**, `Webview::focus()` runs `self.webview.window().unwrap()` before `makeFirstResponder` (`wry-0.57.0/src/wkwebview/mod.rs:1057-1064`) — an unwrap inside the event-loop callback.

## Delivery matrix — who delivers `WindowEvent::Focused(true)`, and from where

| Platform | Delivered? | Emitted from | Nature of the trigger |
|---|---|---|---|
| Linux (WebKitGTK) | **Yes** | tao `connect_focus_in_event` (`tao-0.37.1/src/platform_impl/linux/event_loop.rs:641`), through the `#[cfg(not(windows))]` early return (`tauri-runtime-wry/src/lib.rs:522-524`) | GtkWindow focus-in = window **activation**, not a widget focus change |
| macOS (WKWebView) | **Yes** | tao `window_did_become_key` → `WindowEvent::Focused(true)` (`tao-0.37.1/src/platform_impl/macos/window_delegate.rs:379`), same early return | `windowDidBecomeKey:` — the window becoming key |
| Windows (WebView2) | **No**, for our shape | Suppressed at `tauri-runtime-wry/src/lib.rs:563-565` (`Self(None)`, inside `#[cfg(windows)]`): not multi-webview and `webviews` non-empty | Windows routes webview focus through `add_GotFocus`/`add_LostFocus` instead (`:5333-5336`, called `:5226`) |

Read off the matrix: the focus-in arm runs on Linux and macOS, never on Windows; where it runs it fires on window activation, so it cannot steal a sibling widget's focus. Do not re-derive it — it cost a review cycle to establish once.

## Considered Options

- **Gate the focus-in arm to `cfg(target_os = "linux")` (rejected).** The edit 0056's matrix recommends, on a false premise: the arm is load-bearing on macOS too, where `windowDidBecomeKey:` is exactly the minimise/restore and ⌘-tab path that re-maps the window with nothing re-asserting the widget. It would also be a gate whose comment contradicts the code above it.
- **Edit 0056 in place (rejected).** It is pushed; filling `superseded-by:` and opening this record is the format's mechanism. Its body is history, including the refutation it got right.
- **`Ready` only (rejected).** 0056's rejection, unchanged by the matrix: minimise/restore and a Wayland re-map map the window without re-establishing a focus widget, those paths are not enumerable, and each would return as a fresh "the keyboard stopped working". The symptom was reported on Linux, but the arm that covers them exists on macOS too.
- **Wait for the measurement before shipping the call (rejected).** The symptom is reproduced, the call costs nothing where focus already works, and the seam narrates every outcome — so the shipped code is also the instrument. An unfixed keyboard plus a pending experiment is worse for a one-line lever.

## Consequences

- **The fix ships as a candidate: the causal mechanism is unmeasured, and that is the honest state of this decision.** What is established is 0056's own weaker finding — the widget *is* given key focus at creation (`WebviewAttributes::from(&WindowConfig)` never sets `visible`, wry defaults it `true`, so `show_all()` and `grab_focus()` both run on a realized widget), nothing re-asserts it after tao's `hide()` and the plugin's reveal, and the symptom is real. The measurement is **deferred** to `src-tauri/tests/webview_key_focus.rs` (`cargo test --test webview_key_focus -- --ignored --nocapture`), which needs a human at a keyboard. **What refutes this decision:** that run showing `focus: webview key focus grabbed` at fresh launch with the keys still dead — the lever fired and changed nothing — supersedes 0057 with the actual cause; no `focus:` line at all means the arm never ran and the call belongs wherever the reveal really happens. Do not "tweak and retry" a call known to have been made.
- **The seam logs success as well as failure so that deferred run is self-reading.** `webview_focus_trace` narrates all three arms, including `focus: webview key focus grabbed`, so an absent `focus:` line means exactly one thing — the arm never ran — instead of being ambiguous between "never attempted" and "attempted and worked", which demand opposite responses.
- **macOS carries the risk, not Linux.** `Webview::focus()` unwraps `self.webview.window()` before `makeFirstResponder` (`wry-0.57.0/src/wkwebview/mod.rs:1057-1064`), so a webview ever detached from its window is a panic in the event-loop callback. Accepted — tauri's own macOS build attaches the webview to the window, and the app already fails hard rather than degrading — but the arm's comment names the unwrap, because 0056's "only one widget" reasoning would have hidden it.
- **Windows runs `Ready` alone, with the weaker lever.** `Focused(true)` never arrives for our shape, and WebView2's `focus()` is `MoveFocus(PROGRAMMATIC)` (`wry-0.57.0/src/webview2/mod.rs:1583-1590`) — focus *within* an already-focused CoreWebView2, never Win32 `SetFocus`. A Windows keyboard report is therefore not evidence against this decision's Linux/macOS path.
- **The `RunEvent` shape traps are the price of the second arm, and they cost real time.** There is no `RunEvent::Focused` variant: focus arrives as `RunEvent::WindowEvent { event: WindowEvent::Focused(true), .. }` (`tauri-2.12.2/src/app.rs:127`, `:234-240`). `RunEvent` (`app.rs:219`) and that variant (`:234`) are both `#[non_exhaustive]`, so `..` is mandatory cross-crate (E0638). The callback owns the `RunEvent` and `label: String` is not `Copy`, so a by-value `if let RunEvent::WindowEvent { label, .. } = event` partially moves it and reddens the existing `RunEvent::Exit` arm with **E0382** — match on `&event`. And `clippy::collapsible_match` rejects the nested-`if` spelling under CI's `-D warnings`, so the label filter is a match **guard**.
- **No mock app in the unit tests, deliberately.** A second `generate_context!()` in the lib unit-test binary duplicates `embed_plist`'s `#[no_mangle] static _EMBED_INFO_PLIST`, already emitted once by `lib.rs` — a **link** error, so `cargo clippy`/`check` (metadata-only) stay green while macOS `cargo test` reddens; `MockRuntime::run` (`tauri-2.12.2/src/test/mock_runtime.rs:1353-1390`) also blocks until a `CloseWindow`. Same hazard class as `docs/research/tauri-mock-runtime-test-crashes.md` and the reason `src-tauri/tests/ipc.rs:54` carries `#![cfg(target_os = "linux")]`. Coverage is this repo's own precedent instead — the pure reduction `focus_probe_trace` (`src-tauri/src/lib.rs:209`), unit-tested with no `App`, mirrored by `webview_focus_trace` beside it — plus the `#[ignore]`d human-read check. Expect **no green test pointing at the behaviour itself**.
- **Supersession is by scope, not erasure.** 0056's refutation of the "unmapped widget" mechanism, its rejections of native menu accelerators and a frontend DOM-focus workaround, and its warning that `WebviewWindow::set_focus` is the wrong window-level sibling all stand and are inherited here. What dies is the Linux-only matrix and the safety argument built on it.

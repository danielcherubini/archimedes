# The **Agents** modal's effective model / thinking / tools are resolved in Rust by the SAME function a real dispatch runs, not derived in the renderer — because the Skills dialog's prop-driven pattern would put a second implementation of the resolution chain between the user and what their next dispatch will actually run

The **Agents** modal shows, per **Agent definition**, the *effective* `model` / `thinking` / `tools` and **which layer supplied each** (`override` / `file` / `parent`). The obvious way to build it is the **Skills** dialog's way: `SkillsDialog` is prop-driven and derives everything in TypeScript from `useSkillCatalog(activeSpacePath)`. We decided: **not here.** A new Supervisor-side command `list_agent_config` returns rows whose `effective` and `source` fields are produced by the same resolution function `resolve_launch` calls, so the modal is structurally unable to display a config the next `subagent` dispatch will not run.

**Why:** the chain is `explicit param > override > frontmatter > parent defaults`, and it is not a lookup — it is filtering (unknown tool names dropped, `subagent` / `list_agents` stripped, ADR 0067's empty-is-absent rule) plus soft degradation (a model key missing from the catalog is skipped, so the value the user pinned is NOT the value that runs). A TypeScript copy would have to reproduce all of that to be honest, and this repo's own precedent for a Rust↔TS twin (`skills::is_mentionable_name` ↔ `isMentionableSkillName`) is that a twin needs a pinning test plus a documented reason for existing. Here the reason is absent and the failure is silent: the modal would say `llama-3 · override` while the dispatch ran something else.

## Considered Options

- **Derive effective + source in TypeScript from the existing commands (rejected).** No new command, and it matches the Skills dialog. Rejected because the renderer would have to reproduce the catalog's resolvability rules AND the tool-filter rules to stay honest — including ADR 0067's empty-is-absent rule — and a copy that drifts reports a config the dispatch will not run.
- **Reuse `list_agent_definitions_for_space` and widen its DTO (rejected).** It is already the Space-scoped agent command, but its DTO deliberately excludes `path` / `system_prompt` / `tools` / `thinking` and filters unmentionable names — both pinned by tests in `commands/agents.rs`, on the grounds that an oddly-named definition is still dispatchable by the model passing `agentName` verbatim. The modal needs `tools` + `thinking` + `path` and must list unmentionable names, so widening it would unpin two documented contracts to serve a different surface.
- **Show only the stored override, never the resolved value (rejected).** Cheapest and unambiguous, but it cannot answer the question the modal exists for — "why is scout running that model" — because with both an override and a frontmatter value, "Inherits" names no layer.

## Consequences

- **One resolver, two callers.** `resolve_launch` and `list_agent_config` share the resolution function; a new layer added to one is invisible to the other only if that sharing is broken, which is what the test must pin (a table-driven test asserting the modal's `effective`/`source` for each layer position, and a `resolve_launch` test asserting the same inputs produce the same output).
- **The command calls the resolver with an EMPTY `LaunchConfig`, so `source` names at most three layers.** `resolve_launch(&launch, agent_name, …)` takes the explicit params as its first argument, so the command passes `LaunchConfig::default()` (every field `None`) and the explicit layer contributes nothing — which is the honest answer, because `agentName` and the explicit params exist only inside a live `subagent` call and no modal can know them. A row's `source: "parent"` therefore means "nothing below the explicit param speaks", not "the child will certainly inherit" — a dispatch that passes `model:` overrides what the row shows. The label is worded for that.
- **The label space is `override` / `file` / `parent`, and nothing else needs a word.** The earlier draft of this decision also carried a rule forbidding the phrase *Space default* in any label. That rule is **gone, and named here rather than dropped quietly**: it existed to stop a renderer from naming a layer the resolver had not consulted, and with no per-Space layer in the chain the phrase cannot occur — there is no state a label could get wrong. A rule nobody can break is not a rule; it is noise that teaches a reader to skim the ADR. If ADR 0066's named door is ever opened and a Space layer returns, the labelling question returns with it and belongs in the ADR that adds that layer.
- **`resolve_launch` runs in the Worker, not the Supervisor** (`agent/harness/dispatch.rs:278`, over `parent.space_cwd` + `parent.config_dir`), so the ADR 0066 store choice is what makes this cheap: the Worker already reads `settings.json` there and needs no new envelope field. The new command is Supervisor-side and reads the same file — two readers, one file, no cache to invalidate on either side.
- **The shadowing report IS part of this decision's surface.** ADR 0065 landed on `main` with PR #65: `AgentDefinition` carries `pub shadowed: Vec<crate::skills::Shadowed<AgentScope>>` (`src-tauri/src/agents.rs:70`), and `SkillsDialog.tsx` already renders the Skill half of the report as a block of plain text under its rows. An earlier draft of this ADR said the opposite — that the field and `Shadowed<T>` lived only on the then-unmerged `feature/skill-shadowing-disclosure`, and warned "do not plan against a symbol that is absent here". That sentence is now false, and the correction is recorded rather than deleted, because the *reasoning* behind it is the durable half: a report belongs on the surface that can actually see the collision. What changed is only the fact of where the symbol lives. `agents.rs`'s own doc-comment on the field said at drafting that the report is "computed, never rendered — and never crosses the wire", naming Settings → Subagents as the surface that structurally cannot see a Space-shadows-user collision; that comment went stale the moment `list_agent_config` carried the field, and this branch updated it.
- **The command is Supervisor-side, not Worker-side.** It needs `config_dir` (for the overrides) and `effective_catalog` (to know which pinned models are still resolvable), both of which live on `SessionManager`. It reads no DB, so ADR 0066's storage choice stays invisible across the wire.
- **The report renders on the winning row, never as a row of its own** — the reason the Skills dialog gives, which is now the reason here too: a row's click would name a definition that resolves to the winner's file, because NAME, not path, is a definition's identity (ADR 0065). The modal is the surface that earns this: `list_agent_config` runs discovery with the active Space's `cwd`, so unlike the app-global Settings page it can see a Space definition shadowing a user one.

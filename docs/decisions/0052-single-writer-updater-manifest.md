# Compose the updater manifest in one trailing `publish` job instead of letting each platform's build job write `latest.json`

A tag builds on several OS runners, and every one of them wants to write the same `latest.json` release asset that the updater endpoint polls. `tauri-action` does **merge** rather than overwrite — it downloads the existing manifest and splices in its own platform keys, and has since 2023 (`upload-version-json.ts`, `c5c0e27`) — but that merge is an unguarded read-modify-write with no locking: N parallel jobs seed from the same state and the last writer publishes its own merge, silently losing every platform that finished in between (upstream #409 "latest.json contains data for only one platform", #1270 asset-delete 404). So "just use the action's flag" leaves a race whose failure mode is invisible on the day it ships and appears only when a user on the losing platform cannot update. We decided to set `uploadUpdaterJson: false` on every build job and compose the ONE manifest in a trailing `publish` job that reads the `.sig` assets off the draft release with `gh`, writes the JSON with `jq --rawfile`, validates it, uploads it `--clobber`, and only then runs `gh release edit --draft=false` — one writer, so the race is structurally gone rather than retried away.

## Considered Options

- **`uploadUpdaterJson: true` on all build jobs (rejected).** Upstream's own fix for the conflict is a `Math.random()` retry delay, and it exists only on the `@v1` line (`98b1609`); the `@v0` line we were on retries with zero delay and does not wrap the manifest upload at all. Mitigation is not serialisation, and the residual failure — a manifest describing one platform — is silent from CI's point of view.
- **Build jobs upload workflow artifacts only; one publish job owns installers *and* manifest (rejected).** Fully deterministic and never uses the draft release as the hand-off medium, but it re-implements the asset upload `tauri-action` already does correctly (asset naming, `.sig` collection, retry). We keep `uploadWorkflowArtifacts: true` as a debug escape hatch only.
- **Serialise the build jobs with `needs:` so each merge sees the previous one (rejected).** Correct, but it trades away the parallelism that makes a three-OS release tolerable, and adding macOS later lengthens the chain again.

## Consequences

- **Publish order is load-bearing, not cosmetic.** `GET /releases/latest/download/latest.json` serves only a **published, non-prerelease** release (GitHub's own REST description; 404 otherwise), so a draft release can never satisfy the endpoint our `tauri.conf.json` names. Publishing before the manifest exists opens a window where the new version is visible to clients with no manifest, or with the previous version's. The `publish` job therefore composes → validates → uploads → publishes, in that order, and any failure before the last step leaves the release a draft.
- **The manifest job duplicates the updater's target-resolution rule**, so that rule is now ours to keep correct. `Updater::get_urls` tries `{os}-{arch}-{installer}` BEFORE `{os}-{arch}` (`updater.rs:700-733`), and the Linux payload bundler only ever signs the AppImage — so a manifest carrying only the bare `linux-x86_64` key serves a `.deb` install the AppImage, which downloads in full, verifies its signature, and only then fails `install_deb`'s `infer::archive::is_deb` check with `invalid updater binary format`. Hence the per-installer keys (`linux-x86_64-appimage`, `linux-x86_64-deb`, `windows-x86_64-nsis`) alongside the bare ones, and hence `jq --rawfile` rather than a heredoc: a `.sig` is base64 *with embedded newlines*, and an empty `signature` string parses perfectly and fails only client-side at minisign.
- **Asset names are discovered by pattern, never hardcoded.** The names carry `productName`, version, arch spellings that differ per bundler (`x64` for nsis, `amd64` for deb/AppImage) and an updater payload suffix (`…AppImage.tar.gz`, `…-setup.nsis.zip`) chosen so the payload's bytes match what the installer on the other end sniffs. A hardcoded name is a silent "platform missing from manifest" waiting for the first `productName` or version change.
- **`tauri-action` moves to `@v1`** in the same change, because the `{os}-{arch}-{installer}` keys and `uploadWorkflowArtifacts` do not exist on `@v0`. Its input names differ (`uploadUpdaterJson`, not `includeUpdaterJson`).
- **A second writer to `latest.json` would reintroduce the bug.** The `uploadUpdaterJson: false` line looks like a mistake to a reader who knows the action has that feature; that is why it carries a pointer here rather than only a comment.

## Amendment (2026-10-18) — the payload-shape premise was wrong; the single-writer decision stands unchanged

**AMENDED 2026-10-18 — one factual premise about which files are the updater payloads, and nothing else.** The second and third Consequences above describe the payload as a *second, packaged artifact* the bundler writes beside the installer — `…_amd64.AppImage.tar.gz`, `…_x64-setup.nsis.zip` — and warn that naming the installer instead yields a payload the client rejects after download. **That is false on Windows and Linux, and it has been false since this ADR was written.** Verified against the crates this release actually resolves (`tauri-bundler` @ `@tauri-apps/cli-v2.12.2`, `tauri-plugin-updater` 2.14.0):

- The bundler reaches `updater_bundle::bundle_project` (the only archive-writing path) **only** when the macOS `.app` target is in the list or `createUpdaterArtifacts` is the deprecated `"v1Compatible"`; its own comment calls the v2 targets the ones it "installs directly, no wrapping needed" (`bundle.rs:221-265`).
- The CLI signs the raw installers on purpose — `PackageType::Nsis | WindowsMsi | AppImage | Deb | Rpm` alongside `Updater` (`tauri-cli/src/bundle.rs:249-258`).
- The plugin decides format by **sniffing the downloaded bytes** (`infer`), never by the URL's extension: `extract_exe` accepts a raw `.exe`/`.msi` (`updater.rs:1162`), `install_appimage` writes raw ELF bytes straight over `$APPIMAGE` (its `is_elf` gate `:1235`, the write `:1303`), `install_deb`/`install_rpm` want the raw package (`:1329`, `:1339`).

So a correct Linux+Windows release has **four `.sig` files serving six `platforms` keys** — `windows-x86_64` and `-nsis` share the one `.exe`, `linux-x86_64` and `-appimage` share the one `.AppImage` — which is what v0.1.0 through v0.3.1 have all shipped and what the updater demonstrably installs from. **macOS is the sole exception**, and the reason the packaging sentence was written at all: `install_inner` opens a `GzDecoder` unconditionally (`:1515-1517`), so only `Archimedes.app.tar.gz` works there, and that is the one artifact the bundler always archives.

**Why this mattered, and why the amendment is not cosmetic.** The reasoning during the v0.3.1 release read "four sigs, six keys" through the un-amended text above and concluded two signatures were missing — which AGENTS.md's rule says is a STOP, so a correct release came within one step of being withheld on a phantom defect. The rule "the `.sig` set must be COMPLETE" is unchanged and still load-bearing; what is corrected is what *complete* means. It is **one signature per targeted platform**, not one per filename — verify by counting the distinct `platforms[].url` basenames and requiring a `.sig` for each. A genuinely incomplete set is a *target with no signature at all* (a `deb` built, its `.deb.sig` never uploaded), and `compose-updater-manifest.sh` composes a shrunken manifest and **exits 0** doing it, which is exactly the silent failure this ADR was written to prevent.

Everything else above stands: one writer for `latest.json`, the publish-order gate, the per-installer keys and the `get_urls` resolution rule that motivates them, `jq --rawfile` for the newline-bearing `.sig`, pattern-not-hardcoded asset names, and `tauri-action` on `@v1`. **This ADR is NOT superseded** — the decision is untouched; only the description of the upstream file layout it reasons about was wrong.

## Amendment (2026-10-23) — completeness is now asked of the release, not of the manifest this ADR's writer produced

**AMENDED 2026-10-23 — the verification procedure the 2026-10-18 amendment left behind, and nothing else.** What stands unchanged: `latest.json` has exactly one writer, the trailing `publish` job; the publish-order gate (assets → manifest → draft flag) is load-bearing; the per-installer keys and the `get_urls` `{os}-{arch}-{installer}`-before-`{os}-{arch}` rule that motivates them; `jq --rawfile` for the newline-bearing `.sig`; asset names matched by pattern and never hardcoded; `tauri-action` on `@v1`; and the 2026-10-18 amendment's central fact — **four signatures legitimately serve six `platforms` keys**, because on Windows and Linux the installer itself is the updater payload. **This ADR is NOT superseded** and its `status` is unchanged. The 2026-10-18 text is deliberately left standing above as written and corrected here, per the convention ADR 0016 states: an amendment records what was believed when the decision was taken rather than silently rewriting it.

**What was still wrong.** The 2026-10-18 amendment corrected *what complete means* (four sigs, not six) and then prescribed how to check it: "verify by counting the distinct `platforms[].url` basenames and requiring a `.sig` for each". That procedure **cannot fail**, and the reason is structural rather than a matter of care. This ADR's writer derives its platform keys FROM the `.sig` files it was handed — the `*.sig` glob is its sole source of targets, and the `-deb` / `-rpm` keys are each emitted inside `if [[ -n "$<format>_sig" ]]`. So a signature that was never uploaded removes the target from the manifest **and** from the set of basenames being compared, in the same motion. The check's left side is a projection of its right side; it passes exactly when it should fail. Measured on the tree: a fixture holding a signed AppImage and deb plus an **unsigned** `…_amd64.rpm` and `…_x64-setup.exe` made the composer print `3 platform key(s)` and exit **0**. Two installed forms were frozen on the previous version forever, and the documented check — the one AGENTS.md step 4 told the releaser to run — was satisfied. The hole also existed one level up, in `release.yml`, which asserted only that *at least one* `.sig` had been downloaded.

**What completeness is now.** `scripts/check-release-signatures.sh --repo <owner>/<repo> --tag vX.Y.Z` asks the question of the **release asset list** (`gh release view --json assets`), which is the ground truth and the only input that can answer it: for every asset `X`, `X.sig` must be present too — **per asset, never by counting**. Two properties the naive version gets wrong are load-bearing:

- An explicit **allow-list of non-payloads** — every `*.sig` (it *is* a signature; treating it as an installer would demand `X.sig.sig`), every `.dmg` (never an updater payload, never signed), and `latest.json` (the manifest). Without it the gate fails on every real release. It is a **skip filter and never a required set**: the gate runs while the release is still a draft and before the manifest is uploaded, so `latest.json` does not exist yet on a normal run and no `.dmg` exists at all until macOS packaging is enabled. Anything not on the list — a future bundler that does not sign, an added checksum asset — fails loud and has to be added deliberately.
- The gate **never reads the manifest**, so no code path can compare a file count to a key count. That is the direct falsification of the "four sigs, six keys ⇒ two sigs missing" phantom that nearly withheld v0.3.1, and it is why the ratio corrected in 2026-10-18 no longer needs a human to hold it in their head while counting files.

An explicit refusal when the release carries **no installer assets at all** closes the same vacuity in the new direction: "every installer is signed" is otherwise satisfied by having nothing to check, which is the class of bug this amendment exists to fix.

`compose-updater-manifest.sh --require-payload <name>` closes the hole on the manual path — AGENTS.md step 4's re-compose after a notes rewrite, which never runs the release-side gate. It asserts that `<name>.sig` is in `--sigs-dir` (a claim about a NAME, not about bytes: the pipeline's `--sigs-dir` holds signatures only, so requiring the installer file itself could never be satisfied). `release.yml` feeds it the gate's stdout, so the two gates share one allow-list, and they remain complementary rather than duplicated: the gate reads the release's asset list, the composer reads the downloaded signatures, and a download that came back short is caught only by the second. Both gates report **every** offender in one run, and both refuse to leave a manifest on disk.

Everything else stands: one writer for `latest.json`, the publish-order gate, the per-installer keys, `jq --rawfile`, pattern-not-hardcoded asset names, and `tauri-action` on `@v1`. **This ADR is NOT superseded** — the single-writer decision is untouched, and the 2026-10-18 payload-shape correction it made is still correct; what changed is that the *check* both of them relied on was unfalsifiable, and is now asked of the release.

## Amendment (2026-10-24) — the sentence "both refuse to leave a manifest on disk" was false the day it was written; `774039d` made it true

**AMENDED 2026-10-24 — one sentence of the 2026-10-23 amendment, and nothing else.** What stands unchanged: `latest.json` has exactly one writer, the trailing `publish` job; the publish-order gate is load-bearing; completeness is asked of the **release asset list** and never of the manifest; `--require-payload` is the composer-side half of that check; four signatures legitimately serve six `platforms` keys. **This ADR is NOT superseded** and its `status` is unchanged; the sentence is deliberately left standing above as written and corrected here, per the convention ADR 0016 states.

**The sentence.** "Both gates report **every** offender in one run, and both refuse to leave a manifest on disk." The first half was true. The second was **false on the composer's side since the flag was introduced**: `--require-payload` refused with a bare `exit 1` that bypassed `fail()`, so on AGENTS.md step 4's documented download-then-compose path — where `--out` holds the `latest.json` the operator downloaded moments ago — the refusal left the PREVIOUS release's manifest in place. That is not a neutral outcome; it is the second half of the bad window this ADR's publish-order rule exists to close ("the new version is visible to clients … **or with the previous version's**"), and with the file still there the next `gh release upload --clobber` of an ignored exit code publishes a stale manifest and silently drops the notes rewrite that was the point of the run.

**What `774039d` changed.** Every exit-1 refusal in the composer now goes through `fail()`, so a refused composition leaves **no** manifest at `--out`, and the sentence is finally true of both gates. The consequence for the operator is procedural and is stated in AGENTS.md step 4: after a refusal the download is gone, so a retry re-downloads `latest.json` before re-composing. The one deliberate exception is a **missing `scripts/updater-payload-shapes.sh`**, which exits 1 without touching `--out` — a broken checkout is not a refused composition, and a tool that never read its arguments has formed no opinion about this release and must not destroy the operator's file. **Narrowed again the same day, one sentence:** "leaves **no** manifest at `--out`" was still false for one invocation shape, because `fail()` deleted only what the parse loop had reached — so a typo typed BEFORE `--out` (`… --verison 0.2.0 --out latest.json`) refused with a clean exit 1 and left the previous release's manifest in place, measured on this tree. The target is now the `--out` found in the invocation's own arguments, so the promise holds whatever the flag order; what remains outside it is exactly what never reaches `fail()` and therefore reports no refusal — the missing shape library above, a legacy value-less flag at the very end of the line (`… --out latest.json --notes`, which dies as a shell fault), and an `--out` path the OS refuses at `mkdir -p` or the write. The harness case that pins the fix types `--out` LAST behind a typo, and the seeded-cleanup assertions it feeds are 17 where the paragraph below counted 14.

**Why nobody noticed, and what now goes red.** Ten of the composer harness's "no manifest survives" assertions had **no red state at all**: `run_compose` writes into a fresh directory, so the assertion was satisfied by an empty room and deleting `fail()`'s `rm -f` left every one of them green. They now seed a valid previous-release manifest at `--out` and assert its fate, which is what the sentence needed to be falsifiable — removing the cleanup reddens 14 assertions where it once reddened 1. The single-writer decision is untouched; what was fixed is that the refusal which was supposed to enforce it was the one refusal that did not clean up.

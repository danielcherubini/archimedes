# A definition's `permission:` block is consulted at the TAIL of row 4 and can only NARROW — so it governs children only, sits below the user's rule list, and may empty an advertised tool list without ever making it ABSENT

An Agent definition's `permission:` frontmatter (issue #101, opencode's per-tool `allow` / `ask` / `deny` block) was read by nothing: `parse_agent_file` visited top-level keys only, so the block was a confident no-op. We decided, and shipped, that it becomes a **third governing layer** beside the two `docs/features/permissions-model.md` already documents — and that it enters the decision at exactly **one** place: the tail of precedence **row 4**, as the stricter of two against the posture verdict. It is **narrowing-only** (`Allow < Confine < Ask < Deny`, strictest wins), it **governs a child subagent only**, and it has **no `settings.json` rung and no fourth `OverrideSource` variant**. A whole-tool `deny` additionally drops the tool from the child's advertised set, and a list that the drop empties stays **`Some(vec![])` — zero tools — and never falls back to `None`**.

**Why a third layer needs its own ADR rather than a paragraph in the feature page:** this decision **narrows ADR 0067**, and the house convention for a narrowing is a `*Partial:*` note appended to the narrowed ADR, which needs a host document to carry the reasoning 0067's note points at. 0067 decided that an emptied tool list means ABSENT and that "**zero tools is reachable only from the explicit `subagent` tool param**". A deliberate `deny` empties a list too, and ABSENT is the *wider* value there — so 0067's sentence is no longer true unscoped, and the boundary between "emptied by accident, therefore silent" and "emptied on purpose, therefore nothing" is a ruling, not an implementation detail. It is recorded here and 0067 carries the note.

## The decision

**One consultation point, at the tail of row 4.** `gate::policy_verdict` runs rows 1–3 for a write through `rule_or_guard_verdict` and **returns early** on any of them — a user rule `deny`, a user rule `allow`, or the self-modification guard's `Ask` (ADR 0083). Only when all three stay silent does it reach `stricter_of_two(decision_for(…), self.definition_verdict(&tc.name))`. A definition's verdict therefore **cannot see** rows 1–3 and cannot bypass them: it cannot un-block a user `deny`, cannot silence the guard, and can tighten a Trust-widened `Allow` back into an `Ask`. That is ADR 0030's *"Trust suppresses prompts but never widens a deny"* applied to definitions — the layer that widens is the user's own choice, never the file.

**Children only, stated plainly.** `resolve_agent_launch` has exactly two production callers — the Agents modal's read-only report (`commands/agents.rs`) and `resolve_launch` behind the `subagent` tool call (`harness/dispatch.rs`) — and a main session's `StartEnv` is built in `agent/session/mod.rs` with `permission: None`, whose comment says why: **a main-session path passes no `AgentDefinition` at all**. So a definition's block governs a **Subagent session** and nothing else. The feature page says this in its own words because a reader of a permissions page otherwise assumes a policy applies to them everywhere.

**Narrowing-only, structurally and at the merge.** No shape in `definition_permission.rs` can express a grant: the actions are exactly `allow | ask | deny`, and a bare verdict is the only whole-tool spelling (`Rules::whole_tool`). At the merge, `DefinitionVerdict::AsSelf` (the file does not speak about this tool) and `Allow` are **both identities** — an `Allow` beats nothing and returns the posture verdict unchanged. A separate verdict type rather than a `Decision` is deliberate: `Decision::Allow` means "run it", which is not what a silent file means, and collapsing the two would let "no opinion" be mistaken for a grant.

**`Confine` is not a midpoint of a `min` over the three per-agent actions.** It ranks **above `Allow`** and **below `Ask`**, and the two arms of `stricter_of_two` spell that out rather than ranking over `{Allow, Ask, Deny}`. The reason is that `Confine` is not a *permission level* — it is a **running sandbox**, the Landlock `bash` the user asked for by choosing `shell: Sandboxed`. A per-agent `Allow` cannot un-confine a command that is already confined, because un-confining is a grant of OS reach, which this layer may never make; and a per-agent `Ask` still tightens a confined run into a prompt, because asking is strictly more restrictive than running quietly inside a sandbox. A merge written as a rank over the three per-agent verbs mis-orders `bash` in one of two directions: either `allow` releases the sandbox (the exact widening the layer forbids) or `ask` fails to tighten a confined shell. Pinned as its own pair of tests — `a_definition_cannot_unconfine_a_sandboxed_shell` and `a_definition_ask_tightens_a_confined_shell` — because it is the failure a reviewer cannot see by reading a `min`.

**The boundary that is NOT narrowing-only, recorded as a boundary.** A user `allow` **rule** (row 2) outranks a definition `deny`, because row 2 returns before the consult. This is the deliberate consequence of row-4-only consultation, not a hole to close: the definition layer sits **below the user's rule list and above the posture**, so the user's own explicit rule is the wider authority. Asserted by `the_row_precedence_cells_are_untouched_by_the_definition_layer`, which pins all four cells in one test — including the direction that a definition `deny` cannot rewrite the guard's `Ask` into a silent refusal either (row 3 returns early, so the user still approves that write by hand).

**Enforced scope is whole-tool `Action` denies, and only at the gate.** `definition_verdict` produces a verdict only from `Rules::catch_all_action()` — a bare `bash: deny`. A per-pattern ruleset is `AsSelf` by design: enforcing those rows needs a command/path matcher nothing has validated, and adding a second resolver at this seam is the #92 / ADR 0081 escape class, so there is none. `definition_verdict` does **no path resolution at all**, deliberately — the boundary question stays the one shared `FsBackend::validate` / `canonicalize_lenient` check. And the layer is **gate-only**: `ToolCtx` carries `file_policy`, `rules`, `protected` and `home`, and no permission block, so unlike the user-rule rows (whose gate and executor twins consult the same `rule_for`) a definition can only ever refuse **before** dispatch, never at the executor.

**The advertisement drop, and the emptied list.** A whole-tool `deny` removes that name from the resolved `launch.tools` before the wire, so the model is not offered a call the gate would refuse. A list the drop empties stays `Some(vec![])`. `None` is not "no tools": `subagent_flow`'s three-way rule reads it as *"the parent's list minus the guard"*, and the `[]`-means-ALL expansion lives in that `None` arm reading a different input (`parent_enabled_tools`). `Some(vec![])` is what every downstream actually means by zero tools — `subagent_flow` ("a non-empty set that empties out yields NO tools — NOT re-expanded"), `worker/core.rs` ("a legitimately-empty child tool set must NOT re-expand into all tools — the recursion guard"), `advertised_tool_specs` (`Some(v)` = exactly `v`), `is_tool_enabled` (`Some([])` enables nothing).

## The defect this decision had to avoid, and how close it came

The drop originally reused ADR 0067's emptied-means-ABSENT rule, cited from `narrow` a few lines above. That citation was **wrong in that position**: 0067 exists to stop a *typo or a stale name* in an allowlist from accidentally zeroing a child — unintended narrowing — and a deliberate `deny` is the opposite case, so its rationale does not travel. Falling back to ABSENT there made `tools: [bash]` + `bash: deny` hand the child the **parent's full set**: the file that denied the most gave the child the **most** tools, the exact inverse of #101's invariant ("a definition can make its own agent stricter … it can never grant past it") and a direct failure of its own acceptance item ("drop the tool from the child's `enabled_tools` … so the model is never offered a call it can't make"). It is strictly worse than the case 0067 guards against, because there the accident required a typo and here it required the most restrictive file a user could write.

**Corrected before anything was committed, and the record says so precisely.** `git log --all -S '(!names.is_empty()).then_some(names)'` over this repo returns **nothing on any ref**: the buggy form and the test that asserted it (`a_deny_that_empties_the_advertised_list_falls_back_to_absent`) survived only in a **dangling stash-commit** — local to one machine, reachable from no ref, and therefore doomed to `git gc`'s default two-week prune. **That object is gone by the time you read this; the quotation below is the evidence, not the hash.** Its drop site read, verbatim:

> ```rust
> // Same ADR 0067-emptied-means-ABSENT rule as `narrow`: a list that
> // empties out is ABSENT, NOT "zero tools" (only the explicit list is
> // allowed to zero a child, and this drop never *adds* a name, so the
> // emptied-means-ABSENT rule only ever applies to the
> // override/frontmatter rung it narrowed).
> (!names.is_empty()).then_some(names)
> ```

and its test asserted the inversion **as the expectation**, message included:

> ```rust
> assert_eq!(r.launch.tools, None,
>     "an emptied list is ABSENT, not zero tools (ADR 0067) — the gate, not \
>      this filter, is what refuses the call");
> ```

That second block is the whole lesson in four lines: a green test defending the widening. The only commit that ever touched the drop shipped the `map` form and the renamed pin `a_deny_that_empties_the_advertised_list_yields_zero_tools_not_the_parent_set`, whose doc comment records that it used to assert the opposite. **So this is a review-caught defect, not a shipped one** — the run's own status log described it as having shipped green, and the object database says otherwise. The lesson stands either way, and is the reason the pin's doc comment is written as a history note: **a test that asserts the current behaviour of a widening is a pin on the defect, and a green suite will defend it.** What makes this one catchable by reading is that the fallback was justified by a citation to a real ADR, which is the most dangerous kind of wrong comment.

## Considered Options

- **A per-agent `Allow` that OVERRIDES rather than intersects** (rejected — the alternative the upstream spelling invites). opencode's block reads like a grant list, and treating it as one would let a markdown file a repo checked in widen what a stranger's agent may reach on your disk. Rejected because the file is not authored by the person whose disk it is: the user's `filePolicy` is the authority and a definition may only subtract from it. Structurally enforced, not merely avoided — no constructor in the module produces a verdict stronger than "the posture stands".
- **Consulting at row 1** (rejected). Putting the definition's `deny` on the rule list would make it trust-immune and would let it **refuse in place of** the guard's prompt — and the guard's `Ask` is the row that keeps a human in the loop about the agent's own instructions. A definition that could convert that prompt into a silent refusal could be used to hide a prompt the user wanted; and a definition `allow` at row 1 would swallow a user `deny`, which is the widening this whole design forbids. Row 4's tail is the only position where neither is reachable, and it is the position that makes the "never bypasses" claim a property of control flow rather than of a comparison.
- **A `settings.json` `permission` rung** (rejected). The issue's scope is *what a file declares*; a second authoring surface would need its own UI, its own precedence against the file's block, and a fourth `OverrideSource` variant — and the three-variant label space is a compile-time fact (`the_source_label_space_is_exactly_three_layers_and_never_space` matches it exhaustively). The layer is therefore exactly `File` when the file speaks and `Parent` when it does not, reusing the existing variants.
- **Enforcing per-command `bash` patterns** (rejected — and this is the decision the feature page's scope section carries). Command text carries its own redirects, so `grep x file 2>/dev/null` contains a `>` and a naive `*>*` deny blocks the stderr-suppression idiom; no ordering in this rule language expresses "redirect to a file but not to an fd". This desktop has no tree-sitter command parse, and a matcher nothing has validated is enforcement that only *looks* real — ADR 0030's *"a guard-rail, not a security boundary"* applied to a pattern list. A `bash` object with ≥1 pattern row therefore **parses and announces itself unsupported** (`UnsupportedUnvalidatedMatcher(BashPatternRules)`) and is never half-enforced; a bare `bash: deny` needs no matcher and is supported.
- **Leaving the field parsed-but-unenforced** (rejected). Parsing, reporting and displaying a block that refuses nothing is the **confident no-op** class #101 exists to fix, and it is worse than not parsing it, because the modal would show rules that look live. The planner for this work reported its own scope blocker precisely here — the one production line that makes enforcement live (`worker/core.rs` handing `StartEnv.permission` to `AgentLoop::set_permission`) sat outside its owned set — and acting on that report is what split the task in two. The acceptance test `the_definition_permission_deny_refuses_the_child_real_worker` pins BOTH halves (the block rides the wire, AND the child's own gate refuses) because the two ways this feature can be a no-op live in different files.

## Consequences

- **ADR 0067 is narrowed, and carries the note.** Its sentence "zero tools is reachable only from the explicit `subagent` tool param" was true of its own two layers (the override map and the frontmatter list) and is no longer true unscoped: a definition's `deny` can empty a list, on the file rung **and** on the explicit-param rung (`subagent({tools: ["bash"]})` + a file `bash: deny` = nothing left, which is still *narrower* than the parent's set and so respects narrowing-only). 0067's own rule — an emptied **allowlist** is ABSENT — is untouched and still shipped inside `narrow`; only its reach is scoped.
- **The layer is gate-only, and that is a stated limit, not a symmetry.** A user rule refuses at the gate *and* at the executor through the same `rule_for`; a definition refuses only at the gate. Anything that later moves refusal into the executors must decide how a per-agent verdict reaches a `ToolCtx` that does not carry one.
- **`task: deny` and the other un-policed keys are announced and unenforceable.** `web_search`, `read_skill`, `fetch_content` and any `ToolKey::Unrecognized` (opencode's `task`, `glob`, `lsp`) have no `policed_direction` twin, so `policy_verdict` answers `None` for them — not `Allow`, not `Deny`, no panic. Pinned by `a_definition_ask_on_an_unpoliced_tool_stays_as_self`, which pins `None` on purpose.
- **The motivating file still refuses nothing, and both halves of that are measured.** `~/.agents/agents/researcher.md` — the file #101's Evidence section names — has **no `tools:` key** (`grep -c '^tools:' ~/.agents/agents/researcher.md` → **0**), so the advertisement filter has no list to narrow, and its `bash:` block's own catch-all is `"*": allow`, so even a perfect matcher would allow. Worse, its `edit:` block is a **pattern map** (`"*": deny`, `"*.md": allow`) on a *path-taking* tool, and the unsupported announcement fires **only for `ToolKey::Bash`** — measured at the one `notes.push` site — so those rows are neither enforced **nor announced** — corroborated by an existing pin, `a_blank_line_inside_a_nested_pattern_map_is_skipped_too`, which feeds `edit: {"*": deny, "*.md": allow}` through a helper that **asserts the notes are empty** and passes. The gate's answer for that file, on the default posture, is `Allow` for `bash`, `edit` and `write`, and `None` for `task`; pinned by `the_real_researcher_block_is_read_and_its_verdicts_are_the_scoped_ones`. The enforceable class (whole-tool `Action` denies) is live and proven on a real child Worker; the cited file is not an instance of it. The feature page carries this so no reader finishes believing the motivating file is now enforced.
- **Whole-tool denies are live end to end.** `StartEnv.permission` → `worker/core.rs`'s `set_permission` → the child's own `policy_verdict`, and the refusal reuses the existing `deny_tool_result` wording with no per-layer renderer, so the model's recovery cannot depend on which layer said no (ADR 0030). `a_whole_tool_bash_deny_refuses_at_the_gate_when_the_tool_is_still_offered` pins the shape the advertisement filter cannot reach — `tools:` absent, the tool still offered, the gate the only refusal available.
- **The Agents modal reports the block and the notes, and nothing sorts.** `filePermission` carries the declared block verbatim with `source.permission` naming `file`, and `frontmatterNotes` is a required `Vec` following the `shadowed` precedent. A `.sort()` on either list would print a sequence in which a different rule appears to decide than the one that does — opencode resolves a tool's patterns in order, last match wins. Display only: no rule-authoring UI, no control, because an editor for rules authored in a markdown file would promise an edit the surface cannot perform.
- **This repo has no Rust↔TypeScript wire-contract test**, so the TS mirror of the block is a hand-copy whose drift is invisible to both suites. The pinned spellings (externally-tagged notes, lowercase `action`, **snake_case `whole_tool`** inside a camelCase DTO) are restated in `src/lib/tauri/types.ts` above the mirror, with the reason, so a "tidying" rename has somewhere to be wrong against.

## Honesty about what this ADR could not check

- **Nothing was executed here.** This is a docs-only task that ran no `cargo` and no `pnpm` suite (the one doc-scanning test, `src/lib/subagentSheetLayout.test.ts`, is run and reported in `docs/features/permissions-model.md`'s `verified-by` stamp). Every behavioural claim above is **read from source** — the gate arms, the resolver's drop, the worker's application line, and the named tests — not observed.
- **The `edit:`-pattern-map silence is read from the one `notes.push` guard (`tool == ToolKey::Bash`) and corroborated by one passing pin that asserts an empty note list for exactly that shape.** A dedicated test naming the claim — "a path-tool pattern map announces nothing" — would turn that from an inference plus a corroboration into a stated contract; this ADR proposes it as the follow-up rather than claiming the measurement.
- **Whether the defect would have shipped is a counterfactual.** The object database shows the buggy form never reached a ref, which is what licenses "caught in review". It does not show how many rounds of green tests it survived on the way there — the run's own status log believed it had shipped, and a log entry is not a commit.
- **The real-file claims are about `~/.agents/agents/researcher.md` as it sits on one machine**, outside this repo's version control. It can be edited at any time, which is exactly why the pins quote its *shape* rather than reading the file, and why this ADR records the counts as measurements at a date.

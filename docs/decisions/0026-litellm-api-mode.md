# LiteLLM as a fourth `api` value (a discovery mode, not a fourth wire)

LiteLLM-proxy-backed providers (e.g. `llm.wizards.town`) advertise their models, thinking levels, and per-model capabilities at a NON-OpenAI discovery endpoint — `GET {base}/model/info` — which the standard `GET {base}/models` (served by the same proxy) does not carry. We decided: `api: "litellm"` is a FOURTH `api` value whose only new behavior is the **discovery mode** (`GET {base}/model/info`, Bearer auth, LiteLLM shape). The **wire stays `openai-completions`**: `build_provider` builds the existing `OpenAiCompatibleProvider` for it, `ModelCatalog::selectable()` accepts it alongside the three wires, and thinking levels are surfaced **verbatim** from `model_info.reasoning_effort_levels` (e.g. `["none","low","medium","xhigh"]`) with no `off`↔`none` normalization — the level string flows onto the wire as `reasoning_effort` as-is.

**Why:** a LiteLLM proxy always speaks OpenAI-compatible chat-completions for completion (verified live: `reasoning_content` deltas and `tool_calls` stream in the exact shapes the existing `SseStream` parses, and the harness already sends `x-litellm-session-id` / `x-request-id` on completions requests) — so there is no new wire to write. The genuinely different axis is DISCOVERY, and `api` already doubles as the discovery-shape selector (`discover_models` dispatches on it for the Anthropic vs. OpenAI `/models` shapes — ADR 0024), so extending it keeps one field, one dispatch point, and no settings migration.

**Considered Options**

- **A known-provider template only** (no new discovery): rejected — it adds nothing the user can't already do (a `openai-completions` row against the same base URL discovers via `/models`), and `/models` carries no reasoning fields, so thinking levels would be lost.
- **A separate `discovery` field on the provider row** (keeps `api` purely the wire): rejected — it doubles the surface (new persisted field, validation, a second UI select) for a distinction that always travels with the wire in practice; `api`'s meaning becomes "endpoint flavor: wire + discovery", which is what it already is (the `anthropic-messages` value does exactly this).
- **A fourth WIRE** (`OpenAiLiteLLMProvider`): rejected — the completion wire is empirically identical to `openai-completions`; a new struct would duplicate a request body and an SSE parser that already work.
- **Normalizing the level vocabulary** (`none`→`off` in the catalog, `off`→`none` on the wire): rejected — the desktop is already "the endpoint supplies everything" (`thinking_levels` is a free-form vec, the selector displays the provider's own words, per-model remembered levels are keyed by `provider/model`); a bidirectional mapping risks sending a level the proxy rejects and assumes LiteLLM's vocabulary is stable across deployments.

**Consequences**

- **`settings.json` `providers[].api` gains `"litellm"`** (no migration — a new value on an existing `String` field with a serde default).
- **`discover_models` gains a `"litellm"` arm**: `GET {base_url}/model/info`, Bearer auth (empty key → no header), parsing `data[].model_name` / `model_info.{max_input_tokens (+ max_output_tokens fallback), reasoning_effort_levels, supports_reasoning}`; `supports_function_calling`, the cost fields, and `default_reasoning_effort` are deliberately ignored for v1 (the `cost_per_mtok_*` seam stays at the documented 0.0).
- **`build_provider` routes `"litellm"` to the default (OpenAI) arm** — the arm that looks like it "should" build a LiteLLM-specific client; this is intentional (the wire IS OpenAI-compatible).
- **`ModelCatalog::selectable()` accepts `"litellm"`** (fourth value in the match).
- **The Settings' API select gains a "LiteLLM" option** (no known-provider template is added — LiteLLM base URLs differ per deployment, so a pre-filled template has no canonical base URL).
- **`default_reasoning_effort` is NOT parsed (v1)**: the level-resolution chain is untouched, a fresh LiteLLM session starts with no thinking level (the proxy's server-side default applies).
- **A user's existing `openai-completions` row against a LiteLLM proxy keeps working** (discovers via `/models`); switching its `api` to `litellm` (the UI select is editable) upgrades discovery to `/model/info` (thinking levels + capabilities + cost).
- **Amendment 2026-10-05 (god-file decomposition, Task 1): `api` is now a named type internally.** `agent::harness::WireApi` (wire.rs) is the wire vocabulary — a 4-variant enum (`OpenAiCompletions` / `AnthropicMessages` / `OpenAiResponses` / `LiteLLM`) with explicit `#[serde(rename)]` kebab-case strings and `parse` / `as_str` (the parse failures are logged where settings parsing tolerates unknowns). The DISCRIMINANT STRINGS are unchanged — `settings.json` and the Worker IPC `StartEnv` stay byte-identical (permissive storage stays `String` at `Model.api` / `ProviderConfig.api` / `KnownProviderDto.api`; only the dispatch sites — `build_provider`, `discover_models`, `selectable`, `catalog` — convert through `WireApi`). The TS side mirrors it: the `WireApi` union in `src/lib/tauri.ts`. The ADR 0023 level chain intentionally stays `&str` (Degrade vs Strict resolution paths are not unifiable without behavior change).

## Amendment (2026-11-01) — discovery fallbacks + multi-deployment grouping (#130)

**AMENDED 2026-11-01 — the single-shot `/model/info` read is overtaken by #130.** What stands unchanged: `api: "litellm"` is a **discovery mode, not a fourth wire**; the 4-value `WireApi` vocabulary is final; the discriminant strings (`settings.json` + the Worker IPC `StartEnv`) stay byte-identical; `build_provider` still dispatches on `Model.api` untouched; thinking levels stay **verbatim** — the no-`off`↔`none` normalization ruling stands; and **`ProviderDiscovery.succeeded` semantics are untouched** (ADR 0076 rule 3 — any answering rung is a success, an empty rung falls DOWN, only an all-empty chain is `Err`). The Consequences bullet below is deliberately left standing exactly as written, preserving the original design intent; the correction is recorded here.

> - **`discover_models` gains a `"litellm"` arm**: `GET {base_url}/model/info`, Bearer auth (empty key → no header) …

**What changed.** `discover_litellm_models` is no longer one `GET {base}/model/info` shot — it is a **fallback ladder** whose TERMINAL rung decides `Ok`/`Err`: `/model/info` → `/v1/models` (the OpenAI shape, which a **non-admin key** can read) → `/v1/model/info` (LiteLLM serves both paths; a proxy may 403 only the unprefixed one) → `/health` (a liveness GATE, never a model source) plus a `GET {base}/model/info?litellm_model_id={id}` probe per deployment id the earlier rungs mentioned but could not turn into a route. A **2xx-empty rung falls DOWN** — the case the old code cached as an empty success — so the "empty `data: []`" proxy now triggers the fallback instead of ending the read. Bearer auth (empty key → no header) and the provider's custom headers (issue #129) ride every rung on one bounded 5s/10s client, so a proxy that answers rung 1 still costs exactly one request per read.

**The deployment multiplicity survives.** A proxy may serve several deployments under one `model_name`; the old `HashMap<model_name, …>` seam destroyed that set last-wins. Entries now group into a module-internal `LiteLLMDeployment` set per route and fold through a **conservative reduction**: `min` context window (a multi-deployment route never overestimates what it accepts), `min` max-output, `max` cost ("the most this route could cost"), thinking controls only when **ALL** deployments reason (the levels are the **INTERSECTION** over the deployments that advertise any), and tool support only when **ALL** deployments carry `supports_function_calling` (absent → `false`). A route whose entries carry no `model_info` at all keeps the all-`None` entry — the reduction fabricates no claim the proxy never made.

**Wildcard routes expand.** A `/v1/models` id carrying a provider-qualified `provider/model` form (a route group like `anthropic/*`) becomes individually selectable, keeping its qualified form so the picker's `provider/model` keying is unchanged; it carries the OpenAI-shape metadata it advertises and nothing else (the documented v1 degradation).

**The parsed `model_info` census widens** from 11 keys to 17: `mode`, `supports_function_calling`, `litellm_model_id`, `id`, `input_cost_per_token`, `output_cost_per_token`, plus a `#[serde(flatten)]` extras guard so a proxy ADDING a key cannot take a route down. The cost fields are now read — the reduction's `max` cost is their first consumer (per-token × 1e6; absent → `0.0`, the documented degradation).

**`DiscoveredMeta` gains four additive `Option` fields** — `api`, `supports_tools`, `cost_per_mtok_in`, `cost_per_mtok_out` — carrying the derived wire and the reduction's conservative truth. They are Default-compatible and never serialized to disk (the in-memory `ProviderDiscovery` cache is the only holder), so the widening is schema-invisible; every non-LiteLLM discovery arm keeps writing `None` and is byte-identical.

**Deferred to the wave-4 amendment (NOT this amendment's behaviour).** The per-model `WireApi` derivation's CONSUMPTION — the write at `EffectiveCatalog::resolve` that puts a derived `api` on each `Model`, **including the propagation of `supports_tools` / `cost_per_mtok_in` / `cost_per_mtok_out` from `DiscoveredMeta` onto `Model` (`unwrap_or(true)` / `unwrap_or(0.0)`, preserving today's defaults for every non-LiteLLM provider)** — plus base-URL normalization, the vendor request-body quirks, the Anthropic prompt-caching headers, and the live-session wire-pin policy. This amendment records only the ladder, the grouping reduction, the widened census, the wildcard expansion, and the four carried fields. The derived wire exists as a pure, CARRIED value (`derive_wire_for_route`: all-`mode == "responses"` → Responses; all-Claude-adapter route hints with the one-time `/v1/messages` probe latch true → Messages; otherwise Completions, with a `current`-deployment tiebreak when a route disagrees); applying it is the wave-4 half's job.

## Amendment (2026-11-02) — the per-model wire is DERIVED at the resolve seam (#131)

**AMENDED 2026-11-02 — the wave-4 half lands.** What stands unchanged: `api: "litellm"` is a **discovery mode, not a fourth wire**; the 4-value `WireApi` vocabulary is **FINAL** (no new variant, and `parse` / `as_str` / the serde discriminant strings are byte-identical — `settings.json` and the Worker IPC `StartEnv` are untouched); the original "the **wire stays `openai-completions`**" sentence and the `build_provider`-routes-`litellm`-to-the-default-arm consequence stay exactly as written (they are what the completions fallback still does); thinking levels stay **verbatim** (no `off`↔`none` normalization); and `ProviderDiscovery.succeeded` semantics are untouched (ADR 0076 rule 3).

**What changed — `api` is derived, not configured (for `litellm` only).** `EffectiveCatalog::resolve` now writes a per-model wire **derived from the discovery payload** instead of cloning the provider's `api`: the value `derive_wire_for_route` proved (`mode == "responses"` → `openai-responses`; a Claude-adapter route with the one-time `/v1/messages` probe latch true → `anthropic-messages`) is written onto the `Model` row. **The `openai-completions` fallback is deliberately NOT written**: it is wire-equivalent to `litellm` (`build_provider`'s default arm — the sentence above stands) while `litellm` additionally carries the **discovery shape**, and `api` doubles as `discover_models`' selector — overwriting it with `openai-completions` would silently downgrade that provider's later metadata refreshes from `/model/info` to `/models`. The fallback therefore keeps the provider value, i.e. the byte-identical pre-amendment row. **Any non-`litellm` provider is untouched**: the write is `Some(provider.api.clone())` with no derivation attempted and no overwrite possible.

**The same write propagates the reduction (interface §10 R5).** `supports_tools` / `cost_per_mtok_in` / `cost_per_mtok_out` ride the resolve seam from `DiscoveredMeta` onto `Model` with `unwrap_or(true)` / `unwrap_or(0.0)` / `unwrap_or(0.0)` — reproducing the literals the write hardcoded before, so every non-`litellm` provider's `Model` row is byte-identical (its `DiscoveredMeta` carries `None` in all four additive fields; pinned by `resolve_non_litellm_provider_byte_identical`). This closes the previous amendment's deferral.

**Base-URL normalization is a NEW helper, not an overload.** `normalize_wire_base_url(base_url, api)` (`provider/anthropic.rs`) owns the per-wire rule and is documented **idempotent** (`n(n(u)) == n(u)` for every wire); `normalize_anthropic_base_url` is untouched and keeps producing only `/v1`-suffixed paths. `build_provider` / `build_provider_with_headers` apply the **Messages half** (strip a trailing `/v1`) so a LiteLLM Messages row hits `{root}/v1/messages` instead of the double-prefixed `{root}/v1/v1/messages` the client's own adapter-boundary append produced. The **append** half (`{root}/v1` for Completions/Responses) is implemented and unit-tested on the helper but **not applied at the construction sites**: the Settings' convention is a `/v1`-suffixed base and the existing suites (including a root-base mock in `tests/provider_headers.rs`) pin today's verbatim paths, so applying it would move request paths for non-LiteLLM providers — which this amendment's byte-identity rule forbids. Flagged for the orchestrator: either the append half becomes a later, deliberately-scoped change with its own test migrations, or the rule is scoped to LiteLLM rows only.

**The two vendor quirks.** (1) Chat Completions suppresses `reasoning_effort` for the `gpt-5.5` prefix family (`gpt-5.5` / `gpt-5.6` / `gpt-5.7` — a documented one-line prefix list, no pattern match, no other model-name branching) when the request carries tools, because the provider 400s on that pair; the gate lives in `openai.rs`'s single body builder, so the Responses wire (its own `responses_request_body`, passing `reasoning.effort` through) is untouched. A suppressed level means "provider default" for that turn — what the 400 forces anyway. (2) Anthropic **prompt caching** (body-level, no new headers): a `claude-` model gets its `system` as an array of text blocks with `cache_control: {type: "ephemeral"}` on the LAST block, and every tool block carries the same marker; `MAX_SYSTEM_BLOCKS` caps the block count by folding the excess into the last block (nothing dropped). The condition is exactly `is_claude_model && (tools || non-empty system)`; a non-Claude model and the Claude-with-no-tools-and-no-system case keep today's shape byte-identically.

**Live sessions keep their wire (boundary, not an oversight).** The wire is bound to the provider instance at spawn (`build_provider` in `default_build_loop`), `refresh_live_models` copies only the window/thinking fields, and `AgentLoop::set_model` rebuilds only on a composed-key change — so a derived-wire **correction** is not pushed to a running session. A mid-session user model switch (which re-resolves and sends the whole `Model`) and every new session carry the derived wire. Widening the refresh gate to carry a changed `api` is the recorded follow-up.

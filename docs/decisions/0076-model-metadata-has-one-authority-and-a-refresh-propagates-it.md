# Model metadata has ONE authority, a refresh PROPAGATES it, and the discovery cache gates on SUCCESS not on ATTEMPT

A **Model**'s context window and thinking metadata are **discovered facts about the model**, owned by the per-provider discovery cache. Nothing downstream may hold a private copy that outlives the read that produced it. Concretely, three rules:

1. **A provider refresh propagates to every consumer of the old value** — the Settings list, the **Live session**'s `AgentLoop` (via the existing `Config { model }` → `ControlCmd::SetModel` → `set_model` path), the stored session's context bar (derived on read, never replayed from a snapshot), and the Client's catalog store.
2. **A stored session's `context_usage.window` is DERIVED from the model its own `capabilities.model` resolves to**; only `used` is replayed from `sessions.context_usage_json`, because `used` is a measurement of THAT session and `window` is a property of the MODEL.
3. **The discovery cache re-fetches a provider whose last attempt FAILED.** `ProviderDiscovery::attempted` is replaced by `succeeded`: a successful result (including a legitimately EMPTY one) caches for the process's life, a failure caches nothing.

**Why:** issue #85. A LiteLLM user's `deepseek/deepseek-v4.1-flash` has a **1,000,000**-token window — `GET /model/info` reports `model_info.max_input_tokens: 1000000` today, verified against the live endpoint while writing this. The report was that an existing session showed **256k** for that model. *Where the 256k came from is not established here* — a gateway that previously declared a smaller window is the obvious candidate and the mechanism below does not depend on which it was (`DEFAULT_CONTEXT_WINDOW` is 128k, so it is not the fallback absorbing a missing field). What is established, and is the whole defect: pressing **refresh** in Settings fixed the Settings page and every NEW session while leaving every existing one untouched.

That last clause is the whole bug in one sentence: **refresh updated the cache that only new sessions read.** The window is copied into `AgentLoop` at spawn (`Compactor::new(catalog.compaction, model.context_window)`), and the only other writer is `set_model`, reached exclusively from a config-option change. So the corrected number had no route to a running session at all.

And it was not cosmetic. ADR 0028 established **"one number, two consumers"**: the loop's window feeds the context bar AND `should_compact()` (threshold `context_window − reserve_tokens`). A session pinned at 256k against a 1M model **compacts at roughly a quarter of its real capacity** — it discards context the model could still have taken, silently, with no error and no log, because under-reporting a window is the safe-looking direction. The user sees a bar that never fills and a session that summarizes itself for no visible reason.

The same staleness had two more faces, which is why this is one decision and not three fixes:

- **Closed sessions**: every `context_usage_update` frame persists `{used, window}` as a full snapshot, so a corrected provider left every historical session's bar showing the frozen window **permanently** — `list_sessions` resolves the row's model for `config_options` and then ignored it for `context_usage`.
- **The subagent card**: `getModelContextWindow` (`src/lib/toolOutput.ts`) is a hardcoded table keyed on the model NAME — `deepseek → 64_000`. Against the live catalog that is wrong for **every** deepseek model deployed here (384k / 1M / 1M), so a 1M-window child's 250k tokens scored **391%** — clamped to a full red bar and a number three digits off.

**Considered Options**

- **Re-discover per prompt or per frame (rejected)** — the window is not per-turn state; this is one HTTP round trip per turn to re-read a value that changes when the operator edits their gateway.
- **Store the window as a per-session column (rejected)** — it would make the duplication durable instead of removing it. The fix is to stop copying model metadata into session state; a fourth copy is the bug with a schema migration.
- **Fix only the display, leaving `AgentLoop`'s window stale (rejected)** — it breaches ADR 0028's own invariant: the bar would read 1M while `should_compact()` still acted on 256k, converting a wrong number into an unexplainable agent. The live path must go through `set_model`, which rebuilds the `Compactor`, re-estimates, re-emits and re-persists in one step.
- **Push the corrected model to every live session of the refreshed provider (rejected)** — `set_model` is not free (rebuild + re-estimate + one `context_usage_update` frame + one `sessions` row write), so an unconditional push means N frames and N DB writes per press of the settings page's most-used button, for a value that usually has not moved. Scoping is therefore **per matched session, and only when the window actually differs** — pinned by `refreshing_a_provider_with_unchanged_metadata_pushes_nothing`.
- **Thread the catalog from `SpacesList` into the transcript as a prop (rejected)** — the subagent card sits two components below `ChatStream` → `MessageBubble`, inside a virtualized list, so this puts the catalog in the render path of every transcript row for a value one row kind reads. A small store (`store/modelCatalog.ts`) is the narrower seam, and `store/settings.ts` is the existing precedent for exactly this shape.
- **Chosen: one authority + explicit propagation.** The cache stays the only source; a refresh pushes to what holds a copy; a read derives instead of replaying; and a failed fetch is not an answer worth caching.

**Consequences**

- **`list_sessions` derives the window from `capabilities.model`, NOT from the `model` it resolved for `config_options`.** That second value falls back to the resolution chain for its own display purpose (ADR 0014's "never a hard error"), so using it would pair `used` — measured against the model the session actually ran — with an unrelated model's window, printing a confidently wrong percentage. An unresolvable stored key therefore keeps its snapshot, which is then the only window anyone knows. This distinction was caught by its own test, not by reading.
- **`getModelContextWindow` keeps the name table as a last resort.** The catalog wins for models it actually carries; a model it has never discovered still gets a guess rather than no number. That is deliberately not a deletion — the table is now wrong-but-better-than-nothing instead of authoritative-and-wrong.
- **A failed discovery is retried on the next read, not latched.** The old gate (`!entry.attempted`) marked a provider attempted BEFORE the fetch and left it attempted on failure, so one transient outage — the app launched before the network was up, a gateway mid-restart — showed `unreachable` with 0 models **for the rest of the process's life**, recoverable only by that provider's own refresh or a restart. This is the same defect as the stale window one layer down: the cache holding a wrong answer with no path to correction. `attempted` became write-only in the process and was deleted rather than left as a decoy.
- **Boot needs no new fetch.** The cache is per-process and starts empty, so the first read already IS a discovery pass; the failure-latch was the actual startup defect. `App` loads the catalog into the store once so the card has it, and a provider refresh re-loads it with the same `forceRefresh` that drives the backend push. Concurrent boot reads serialize on the cache mutex (`resolve` holds it across the fetch), so two Client callers cost one discovery pass and two cheap IPC calls.
- **`mergeRefreshedSessionRows` touches the per-id maps and NOTHING about membership.** `setHistorySessions` re-splits the three lists by the archived flag, and its own comment forbids running it mid-run (it would drop sticky live+archived entries and silently un-archive on the next close). It also skips ids that are LIVE: the store's map outranks the row, so a snapshot older than the session's own last frame would move the bar BACKWARDS.
- **The unparsed two-thirds of the payload is now the known gap.** The live deployment's `GET /model/info` exposes **35** distinct `model_info` keys across its 9 models; `LiteLLMModelInfo` reads **11** of them — `max_input_tokens` / `max_output_tokens`, `reasoning_effort_levels` + the seven `supports_*_reasoning_effort` booleans, and `supports_reasoning`. `input_cost_per_token` / `output_cost_per_token` are NOT parsed — and `Model::cost_per_mtok_in` / `cost_per_mtok_out` are **never read by any consumer** (the only occurrences are the two field declarations and the `0.0` initializers, and `ModelDto` does not carry them to the Client). Parsing pricing would populate a dead field, so pricing needs its own decision about what it is for; `supports_function_calling` is likewise unread, since every discovered model is `supports_tools: true`.
- **A live session's window can move mid-session.** It always could (a model switch), but a refresh now does it too — which is the intended behaviour and the reason the propagation reuses `set_model` rather than poking the field.

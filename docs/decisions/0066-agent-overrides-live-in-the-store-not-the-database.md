# Agent overrides live in the **store file** (`settings.json`), never on the `spaces` row — because closing a Space tab DELETES that row, and an override is exactly the configuration a tab close must not eat

An **Agent definition**'s model / thinking / tools can already be overridden app-globally, by ADR 0023's `subagentModels` map. This decision replaces that map with a real override layer carrying the whole trio, and settles WHERE the layer lives: **`settings.json`**, as `agentOverrides: { "<agentName>": { model?, thinking?, tools? } }` — a flat map keyed by agent name, serialized in camelCase like every other key in the file. What it is NOT: a column on the `spaces` table, which was the obvious home because **Trusted Space** already lives there.

The deciding fact is that `spaces` is not a durable per-Space store. `removeSpace` (`src/store/sessions.ts:643`) → `delete_space` → `DELETE FROM spaces WHERE path = ?1` (`src-tauri/src/storage/db.rs:721-725`) runs on **every tab close**, and ADR 0043 promises the re-opened folder returns WITH its history. Trust survives that because a security posture is expected to be re-granted; an override the user pinned for an agent surviving a tab close is the opposite expectation, so that row is the wrong table for overrides regardless of how well a column would fit. The argument is about **placement**, and it holds for the global map exactly as it held for the per-Space map this round does not ship: an override that a UI gesture can delete is not a preference, it is an accident waiting to happen.

**Why (secondary, and load-bearing for the Worker):** the **Worker process** has no DB (ADR 0025), so it reads `settings.json` in-process for exactly the things the Supervisor cannot hand it — and `resolve_launch` ALREADY does this for the ADR 0023 override (`src-tauri/src/agent/harness/launch.rs:58-63`). A store-file layer is therefore one `or_else` with no protocol change, and it keeps ADR 0023's "a settings edit takes effect on the NEXT dispatch, no restart" property. A `spaces` column would need the Supervisor to resolve overrides and add a field to the `Start` envelope, turning a live edit into a per-session snapshot.

## Considered Options

- **A column/table on the SQLite `spaces` row (rejected).** Beyond the deletion above: the Worker cannot read it, so it costs a protocol change and loses the no-restart property; and it is not hand-editable, which was ADR 0023's stated reason for choosing `settings.json` over a table in the first place. Its ONE genuine advantage — a dead Space's configuration dies with the row, so nothing orphans — is the same mechanism that makes it wrong, and it is bought back by the orphan rows the modal renders.
- **A repo-committed project layer, `<space>/.archimedes/agents.json` (rejected for now, and the shape does not block it).** This is ADR 0019's MCP pattern replayed — project file > store file > frontmatter — and it is the option a user who wants to *share* an agent setup with their team should eventually get. Rejected because it makes the Client a writer inside the user's repo, and because a repo file has no `spaces` row to clean up either. A flat `agentOverrides` map is deliberately NOT the place a repo layer would merge: a future project layer joins as a new, more specific layer in the resolver, so adding it later is a new layer, not a re-shape.
- **A separate `~/.local/share/archimedes/agents.json` (rejected).** A third config file for what the store file already hosts — the same rejection ADR 0019 made for MCP.
- **A nested `agentOverrides: { global, spaces }` shape (rejected — see *Deferred: per-Space*).** The nesting names the scope in the data, which is worth something; it also guarantees that the map a reader must understand has TWO levels before it reaches an agent name. With one editing surface and one layer, the scope is not information the file needs to carry, and the flat shape is the one the dispatch's own lookup wants: `agentOverrides` → name → fields.

## Deferred: per-Space

Per-Space overrides were designed — the nested `{ global, spaces }` shape, the canonical-path key, the second resolver rung — and then deliberately cut from this round to keep **one** editing surface for **one** global config (the reasoning is ADR 0068's, and the same cut removes the question of which layer a row is editing). This is a scoped decision with a named door, not a defect:

- **The wire shape is the only thing that has to change back**, and it changes additively: re-introduce a `spaces` sibling beside the flat map's entries by moving the map under `global`, leaving the per-Space map keyed by the canonical path. Nothing about `AgentOverrideFields` moves — the value type per agent is identical at both scopes.
- **The machinery for the second layer already exists in this very round.** Per-Space returns as a second one-time load-time fold plus one more `or_else` rung in the resolver, both sitting on code this round writes for the legacy `subagentModels` fold and the override rung. The store-file choice — the actual content of this decision — is what makes that a rung and not a redesign, because the Worker can already read every layer it would need.
- **`space_key` is the one hazard to carry forward**, and ADR 0064's warning is the reason: the key must be exactly the string `space_key()` produces (`db.rs:742-746`, `canonicalize().display()` — on Windows the verbatim `\\?\C:\…` form), never a path the renderer happens to hold. A raw-vs-canonical mismatch is invisible and makes an override silently never apply, which is the failure class ADR 0064 documents for the `spaces.path`/`sessions.cwd` joins.

## Consequences

- **The map key is an agent NAME, and case folds.** Same identity ADR 0023 chose: the backend resolves keys with a case-insensitive scan and never rewrites the stored key, so the UI writes `def.name` verbatim and drops every ASCII case-fold twin on the way (a `"Scout"` beside `scout` leaves the scan choosing in nondeterministic HashMap order). A Space folder that is renamed or moved is irrelevant to a global map — nothing here orphans on a filesystem move.
- **Orphaned entries are disclosed, not garbage-collected.** An override whose agent is no longer discovered stays inert on the wire (ADR 0023's rule, unchanged) and renders as a muted row with a remove button — the shape `SubagentSection.tsx`'s `orphanedSubagentModels` used at drafting, now MOVED into the sidebar **Agents** modal as that section is deleted (the affordance survives; only the screen that draws it changes, which is why ADR 0023 is amended rather than superseded). There is exactly one kind of orphan now, because there is exactly one map. **When a Space is open** — with no Space the modal suppresses the orphan block (its discovery read only sees the user roots and cannot prove a key stale), so cleanup is reachable after opening any Space.
- **`subagentModels` becomes a read-time legacy key, and the retirement is not optional.** `Settings::subagent_models` (the app-global per-agent model map of ADR 0023, `config.rs:203` in a `Settings` struct that is one flat list of ~22 top-level fields) gains `#[serde(default, skip_serializing)]`; `load_settings` folds it into `agent_overrides` on read and then clears it, so the first save after upgrade drops the dead key permanently. The fold must live in `load_settings` and not in the `get_settings` command, because the **Worker** reads settings directly (`launch.rs:59`) and a command-side fold would give the two processes different views of one file. Honouring the legacy key is what makes this an upgrade rather than a silent loss of the user's pinned models. **Note the asymmetry, because it reads as a contradiction and is not:** the legacy key is `skip_serializing` (it must stop appearing in the file) while the NEW map is plain `#[serde(default)]` (it must always appear, empty as `{}`, because the renderer types it required — the same contract every other map field in `config.rs` already keeps, none of which uses `skip_serializing_if`).
- **Provider-id remapping has one map to walk.** `SettingsPage.tsx:269-273` remaps model refs in `subagentModels` when a Provider is renamed so overrides do not orphan; it walks `agentOverrides` in the same pass instead. The hazard it exists to close is unchanged — renaming one Provider quietly orphans every override that named one of its models — but with one map there is one place to get wrong rather than a global map plus a map per Space.

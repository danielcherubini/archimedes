# The self-modification guard is an ASK when no rule matches — the protected agent-definition dirs are a guard-membership set, not a rule set

A write into one of the four user-level agent-definition directories — `~/.agents/skills`, `~/.pi/agent/skills`, `~/.agents/agents`, `~/.pi/agent/agents` — was refused **in every policy**, including the shipped default `writes: Allow`, by a hardcoded deny-list checked before the **Boundary** and routed to a tool-result error that never reaches the UI. That control did not prevent the write; it prevented the *telling* — the refusal was silent, so the model routed around it, usually through `bash`, which the deny-list never inspects. We decided: the unconditional deny becomes an **ASK** when no rule matches, and the four dirs become a **guard-membership set that is NOT a rule set**. `policy::default_rules()` returns **EMPTY**. `boundary::protected_dirs()` stays the plain four-dir list, feeding the guard's membership test and the sandbox's Landlock subtraction, unchanged. A **rules** list of `{path, direction, decision}` exceptions — USER rules, `decision ∈ {allow, deny}`, no `ask` value — is added beside the three posture selects, evaluated by longest canonical prefix in the ONE resolver `rule_for`, consulted by the gate and the executors alike.

**The consequence, stated at the top because it is the security claim this ADR narrows:** at the shipped defaults there are no rules at all, so **an untrusted Space gets the guard ask and a Trusted Space proceeds silently**. That silent proceed — not a residual default, not a rule someone has to delete — is the actual relaxation of ADR 0030's *"refused in **every** policy"*. It was the author's accepted posture (the spec says so twice: *"Trust suppresses the guard. A Trusted Space permits silent self-modification"*, and the Settings copy it mandates, *"A trusted Space's agent can also write its own instruction directories without asking"*), and it is the price of replacing a silent denial with a question. ADR 0030 carries the narrowing as an appended amendment; this ADR is its successor record, and neither file's `status` changes.

**One correction to make before anything else, because it was the run's most consequential misreading.** An earlier revision of this work made the four dirs `default_rules()`'s own `Write`/`Deny` rules and derived `protected_dirs()` from that rule set. That is `A AND NOT A` at row 3: the guard set and the default-deny set were the SAME paths under the SAME prefix predicate, so "no rule matches AND the target is under an agent-definition dir" was unreachable — measured at 0 of 16 cases across the four dirs at four nesting depths — and the spec's single behavioural change did not exist. This ADR records the corrected reading outright.

## The decision

Four rows, evaluated for a path-param tool against one concatenated list:

1. **A USER rule matches with `decision: deny`** → a tool-result error. **Trust-immune.** At the shipped defaults, with no user rules, this row cannot fire at all.
2. **A USER rule matches with `decision: allow`** → proceed silently; the posture select is not consulted.
3. **No rule matches AND the target is under one of the four agent-definition dirs** → **ASK** — the **Self-modification guard**. **Write-only:** a read of an agent-definition file is not an ask at any posture and falls to row 4. **Trust suppresses it like any other prompt.**
4. **No rule matches** → the posture select (`decision_for`), exactly as today.

**Row 3 is the only behavioural change.** Rows 1, 2 and 4 are additive: rules change nothing until the user writes one, and the posture stays open.

`FilePolicy` gains `rules: Vec<AccessRule>` (`settings.json` key `filePolicy`, `#[serde(default)]`, and an empty list is not serialized, so the three-direction wire shape stays byte-identical for every existing install). The gate and the executors consult the ONE resolver `rule_for` — ADR 0029/0030's one-canonicalizer rule, quoted in `policy.rs`'s own module doc: *"the gate and the executor must both go through `rule_for`, never a second matcher"*. The list they hand it is the concatenation `default_rules() ++ file_policy.rules`, assembled **once per turn** beside the `file_policy` re-read (ADR 0030 Deviation 4) and carried on `ToolCtx.rules`, so the two layers judge the SAME list and cannot decide differently about one access.

The enforcement split is directional and deliberate: the **gate** runs rows 1–3 for **writes** (`rule_or_guard_verdict`), because only a write can reach the guard's ask; the **executors** run rows 1–2 in **both** directions (`write_rule_refusal` for `write`/`edit`, `read_rule_refusal` for `read`/`find`/`grep`/`ls`). A `deny` rule refuses a read exactly as it refuses a write — row 1 is about the access, not the direction. **There is no read-side ask anywhere**, in either layer.

`default_rules()` is EMPTY, and it is empty for two independent reasons that both need stating. The four dirs are not rules — they are the guard-membership set, and putting them on the rule set is the defect described above. And the spec's three "pre-filled defaults" (`~` read/write `allow`, `/` read `allow`, `~/.pi/agent` read `deny`) are **USER rules the user writes through the Settings panel's "Add default rule" button, never code** — the spec itself says they are *"written only on first write"*, i.e. a Settings-side pre-fill, so there is nothing for a runtime default to emit and no install can silently gain the one real restriction. `protected_refusal_text` keeps its wording, now reached only when a rule has already decided `Deny`; a rule `deny` outside the guard set gets its own sentence (`rule_deny_text`) naming the rule's path, because the thing the user wrote is the thing they can go edit.

## Why a rule deny stays trust-immune and the guard ask does not

A `deny` — at the shipped defaults, a **user** `deny`, since there are no default denies — is a tool-result error (`deny_tool_result` at the gate, the executor's own refusal wording in the executors) that never reaches the UI in any configuration. Trust's entire meaning is *suppress prompts*. A deny is never a prompt, so trust has nothing to grip. ADR 0030's precedence sentence — **"Trust suppresses prompts but never widens a deny"** — stays true verbatim, and `is_guard_path`/`rule_or_guard_verdict` inherit it rather than re-implementing it: row 1 returns `Deny` before trust is even consulted.

The guard's row-3 ask **is** a prompt, so trusting a Space suppresses it. That is consistent with the precedence table, and it is newly *possible* because a guard prompt can now appear on a Space that is already trusted — which kills the assumption ADR 0030's prompt builder carried in a code comment (*"always three options, since a prompt only ever appears for an untrusted Space, so `trust-space` is always actionable"*). That comment is gone; the option list is per-prompt.

The asymmetry is the point, not an oversight: **deliberate trust still silences the guard, and nothing lets a `deny` be silenced.** One is the user choosing, once, in Space settings, to stop being asked. The other is a decision the user wrote down as a rule, and no prompt answer may walk it back.

## The guard prompt: `trust-space` is deliberately absent

The guard prompt's options are exactly three — `allow` ("Allow once"), `allow-directory` ("Always allow this directory" — persists one rule through the Supervisor relay), `reject` ("Block") — and **no `trust-space`**. Pinned by `a_guard_prompt_offers_exactly_allow_allow_directory_reject_and_no_trust_space`.

What is removed is not trust; it is the *shortcut inside the guard's own prompt*. The boundary prompt's third option — "Don't ask again for this Space" — persists `set_space_trusted(cwd, true)`. Left in the guard's list, the prompt that exists to protect the agent's own instructions would contain a **one-click, permanent way to disable that protection**, sitting in the position of the button a user reaches for precisely when a prompt has started recurring. Deliberate trust stays available from Space settings; accidental trust does not. Boundary prompts keep their own three options unchanged, including `trust-space` — they ask about the user's files beyond the read boundary, where "stop asking me about this Space" is a reasonable answer.

`allow-directory` carries a `path`: the **nearest existing ancestor** of the resolved target, through `canonicalize_lenient` — canonical, never a `~` residue. That is load-bearing rather than cosmetic. An earlier revision derived the ancestor from the RAW `path` argument, so a `~`-spelled write persisted a `~`-spelled rule that `rule_for`, matching against the executor's canonicalized target, could never have matched: the click that is supposed to stop the prompting would silently not stop it. The target is now resolved ONCE, leniently, and the same value feeds the rule lookup, the guard-membership test, the emitted ancestor and the executor.

## bash is not policed by rules — the OS-permission principle

**Rules never apply to `bash`.** The shell keeps its own posture select and its Landlock confinement under `Sandboxed`; `POLICIED_TOOLS` still carries `bash` in the `Shell` direction, where there is no path to resolve and nothing for `rule_for` to read.

One naming correction against the spec, because the spec's tool list is not the tree's: the spec names the policed set `read` / `write` / `edit` / `grep` / `glob`, and **there is no `glob` tool** — `find` IS the glob/search tool (its `pattern` parameter takes a glob), and the set the policy actually judges is `read` / `find` / `grep` / `ls` / `write` / `edit`, unchanged from ADR 0030's `POLICIED_TOOLS`. The shipped Settings copy repeats the spec's list verbatim, so the panel currently names a tool that does not exist; that is a one-line copy fix on the frontend's side, recorded here rather than silently re-worded in this ADR.

The principle, in the words the Settings panel is required to print: *`bash` runs with your own user's OS permissions — if the user cannot write a path, neither can the shell; that is a user-level concern, not an app policy.* Parsing a shell command for redirect targets was considered and rejected: base64, heredocs and interpreted scripts make it bypassable in a dozen ways while *looking* like enforcement. This is ADR 0030's *"a guard-rail, not a security boundary"* expressed as something a user can act on — the action being their own file permissions.

**The Landlock subtraction stays on `protected_dirs()`'s plain four-dir guard list**, and that is a decided consequence, not an accident of implementation. Landlock rules are ADD-only — a rule cannot take a right back from an ancestor — so the only way a confined `bash` is stopped from writing the agent's instructions is that the dirs are *subtracted* from the write roots at `Sandbox::create`. Because that subtraction consumes the plain guard list and not any rule set, **a user `allow` rule can never widen confined `bash`**, and no user rule ever reaches it. Pinned by `protected_dirs_ignore_user_rules_because_bash_never_applies_them`. A confined command therefore stays stricter than the path tools do under the same `allow` rule: that is the chosen posture, and it is the honest reading of "rules never apply to `bash`" from the sandbox's side.

## protected_dirs() stays the plain four-dir guard-membership list — ADR 0081's leniency is load-bearing on the guard set and on user rules

`default_rules()` returns EMPTY and therefore carries nothing, so ADR 0081's leniency has exactly TWO anchor points — **the guard set's own construction, and user-rule matching — and never `default_rules()`**, which is the third place a reader of the earlier revision would have looked:

1. **The guard set's own construction.** `protected_dirs()` keeps the machinery ADR 0081 mandated: entries are built through `push_protected` → `fs_backend::canonicalize_lenient`, so a directory that does not exist yet is **KEPT** as its canonical nearest-existing ancestor plus the re-applied trailing components, and an entry whose whole path cannot be resolved is kept RAW (issue #92's two halves; `protected_dirs_keep_a_missing_dir`, `protected_dirs_keeps_an_unresolvable_entry_raw`). That leniency is now load-bearing for a *second* consumer: a write into a not-yet-created agent-definition dir must still reach row 3's ask, and a strict compare on the membership side would silently no-op the test — #92's "a failed compare is a silent non-match" class, relocated onto the guard seam. It stays load-bearing for `sandbox.rs`'s subtraction over the same list, and for `protected_refusal_text`, whose canonicalize-both-sides compare is the one `is_guard_path` mirrors so the two layers cannot disagree about "under an agent dir". `protected_dirs_are_the_plain_four_dir_guard_membership_list` pins both halves at once: the list is the literal four dirs, **and** `default_rules()` is empty alongside it — two different sets, which is what makes row 3 reachable by construction.
2. **The spec's three pre-filled defaults, as USER rules.** Both sides of every rule compare go through the same lenient canonicalizer — the rule path after `~` expansion, and the call path — so a rule naming a directory that does not exist yet still matches (`a_rule_naming_a_directory_that_does_not_exist_yet_matches_leniently`). That is #92's property, now a property of user rules rather than of the deny-list.

The three defaults, when the user adds them: the two `allow` rows document the real state and change nothing at the default posture (the executor floor is already `["/"]`); the third, `~/.pi/agent` read `deny`, is **the one genuinely new restriction**, and it covers `~/.pi/agent/auth.json`, which today sits outside the **Boundary** and is therefore refused only under `reads: Sandboxed`.

A note on the count pin, because a plan of this run attributed the wrong file and the wrong function. There is no `default_rules().len() == 4` pin in `policy.rs` and never was one; the four-rule count assertion lived inside `boundary.rs`'s `protected_dirs_are_the_derived_default_deny_rule_paths`, the pin that asserted the *derivation*. The emptiness this ADR records is not that pin edited down to zero — it is T03's landing replacing the derivation pin with `protected_dirs_are_the_plain_four_dir_guard_membership_list`, which asserts emptiness and non-empty-guard-settiness together.

## The rule write follows ADR 0025's ownership

The gate runs in the **Worker**, which has no `Db` and no `config_dir` — which is exactly why the `trust-space` flag write lives in the Supervisor's `respond_permission` relay. A rule write follows the same split: **the relay persists it**, and the gate never persists anything. `settings.json` is the desktop's file (the Settings UI writes it), so the Worker is a reader of it and never a writer.

`PermissionOutcome::Selected` gained `value: Option<String>` — the option's `path`, echoed back verbatim by the UI — with the serde PAIR `#[serde(default, skip_serializing_if = "Option::is_none")]`: `default` so a previously-serialized outcome with no `value` still parses, `skip_serializing_if` so `None` OMITS the key rather than writing `"value": null` (bare `default` alone would have changed the wire bytes). The relay arm calls `persist_allow_directory_rule`, which goes through `load_mutate_write` → `append_rule` → `write_settings_atomic`. What it writes is one `ReadWrite`/`allow` rule — `ReadWrite`, so one "always allow this directory" answer covers the write that prompted AND the reads and greps into the same directory — appended at the END of the file's `rules`, which holds ONLY user rules (`default_rules()` is runtime-only and never serialized). A repeat click on the same directory writes nothing (dedupe by path + direction + decision, on the PERSISTED spelling verbatim, because matching canonicalizes at match time, not at write time). A blank or absent path persists nothing. The write is best-effort: a failure is logged and does not fail the user's answer, matching the `trust-space` arm's discipline. Subagent sessions ride the same relay — the child's gate is answered through the same `respond_permission` path.

## Decisions this run made that the spec did not state

1. **The exact-tie rule, and the concatenation contract.** The spec says longest-prefix matching *"needs no rule ordering in the UI"*. That is true — for the UI. It stops being true the moment two rules match at EQUAL prefix length, which after the component-prefix filter can only mean two rules naming the SAME canonical path. The run decided: on an exact tie the **last rule wins** (the resolver's `max_by_key` on `(component count, list index)` returns the last equally-maximum element; `an_exact_tie_goes_to_the_last_rule_so_an_appended_allow_beats_a_default_deny` pins the decision in its own name, in BOTH concat orders so an inversion fails loudly). And the runtime list is assembled by a **concatenation contract**: `default_rules()` FIRST — EMPTY at the shipped defaults — the per-turn user rules APPENDED, once per turn. Because the default half is empty, the contract's load-bearing content is the ORDER alone: under the corrected reading the "beats a default deny" case in that pin's name is history, and the live tie is between USER rules — an appended user `allow` beats a user `deny` on the same path, and beats any T06-prefilled default (`~`, `/`, `~/.pi/agent`) the user set. The file holds only user rules; the relay appends at the END of what is already there. Stated honestly: **the UI needs no rule ordering; the resolver and the persisted file both carry an order contract, and the exact tie is the one place order matters.**
2. **Spec deviation — the pre-filled defaults are NOT written automatically.** The spec says the three defaults are *"written only on first write"*. No first-write mechanism exists anywhere in the settings path — no save history, no version marker, and the Rust missing-file branch is not surfaced to the UI — and the wire cannot distinguish an empty `rules` list from an absent one (`skip_serializing_if` makes them byte-identical). T06 ships an explicit, user-visible **"Add default rule"** button that pre-fills the DRAFT and writes nothing until the user saves the dialog, plus panel copy naming all three defaults and labelling the `deny` row as deletable. Reason recorded: no automatic write is possible, so no install silently gains the one real restriction; the button plus the copy is the honest substitute, not a silent substitution. **Under the corrected reading this deviation is load-bearing for this ADR itself:** because the defaults are user rules and never code, `default_rules()` is empty and the four dirs are a guard-membership set rather than a default-deny floor set.
3. **The `settings.json` concurrency limit — NEW, and distinct from the spec's own limit.** `settings.json` has **six-plus independent whole-document writers and no shared lock** (the Settings page's whole-document save, `set_config_option`'s remembered-thinking-level write, this relay, and the rest; the landed doc comment in `load_mutate_write` states the count and the residual case). T04 narrowed two classes of exposure without closing the race: the relay's write is **atomic** (a `NamedTempFile` in the config dir, `sync_all`, then `persist` — `tempfile` moved from dev- to regular dependency, one line, version unchanged; and on unix the existing file's mode is copied onto the temp before the rename, because `NamedTempFile` creates 0600 and the rename takes the TEMP's mode, which would otherwise silently tighten `settings.json` from 0644 to 0600), and its read-modify-write **window is narrowed** to one function call (`load_mutate_write` re-reads immediately before the overwrite). The residual lost update, concretely: the relay appends its rule, and a Settings-page Save composed from a `useSettingsDocument` snapshot taken BEFORE that append then overwrites the whole document and **silently drops the rule** — and because the relay's write is best-effort-logged and it already returned, the loss surfaces to no one. Recorded, **narrowed, not closed**; the recorded follow-up is a settings-write `RwLock` or a save-version/merge at the store boundary. **And in the same breath, the two limits are not the same limit:** *"`settings.json` is not agent-writable-proof"* is a SECURITY claim — the file already holds `filePolicy`, is not in `protected_dirs`, and a model that can write it could already do anything with `bash`; that is pre-existing. The concurrency limit is a DIFFERENT claim, about writer interleaving, introduced by adding a second writer that runs while the user is not looking. This ADR and `docs/features/permissions-model.md` each state the two apart, with an explicit sentence that they are distinct, because conflating them would let the new limit hide behind a recorded one.
4. **The sandbox honesty point.** The subtraction fact above is a decision, not a leftover: Landlock's subtraction stays on `protected_dirs()`'s plain four-dir guard list *precisely so* a user `allow` can never widen confined `bash`. `Sandbox::create` keeps its `(cwd)` signature and consults no rules at all.
5. **The `home: None` limit.** With no resolvable home, `rule_for`'s `expand_rule_path` expands nothing against `None`, so a `~`-named USER rule matches NOTHING — a silent no-op, never a wider interpretation. Pinned by `a_tilde_rule_with_home_none_matches_nothing_and_with_a_real_home_matches_and_decides`, whose `ToolCtx.home` doc states exactly that. `default_rules()` is empty **by decision at all times**, so an empty rule set is no longer a no-home edge: `an_empty_rule_set_matches_nothing_so_the_posture_select_decides` now describes the ordinary shipped state — `rule_for` answers `None`, and the caller falls through to the guard's row-3 ask for a write under one of the four dirs, and to the posture select everywhere else. The reachability nuance is recorded honestly: on unix `home_dir()` falls back to the passwd database, so an unresolvable home is practically unreachable from a test process, which is why the earlier `#[ignore]`d no-home fixture was deleted rather than kept as a landmine; the reachable consequence is the empty-rule-set pin above.

## Considered, and rejected

- **Widen the Boundary** (`~`, `~/.pi` as roots). Fixes nothing — the refusal came from the deny-list, which is independent of roots — and collides with discovery: `find_skill_files` recurses, so widening discovery to `~/.pi` would admit `~/.pi/agent/extensions/*/SKILL.md` at depth 3, which is not in the guard set and writable at the default posture. A model could plant a **Skill** injected into every future session. Narrow discovery roots are load-bearing.
- **Rules as the primary enforcement model** (revoke = actually block). Pre-filling `~` read/write and `/` read as the ONLY grants would make the app *more* restrictive than today, since `/` write is allowed now and an unmatched path would get nothing. Contradicts the open posture ADR 0030 chose.
- **Default-deny floors for the four dirs as `default_rules()`** — the rejected reading. It makes row 3 `A AND NOT A`, the guard prompt unreachable, and ships the silent-deny defect this spec exists to fix. Rejected by this ADR's own premise; see the correction at the top.
- **An `ask` value in `RuleDecision`/`AccessPolicy` for the guard.** Rejected per the model: a `deny` stays a `deny` (now a USER deny), and absence of a rule IS the ask. Adding `ask` to the decision vocabulary would let a rule claim to deny while doing something else.
- **Parse `bash` commands for write targets.** Bypassable in a dozen ways while looking like enforcement. See the OS-permission principle.
- **Re-read `settings.json` per tool call** to make "always allow" immediate. Breaks ADR 0030 Deviation 4's one-read-per-turn design, which is pinned. Rejected as disproportionate for a one-time cost per directory.

## Consequences

- **Per-turn effectiveness.** An `allow-directory` answer persists a rule that is re-read once per turn (Deviation 4), so it takes effect at the **next prompt**, not mid-turn: five writes into a fresh directory prompt **five times** the first time. Disclosed in `docs/features/permissions-model.md`, not left to the module doc.
- **Subagent sessions are covered** — their prompts reach the UI and the same relay persists their rule writes.
- **The Settings surface**: a Permissions section carries the rules list (row + add/edit dialog, three fields, no Test action), the posture rows and the trust toggle moved out of General, the scope copy the `bash` decision requires, and the rewritten trust copy. `docs/features/permissions-model.md` is its user-facing page; `CONTEXT.md`'s **Beyond-boundary policy**, **Permission prompt**, **Trusted Space**, **Boundary** and the new **Self-modification guard** entries are the vocabulary.
- **The shipped-defaults consequence, again at the close, because it is the point of the whole change:** with no user rules at all, an untrusted Space is ASKED and **a Trusted Space proceeds silently**. That is the deliberate relaxation of ADR 0030's claim, bought with a visible prompt in place of an invisible refusal, and it is what the corrected trust copy now promises.
- **ADR 0030's amendment** (its 2026-10-28 amendment) narrows the universal-deny claim in place, leaving the original sentences standing above as written.
- **ADR 0081's armed probe now hits this feature.** Measured empty at 0081's writing — `grep -rn -iE "protected|deny-list|guard-rail" docs/features/ docs/css-theme-tokens.md` (**both paths**) — it is now expected to hit `docs/features/permissions-model.md`. That is the new page answering 0081's recorded gap (*"`docs/features/` has no page for the protected directories at all"*), not a regression.
- **Two glossary sentences outside this task's touch list were falsified by this change, and are NOT edited here.** `CONTEXT.md`'s **Agent definition** entry says *"the user-level agents dirs are readable through the **Boundary** but on the write deny-list (`boundary::protected_dirs`) — a session may not rewrite its own agent definitions"*: the first clause stands (the read roots are untouched) and the second is now about a **deny rule** the user may or may not have written, with the no-rule case being the **Self-modification guard**'s ask rather than a refusal. The **Lenient deny-list entry** entry likewise says a Session *"is refused writing into it immediately, with no restart"* — the entry is still KEPT and still compared leniently, which is that entry's actual subject, but a no-rule write into it is now ASKED rather than refused (ADR 0081 had already flagged this entry as over-claiming by one clause, and that flag is now about a different clause). Both are one-clause follow-ups for whoever owns those entries next, recorded here so a later sweep reads them as **known** rather than as drift from this change.

# The verbatim `\\?\` Windows path is stored and compared exactly as `canonicalize` produces it, because it is what a long path opens with AND the string ten Space↔session joins compare — so a strip moves every site in one change or none

A Windows user sees `\\?\C:\Users\me\proj` in a Space tab's tooltip, in the database, and in the Worker's `cwd`, and every reader's first instinct is to strip the prefix. We decided: **the prefix stays.** `std::fs::canonicalize`'s Windows output is persisted, compared, handed to the Worker and displayed verbatim, and **any future strip must move every coupled site in a single change or move none of them.** The reason is two-sided and independent: the prefix is doing real work for long paths, and it is the join key of the entire Space↔session relationship. The "obvious cleanup" breaks the app twice over — a deep Space stops opening, and Spaces silently lose their sessions.

This ADR records the decision, its evidence status, and the traps for whoever eventually strips it. It is a decision **not** to change behaviour, so it comes with an explicitly unresolved question, recorded at the end rather than quietly dropped: **this ADR does not claim the verbatim path is, or is not, the cause of the reported first-Space failure.**

**Numbering, so nobody renumbers after a merge race:** this is **0064**. `0062` exists on the unmerged `feature/ui-design-lightning-round`, and `0058`/`0059` exist on the unmerged `feature/web-search-and-fetch` — while `main` already cites "ADR 0058" in source comments (`agent/session/router.rs:83`, `agent/web/render.rs:5`, `navigation_guard.rs:73`) with **no file behind the citation** on that checkout. The gaps are therefore not fillable and nothing here is renumbered; `git log --all --diff-filter=A` over `docs/decisions/` shows no `0064` anywhere in the object database.

## The prefix is load-bearing for long paths — and that sentence is an inference, labelled as one

Verified in this tree (each re-run while writing this ADR, not trusted from the plan):

- `src-tauri/windows-app-manifest.xml` is **14 lines** and contains **no `<longPathAware>` element** (`grep -c longPathAware` → `0`); its whole content is the Common-Controls-v6 `dependentAssembly`.
- Its "byte-for-byte copy of tauri-build's default" claim (`build.rs:21-23`, restated as "byte-equal" at `:84-86`) holds: `md5sum` of our manifest and of the vendored one in **each** locally-vendored `tauri-build` — 2.6.3, 2.7.1 and the locked 2.7.2 — are all `52be4de7dbb84d8eef5a957d679195cc`. `tauri-winres` 0.3.6 contains no `longPathAware` string anywhere, so there is no second place the element could already come from. `build.rs:93-98` embeds the file with `/MANIFEST:EMBED` + `/MANIFESTINPUT` + `/WX` on the `windows`+`msvc` branch, after `new_without_app_manifest()` (`:46`) takes it away from `tauri-winres`.

Microsoft's documented mechanism (*Maximum Path Length Limitation*) then says: without long-path awareness, the Win32 wide file APIs reject a **non-verbatim** path over `MAX_PATH` (260) with `ERROR_PATH_NOT_FOUND`, while the `\\?\` verbatim form bypasses that check entirely. Read together — no manifest element, plus that mechanism — the verbatim prefix from `canonicalize` is currently **the only thing letting a Space deeper than 260 characters open at all.**

⚠ **That last sentence is an inference from a verified manifest fact plus Microsoft's spec. It was not observed on a Windows machine**, and nothing in this repo has executed it. State it that way or not at all.

Two further precision points, both easy to get wrong:

- The manifest element and the registry value are **conjunctive**. Microsoft states both must hold: the `<longPathAware>` element, *and* `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled` (`REG_DWORD`) present and `1`, cached per process after the first affected call — so a change is invisible to a running process and may need a reboot. Adding the manifest element alone therefore does **not** make long paths work on a user's machine.
- **The default value of that key is NOT verified here, and neither is any platform's default.** The widely-repeated "11 ships it on, 10 ships it off" claim was not confirmable from Microsoft's own page and a third-party report describes a Windows 11 install where it read `0`. Do not repeat either default as fact. It also applies only to a named list of `…W` functions — it is not a global "`MAX_PATH` is gone" switch. **The verbatim `\\?\` route needs neither condition**; that is the distinction to keep: the registry value gates only the *manifest-based, non-verbatim* route.

The part of the chain that **is** locally verifiable, and is real: the path does reach the OS as a string, so no type protects it after conversion. `StartEnv.cwd` is a `String` (`agent/worker/protocol.rs:201`), built from `cwd.display().to_string()` (`agent/session/mod.rs:959`), turned back into a `PathBuf` in the Worker (`agent/worker/core.rs:253`) and handed to the OS as `cmd.current_dir(&ctx.cwd)` (`agent/tools/exec.rs:401`). So "it stays a `PathBuf`, therefore only display strings change" is **false** on that leg — strip the prefix there and a working deep Space becomes failures, and a re-keyed `sessions.cwd` re-canonicalized on resume (`agent/session/mod.rs:1156`) fails and reports *"folder not found"* for a folder that exists.

## The coupling: two writers, one string, ten readers

Two different code paths write the same folder's path, and they must keep producing **byte-identical** strings:

| | Written by | Shape |
|---|---|---|
| `sessions.cwd` | `Db::record_session` — the ONLY writer (`src-tauri/src/storage/db.rs:314`, the value at `:325`) | the **raw** `info.cwd.display()` — no canonicalization at all |
| `spaces.path` | `Db::upsert_space` (`db.rs:644`) → `space_key()` (`:645` → `:742-746`) | **re-canonicalized** (`canonicalize().display()`, raw fallback on failure) |

Production keeps them equal because the cwd is canonicalized before either writer sees it (`agent/session/mod.rs:1133` on start, `:1156` on resume); the invariant is about the two **stringifiers**, not about canonicalization being free.

What depends on that equality is **raw string comparison**, at ten frontend sites — `session.cwd === space.path` at `src/store/sessions.ts:466`/`:502`/`:560`/`:565`/`:921`/`:966`/`:1249`, plus `src/components/SpaceTabs.tsx:106` (the tab-close "how many are open" gate), `SpaceTabs.tsx:162` (the per-tab status fold) and `src/components/SpacesList.tsx:74` (`spaceNameFor`, reached with `session.cwd` from `:204`/`:758`). Same equality at `sessions.ts:1038` gating `startSessionInActiveSpace`, and `addSpace(info.cwd)` (`sessions.ts:1053`, `NewSpaceDialog.tsx:93`) derives the tab from it. Rust compares the same strings: **`agent/worker/manager.rs:768`** matches Workers with `entry.env.cwd == cwd`. And `find_space` (`db.rs:691-694`) / `delete_space` (`:721-725`) take the frontend's string **raw**, so a mismatch fails in silence — while `set_space_trusted` (`db.rs:660-661`) re-canonicalizes, so a trust write would still land on the *other* row. **The two sides would drift differently, which is worse than drifting together.**

Grep `cwd ===` rather than trusting those line numbers — they drift; the invariant does not. (One correction carried forward from the plan: the plan body's `sessions.ts` numbers were each one line above the comparison, and its `SpaceTabs.tsx:150` citation is a `s.path === activeSpacePath` compare, not a cwd compare.)

**The tripwire is `src-tauri/tests/storage.rs::the_session_cwd_string_and_the_space_path_key_are_the_same_string`** (`:688`). It is a **characterization test**: it passes today and is not bug-hunting. It canonicalizes its fixture dir *before* building the `SessionInfo` — load-bearing, not hygiene, since a raw temp path diverges on macOS (`/var` → `/private/var`) and on Windows (prefix added on one side only) for reasons unrelated to the coupling — records a session and upserts a Space, then reads **both** strings back out of the database and asserts equality. Its whole job is to redden the moment either stringifier is normalized without the other; it was proven non-vacuous by mutation probes on each side in turn (both went red).

## If you ever strip it: three traps, all verified, all silent

1. **Migration ordering bricks startup.** The probe-then-transaction migrations in `Db::open` sit at `db.rs:120-132` (a `pragma_table_info` probe, then a transaction) and `:144-161` (two `sqlite_master` probes, then a conditional `ALTER`), i.e. **before** `conn.execute_batch(SCHEMA)` at `:162`. A `SELECT … FROM spaces` there errors `no such table`. A re-key must run **after** `:162`.
2. **`spaces.path` is a `PRIMARY KEY`** (`db.rs:778`). An `UPDATE` onto a plain key that already exists raises `UNIQUE constraint failed`, which propagates as `DbError::Sqlite` and **fails `Db::open` forever** — a bricked application, not a caught error. The file's own comments at `:133-143` describe exactly this class of self-inflicted permanent failure (a re-run hitting `no such table` → rollback → `Db::open` erroring forever). Delete-then-update also silently discards the verbatim row's `trusted`, reintroducing the forgotten-trust-flag bug the migration would exist to prevent.
3. **A SQL `LIKE` probe matches zero rows.** Re-run here against `sqlite3` 3.51.2 with a seeded `\\?\C:\proj` row (written from a `.sql` file — shell quoting eats backslashes; the stored value's `hex()` confirms `5C5C3F5C433A…`): `path LIKE '\\?\%' ESCAPE '\'` → **0 rows** (under `ESCAPE '\'` the pattern is a 5-character exact match with no wildcard), `substr(path,1,4)='\\?\'` → 1 row. A probe that finds nothing makes the migration report success on every database except the ones it exists to fix. Prefer a Rust-side `starts_with(r"\\?\")` scan; if SQL is needed, use `substr`. `LIKE` is also ASCII-case-insensitive where a `PRIMARY KEY` lookup is binary (`LIKE '/tmp/alpha'` → 1, `path = '/tmp/alpha'` → 0) — another way the probe and the real operation disagree about whether a row exists.

## What is genuinely unaffected — so nobody over-scopes

The sandbox, the trusted-space lookup and `FsBackend` canonicalize **both** sides at check time, so both carry the same `\\?\` shape and they agree. Re-read, not trusted: `FsBackend::check_under_roots` canonicalizes each root per check (`agent/fs_backend.rs:161-171`), the session boundary's `canon` helper canonicalizes before comparing (`agent/boundary.rs:96-98`), `agent/tools/sandbox.rs:579` canonicalizes the write root against already-canonicalized `protected_dirs`, `agent/tools/exec.rs:320-323` canonicalizes both sides, and `space_trusted` (`db.rs:705-717`) canonicalizes its `Path` argument. None of these needs changing, and none is evidence that the string sites are fine either.

⚠ **The wording trap in that paragraph: `canonicalize` does not *remove* the verbatim prefix on Windows — it *adds* it.** `agent/boundary.rs:28-35` records the real CI failure this caused (`read: path escapes the session sandbox: \\?\C:\Users\runneradmin\AppData\Local\Temp\…\secret.txt`, from comparing a verbatim path against a bare `/`). Reasoning "the OS normalizes it away" is precisely how this bug comes back; apply that thought to a **string** site first — `sessions.cwd`, `spaces.path`, the `SpaceTabs.tsx:237-240` tooltip, `StartEnv.cwd`.

## Not settled, and this ADR does not pretend otherwise

**The reporter's Windows log evidence is still outstanding.** No Windows machine, no Windows VM run against a real Space, and no channel to the reporter were available on the branch that produced this analysis. No Windows output has been invented, paraphrased from expectation, or reasoned into existence here. **Nothing in this file settles which of the two candidates failed on their machine, and nobody should cite this ADR as having done so:**

- **`no models available for the native session`** — `SessionError::Command` at `agent/session/mod.rs:1796`, the leading hypothesis because a fresh install has no provider configured and it fits every observed fact (first Space, new Windows install, a structured rejection, no log on disk).
- **A drive-root verbatim path** — `canonicalize` on `C:\` yielding `\\?\C:\` (documented shape, not observed here), reaching something that mishandles it.

Only a log distinguishes them. What would settle it, in one session on the reporter's machine: set `ARCHIMEDES_DEBUG=1` **before launching** (read once at startup, `agent/debuglog.rs:42-56`; with it unset no file is created at all) on a build **containing the diagnostic** — the `ipc start_session FAILED: …` line exists in no released build — then open a Space (i) at a drive root, (ii) at an ordinary shallow folder, (iii) at a path over 260 characters, and read `%APPDATA%\archimedes\supervisor.log` (on Windows that directory resolves via `SHGetKnownFolderPath(FOLDERID_RoamingAppData)`, which **ignores** `%APPDATA%` — ADR 0025) alongside the `spaces` and `sessions` tables. The same sentence in all three cases exonerates the path entirely; only (i) failing implicates it. Note the ordering problem this creates for closing the issue: the diagnostic that identifies the cause ships in the same branch as the fix for the symptom that hid it.

## Considered Options

- **Strip `\\?\` at four sites plus a re-key migration (rejected).** This was the plan's first draft, and two review passes found it would have shipped three regressions, each verified by experiment: deep Spaces failing to open (the prefix is load-bearing), `addSpace(info.cwd)` minting a second tab for one folder while sessions render in no Space group (the ten equalities), and a migration that either errors `no such table` or bricks `Db::open` permanently. The characterization test above is the guard that replaced it.
- **Strip at the display boundary only (rejected).** It looks like the safe half, and it is the worst option: the frontend would keep comparing the plain form while the database and `SessionInfo.cwd` carry the verbatim one, so the ten joins and `manager.rs:768` break while the trust writes — which re-canonicalize — keep landing. Two sides drifting **differently** is strictly worse than two sides drifting together.
- **Add `<longPathAware>` now (deferred — needs its own ADR).** It changes what the shipped binary can open, it is gated by a per-machine registry value we do not control and whose defaults are unverified, and it makes `build.rs:21-23`'s and `:84-86`'s byte-equality claim **false** — that claim is the entire "nothing disappears from the shipped app" argument the unscoped-embedding workaround rests on, so the comment must be rewritten in the same change that adds the element. Deferring it is not dismissing it: a Space deep enough to cross 260 characters may be misbehaving today for this reason alone.
- **Fix the `//?/C:/…` shape in the system prompt (rejected as cosmetic, and as a one-sided normalization).** `agent/harness/prompt.rs:138` slash-normalizes the cwd (`replace('\\', "/")`), so a Windows prompt shows `//?/C:/Users/me` — a path the model cannot use. It is a path in a prompt, cosmetic on both platforms, and fixing it alone is exactly the one-sided normalization this decision exists to prevent. Two sibling sites are untouched for the same reason and are listed so a `canonicalize` grep does not read them as oversights: `src-tauri/src/agents.rs:139` (`path: canon.to_string_lossy()…`, canonicalize at `:105` — the crate-root `agents.rs`, not `commands/agents.rs`) and `src-tauri/src/skills.rs:259`, which feed the prompt's `<location>` / `<project_instructions path>` attributes (`agent/harness/prompt.rs:95-97`).

## Consequences

- **The prefix is a wire format, not a display artifact.** Any future change to how `sessions.cwd`, `spaces.path`, `SessionInfo.cwd` or `StartEnv.cwd` is stringified is a change to a join key and must name the ten equalities, `manager.rs:768`, and a migration in the same change. The characterization test is the tripwire; ADR 0063's envelope is unaffected by it (`message` interpolates this path into prose).
- **`\\?\` in the UI is accepted, for now, as a known wart** — the honest trade is a readable-looking tooltip against a Space whose sessions vanish, and the second is worse. A display-only fix that keeps the compared strings identical (e.g. formatting the tooltip from both sides identically) is the only shape that does not need this ADR reopened.
- **Long-path awareness stays the first follow-up**, tracked as its own decision rather than folded in here, because it alters the shipped binary's capabilities and invalidates a `build.rs` invariant.
- **This ADR's Windows half rests on reading, not observing.** Verified: the manifest, its md5, the ten join sites, `manager.rs:768`, `spaces.path`'s `PRIMARY KEY`, the migration ordering in `Db::open`, the `LIKE`/`substr` probe asymmetry, and that the characterization test reddens under mutation on either side. Not verified: any Windows runtime behaviour, every `LongPathsEnabled` default, and which candidate actually failed for the reporter.

# Permissions model — posture, rules, and what an Agent definition may narrow

Three kinds of setting decide what a **Session** may touch on your disk. The first has existed since [ADR 0030](../decisions/0030-file-access-policy.md): a **posture** per direction. The second is a list of **rules**. The third is newest, and it is not yours — it is a **definition's** `permission:` block, authored in an Agent's markdown file, and it governs a **child subagent only** (`## The third layer`). The thing that changed most about the first two is neither of them — it is what happens when neither has an opinion about a write into the agent's own instruction directories. It used to be a silent refusal. It is now a question. See [ADR 0083](../decisions/0083-the-self-modification-guard-is-an-ask-when-no-rule-matches.md).

## The model

- **Posture** — `reads` / `writes` / `shell`, each `Sandboxed` / `Ask me` / `Don't ask me`, **defaulting to `Don't ask me` (`Allow`)**. Unchanged in meaning and in values. `Sandboxed` refuses a file tool and confines `bash`; `Ask` prompts unless the **Space** is trusted; `Allow` is silent and unlogged.
- **Rules** — a list of `{path, direction, decision}` exceptions, `decision ∈ {allow, deny}`. **USER rules only.** `direction` is required, because "`/` has read" is direction-specific, and `path` may lead with `~` (expanded at MATCH time, never at write time, so a rule survives a home-path change).

**There is no `ask` decision value.** Asking is not a setting; it is what happens when no rule matches and the guard applies. That is what keeps the vocabulary honest: a `deny` stays a `deny`.

Both live in `settings.json` under the existing `filePolicy` key (`FilePolicy { reads, writes, shell, rules }`). `rules` is serde-defaulted, so an old `settings.json` with no `rules` key parses to the new empty default, and an EMPTY list is not serialized at all — the three-direction wire shape is byte-identical for every existing install.

The four user-level agent-definition directories — `~/.agents/skills`, `~/.pi/agent/skills`, `~/.agents/agents`, `~/.pi/agent/agents` — are a **guard-membership set, not a rule set**. They are not rules, they are not defaults, and nothing in `settings.json` can add or remove them. See `## Matching`.

**The third kind of setting is not a setting of yours at all.** An Agent definition — the markdown file behind a `subagent` dispatch's `agentName` — may declare a `permission:` block (opencode's per-tool `allow` / `ask` / `deny` vocabulary, issue #101). It is not in `settings.json`, it has no Settings control, and it is not merged into `FilePolicy`: it is a per-definition, per-tool ruleset that reaches the gate as its own layer. Two facts about it belong at the top, because both are the opposite of what a reader of a permissions page would assume:

- **It governs a child subagent only.** No main-session path passes an `AgentDefinition` to anything: `resolve_agent_launch` has exactly two production callers — the Agents modal's read-only report and the `subagent` tool's own dispatch — and a main session's `StartEnv` is built with `permission: None`, whose code comment states the reason. **So a definition's `permission:` block cannot affect a normal Session, cannot affect you reading this page, and cannot affect what your main agent reaches for.** It tightens the child that definition creates, or it does nothing.
- **It can only ever NARROW.** `Allow < Confine < Ask < Deny`, strictest wins, and a file's "no opinion" and its `allow` are both identities. See `## The third layer` for why that ordering is not the obvious one.

## Precedence

For a path-param tool, in this order:

| # | Condition | Outcome | Trust-immune |
|---|---|---|---|
| 1 | A **user** rule matches, `decision: deny` | tool-result error — never a prompt | **Yes** |
| 2 | A user rule matches, `decision: allow` | proceed silently, posture not consulted | n/a |
| 3 | No rule matches **and** the target is under an agent-definition dir | **ASK** — the **Self-modification guard** | No — it is an ask, so Trust suppresses it |
| 4 | No rule matches | the posture select, **then the child's definition `permission:` block tightens it if it can** (row 4's tail — `## The third layer`) | the definition layer never reaches rows 1–3 |

**Row 3 is the only behavioural change to the user-policy rows.** Rows 1, 2 and 4 are additive: nothing changes until you add a rule, and the posture stays open. Row 4 gained a tail in issue #101, and that tail is a **child-only, narrowing-only** consult — it is the reason the table still has four rows instead of five.

**At the shipped defaults there are no rules at all**, so row 1 cannot fire, and an untrusted **Space** gets the guard ask while **a Trusted Space proceeds silently**. That silent proceed is the deliberate consequence of the change, and the reason the trust copy below was rewritten.

Row 3 is **Write-only**: reading `~/.pi/agent/agents/SKILL.md` is not an ask at any posture — a read with no matching rule falls to row 4, which under the default `reads: Allow` proceeds silently. A `deny` rule refuses a read exactly as it refuses a write, because row 1 is about the access, not the direction; there is simply no read-side ask anywhere.

### The strictness order, and why `Confine` is not a midpoint

The definition layer merges into row 4 by **strictest wins** over a total order — `Allow < Confine < Ask < Deny` — implemented as two arms in `stricter_of_two`, not as a `min` over a rank. The ordering is the subtlest thing on this page, so it is worth the paragraph it costs.

`Confine` is the odd one out because **it is not a permission level; it is a running sandbox.** It is what `shell: Sandboxed` produces for `bash` — the command *runs*, inside a Landlock ruleset the user asked for by choosing that posture. Two consequences follow, and they point in opposite directions:

- **`Confine` ranks ABOVE `Allow`,** because a confined command has already been granted to run. A definition's `bash: allow` therefore cannot un-confine it — releasing the sandbox would be a grant of OS reach, which is the one thing this layer may never make. Posture `Confine` + definition `Allow` → **`Confine` stands**.
- **`Confine` ranks BELOW `Ask`,** because asking is strictly more restrictive than running quietly inside a sandbox: a prompt hands the decision to a person, a sandbox merely narrows what the command can do. So a definition's `bash: ask` **tightens a confined run into a prompt** — `Ask` beats `Confine`.

A merge written as a rank over the three per-agent verbs `{allow, ask, deny}` mis-orders `bash` in one of two directions: either an `allow` releases the sandbox (the exact widening the layer forbids), or an `ask` fails to tighten a confined shell (a narrowing silently refused). Both arms exist to be readable, and each has its own pin — `a_definition_cannot_unconfine_a_sandboxed_shell` and `a_definition_ask_tightens_a_confined_shell`.

`AsSelf` — the file does not speak about this tool, or cannot decide it — is the merge's identity, and it is a **separate verdict type rather than `Decision::Allow`** on purpose: `Decision::Allow` means "run it", which is not what a silent file means, and collapsing the two would let "no opinion" be read as a grant. A definition's `Allow` is also an identity: it can beat nothing.

### The one precedence boundary that is NOT narrowing-only

**A user `allow` rule (row 2) outranks a definition `deny`.** Row 2 returns before the definition layer is ever consulted, so a write into a directory you explicitly allowed goes through even if the child's definition denies that whole tool. This is a **boundary of the design, not a bug in it**: the definition layer sits *below the user's rule list and above the posture*, and the user's own explicit rule is the wider authority. The same control flow that makes it true also makes the interesting claim true — because rows 1–3 return early, a definition can never see them, so it can never un-block your `deny` and can never silence the guard. All four cells, in both directions, are pinned by one test: `the_row_precedence_cells_are_untouched_by_the_definition_layer`, which includes the case a reader would not predict — **a definition `deny` cannot rewrite the guard's `Ask` into a silent refusal either**, because row 3 answers first. You still approve that write by hand; nothing is granted that the guard would have stopped.

## The third layer — what a definition's `permission:` block can and cannot do

Issue #101. A definition declares it in its frontmatter:

```yaml
permission:
  edit: deny          # a BARE verdict — this is what gets enforced
  read: ask
  bash:
    "*": allow        # a PATTERN object — parsed, announced, NOT enforced
```

**Where it is consulted.** At the tail of row 4 and nowhere else (`policy_verdict` calls `stricter_of_two(decision_for(…), definition_verdict(…))` after `rule_or_guard_verdict` has declined to answer). That single position buys the whole safety property: it cannot bypass a user `deny` (row 1), cannot bypass a user `allow` — which is the boundary above — and cannot bypass the protected-dir guard (row 3); and it *can* tighten a Trust-widened `Allow` back into an `Ask`, because Trust suppresses prompts and is not a grant. That is ADR 0030's *"trust suppresses prompts but never widens a deny"* applied to definitions, and the rejected alternatives for that placement — consulting at row 1, or letting an `allow` override rather than intersect — are recorded in [ADR 0084](../decisions/0084-a-definition-permission-block-is-consulted-only-at-the-tail-of-row-4-and-can-only-narrow.md).

**How it reaches a child.** File → `AgentDefinition.permission` → `resolve_agent_launch`'s `[File]`-only rung (`source.permission` reports `file`, or `parent` when the file is silent — there is **no `settings.json` rung** and no fourth `OverrideSource` variant) → `LaunchConfig.permission` → the dispatch wire verbatim → the child's `StartEnv.permission` → `worker/core.rs`'s `loop_.set_permission(…)` → that child's own gate. Every hop is a place the block can be dropped and enforcement becomes decoration, so the acceptance test pins two independent halves: that the block rides the wire, **and** that the child's own `bash` call is refused by the child's gate (`the_definition_permission_deny_refuses_the_child_real_worker`).

**What it can also do, before the gate: shrink the advertised tool set.** A whole-tool `deny` removes that name from the child's resolved `tools` list, so the model is never offered a call the gate would refuse. A list the drop **empties stays `Some(vec![])` — zero tools — and does NOT fall back to `None`**, and that is a deliberate exception to [ADR 0067](../decisions/0067-an-agent-override-never-speaks-by-being-empty.md)'s emptied-means-ABSENT rule, whose reasoning is about a *typo* accidentally zeroing a child. `None` is not "no tools": it means *"the parent's list minus the guard"*, so reusing that rule here made the most restrictive file the least restrictive outcome. 0067 carries the narrowing; the boundary is **emptied by accident → silent (ABSENT); emptied on purpose by a `deny` → nothing (`Some(vec![])`)**.

**When an edit to a definition's block takes effect.** At the **next dispatch**, not per turn: `resolve_launch` discovers the definitions and reads `settings.json` itself each time a `subagent` call runs (ADR 0023's property), so a file edit is seen by the next child and by no child already running. That is a different freshness rule from the user's rules and posture, which are re-read **once per turn** (`## When an "always allow" takes effect`) — a child that is already running keeps the block it was dispatched with, exactly as it keeps its model.

**A refusal from this layer is worded exactly like any other refusal.** It arrives through the same `Some(Decision::Deny)` arm and the same `deny_tool_result`, so a definition's `no` is byte-identical to a user rule's or a posture's — no per-layer renderer, and the model's recovery cannot depend on which layer spoke (ADR 0030). An `ask` this layer produces is likewise an ordinary `Ask`: on a **Trusted** Space it is auto-approved by the same short-circuit that suppresses any other prompt, so the tightening is a decision and not a stall (`a_definition_ask_tightens_a_trust_widened_allow` pins both halves — the verdict becomes `Ask`, and no prompt event appears).

**The Agents modal reports the block, and nothing sorts.** `filePermission` carries the declared ruleset verbatim with `source.permission` naming the layer, and `frontmatterNotes` carries the announcements. Both are display-only — no control, no authoring UI, because the rules are authored in the markdown file and a control here would promise an edit the surface cannot perform. Nothing sorts either list: a tool's pattern rows are ordered and the last match is the one that would decide, so a `.sort()` would print a sequence in which a different rule appears to win.

## Matching

**Longest canonical prefix wins — never first-match.** Granting `~` read/write while denying `~/.pi/agent/agents` must not let the broad rule swallow the specific one; under first-match the guard would silently stop working, which is issue #92's failure mode relocated into the rules layer. The resolver filters to genuine **component** prefixes (`/tmp` is not a prefix of `/tmpfoo` — a string compare would say it is), ranks by canonical component count, and breaks exact ties by list position.

**Both sides go through the lenient canonicalizer** — ADR 0081's `canonicalize_lenient` ([ADR 0081](../decisions/0081-a-lenient-deny-list-entry-needs-a-lenient-compare-one-half-alone-is-a-silent-no-op.md), reference rather than restated here). A rule may name a directory that does not exist yet and still match it; a strict compare on either side would silently match nothing.

**An exact tie goes to the LAST rule**, and the runtime list is assembled by a **concatenation contract**: `default_rules()` FIRST, then the per-turn user rules, appended — assembled **once per turn**, beside the per-turn `filePolicy` re-read. **At the shipped defaults `default_rules()` is EMPTY.** The three values in `## The default rules` below are USER rules you write through the Settings button, never code, so the contract's load-bearing content is the ORDER alone: an appended user rule beats a matching earlier one on an exact tie, including any pre-filled default you set. The rule the guard's "always allow this directory" writes is appended at the END of the file's user rules for exactly that reason.

State the tension honestly: **the UI needs no rule ordering, but the resolver and the persisted file both carry an order contract** — the exact tie is the one place order matters, and with an empty default foundation that contract is now between your own rules.

**`protected_dirs()` remains the plain four-dir list.** It is the guard-membership set for row 3 AND the list the OS sandbox subtracts for confined `bash`. It is NOT derived from `default_rules()` — which carries nothing — and no user rule ever reaches it. That separation is what makes row 3 reachable at all, and it is what stops a rule from widening the shell.

## Scope — the five path tools, never bash

Rules apply to the file tools: `read` / `write` / `edit` / `grep` / `glob` — and **rules never apply to `bash`**. The principle, which is the one you can act on: **`bash` runs with your own user's OS permissions — if the user cannot write a path, neither can the shell; that is a user-level concern, not an app policy.** Parsing a shell command for redirect targets was considered and rejected: base64, heredocs and interpreted scripts make it bypassable in a dozen ways while looking like enforcement. The Settings panel prints the same thing, because a rules panel that implies otherwise is a panel that lies:

> These rules apply to the file tools (`read`, `write`, `edit`, `grep`, `glob`). **`bash` runs with your own user's OS permissions — it is not covered here.** To stop the agent reaching something with `bash`, remove your user's access to it.

One naming note against the tool list above, stated rather than smoothed: the tree's policed set is `read` / `find` / `grep` / `ls` / `write` / `edit` — **there is no `glob` tool**; `find` IS the glob tool (its `pattern` takes a glob). The shipped Settings copy repeats the spec's list and so names a tool that does not exist; the honest content is unchanged, and the copy is a one-line fix.

**The Landlock subtraction stays on `protected_dirs()`'s plain four-dir list**, so a user `allow` rule can NEVER widen confined `bash`: Landlock rules are add-only, and the only thing that keeps a `Sandboxed` command out of your instruction directories is that those directories are subtracted from its write roots. A confined command therefore stays **stricter than the path tools do under the same `allow` rule** — that is the chosen posture, and it rests on ADR 0081's guard-rail honesty rather than restating it.

## Scope of the third layer — what it ACTUALLY enforces

Read this as the honest counterpart to the scope section above. The user-rule layer's scope line is "the path tools, never `bash`". **The definition layer's scope line is narrower in a different direction: whole-tool verdicts only, on tools the gate already polices.**

- **Enforced: a whole-tool `Action` verdict.** `edit: deny`, `read: ask`, `bash: deny` — a bare verb, stored as the catch-all pattern with `whole_tool: true`. This is the only shape `definition_verdict` can read, and it is live on a real child Worker.
- **Parsed, announced, and NOT enforced: per-command `bash` patterns.** A `bash:` object with pattern rows is read faithfully and announces `UnsupportedUnvalidatedMatcher(BashPatternRules)`. It is not half-enforced, because deciding command text needs a matcher nothing here has validated — command text carries its own redirects, so `grep x file 2>/dev/null` contains a `>` and a naive `*>*` deny blocks the stderr-suppression idiom, and no ordering in this rule language says "redirect to a file but not to an fd". The modal prints the announcement in words: *"bash pattern rules are parsed but NOT enforced"*. Saying "unsupported" alone would imply the rules vanished; saying only "parsed" would imply they work.
- **Announced and UNENFORCEABLE: a whole-tool deny on a key with no gate hook.** `task: deny` is the clearest case — opencode has a `task` tool, this desktop does not, so the key is retained as `Unrecognized("task")` (never dropped) and announced, but `policy_verdict` has no policed direction for it and answers **`None`** — not `Allow`, not `Deny`, no panic. The same holds for `web_search`, `read_skill` and `fetch_content`, which are real tools here but are not policy-gated. A deny there is a disclosure, not a control.
- **And a gap the announcement does not cover, measured here rather than inferred:** the unsupported announcement fires **only for `ToolKey::Bash`** — one `notes.push` site, guarded by `tool == ToolKey::Bash`. So a **path-taking** tool's pattern map (`edit: {"*": deny, "*.md": allow}`) is neither enforced **nor announced**: it parses, the gate answers `AsSelf`, and no note says why. That shape is exactly what the motivating file writes for `edit`, and an existing pin (`a_blank_line_inside_a_nested_pattern_map_is_skipped_too`) feeds it through a helper that asserts an empty note list — so the silence is corroborated, not speculated. A deny the user wrote for `edit` therefore reads as a rule in the modal and refuses nothing, quietly. Recorded as the follow-up this page can name without pretending to have fixed.

**The layer is gate-only, and that asymmetry is a stated limit.** A user rule refuses at the gate *and* at the executor, because both consult the same `rule_for` over the same `ToolCtx.rules`. `ToolCtx` carries no permission block at all, so a definition can only ever refuse **before** dispatch. Nothing about that is a hole today — the gate runs first — but it means anything that later moves refusals into the executors has to decide how a per-agent verdict reaches a context that does not hold one.

### The motivating file still refuses nothing

Issue #101's Evidence section names `~/.agents/agents/researcher.md`. **That file, as measured on 2026-10-29, still refuses nothing at the gate.** Re-measured directly, not quoted from the plan:

- `grep -c '^tools:' ~/.agents/agents/researcher.md` → **`0`**. There is no `tools:` key, so the advertisement drop has no list to filter and `bash` is still offered to the child — the gate is the only layer that could refuse it.
- Its `bash:` block's own catch-all is `"*": allow`. Even a perfect command matcher would then **allow** a read-only `grep` — the deny rows after it are the ones carrying the intent, and nothing that ships can read any of them.
- Its `edit:` block is a **pattern map**, and pattern maps on path tools are the un-announced case above.

The gate's answer for that block, on the default posture, is `Allow` for `bash`, `edit` and `write`, and `None` for `task` — pinned deliberately, by `the_real_researcher_block_is_read_and_its_verdicts_are_the_scoped_ones`, so that nobody can describe the scope line as a silent drop by accident. **What is live is a class, not the cited file:** whole-tool `Action` denies are enforced end to end on a real child Worker, and the issue's own file-of-evidence does not contain one. A reader who finishes this page believing `researcher.md` is now policed has read it wrong.

## When an "always allow" takes effect

The policy AND the rules are re-read from `settings.json` **once per turn**, not per tool call — ADR 0030 Deviation 4, pinned by tests. So an `allow-directory` answer takes effect at the **next prompt**, not mid-turn: a model writing five files into a fresh directory prompts **five times** the first time. Making it immediate means breaking the one-read-per-turn design, in which every tool call inside a turn agrees; that was rejected as disproportionate for a one-time cost per directory. Expect the five prompts once per new directory, then silence.

## The default rules

| Rule | Effect at the default posture |
|---|---|
| `~` read/write `allow` | **nothing** — the executor floor is already `["/"]`. It documents how open the default is |
| `/` read `allow` | **nothing** — same reason |
| `~/.pi/agent` read `deny` | **the one genuinely new restriction** — it covers `~/.pi/agent/auth.json`, which today sits outside the **Boundary** and is refused only under `reads: Sandboxed` |

**These are USER rules, not code defaults.** They are absent until you add them, so at the shipped defaults the rules list is empty and `default_rules()` contributes nothing (see `## Matching`).

**The "Add default rule" button, and why there is no automatic seeding.** The design called for these three to be "written only on first write", so an existing install never silently gains a restriction. No first-write mechanism exists anywhere in the settings path — no save history, no version marker, and the missing-file branch is not surfaced to the UI — and the wire cannot distinguish an empty rule list from an absent one. So Settings ships an explicit **"Add default rule"** button that **pre-fills the dialog draft and writes nothing until you save it**. No automatic write is possible, which means no install ever silently gains the one real restriction; the button plus the panel copy naming all three defaults is the honest substitute, and the `deny` row is labelled in the UI as a default you can delete so it never reads as hidden behaviour. The offer re-appears whenever the list is empty.

## Honest limits

**(a) `settings.json` is not agent-writable-proof.** It is not in `protected_dirs` and it already holds `filePolicy`, so agent-writable policy is pre-existing rather than introduced here. A model that can write that file could grant itself anything with the path tools — but it could already do that with `bash`, which no rule covers. Recorded, not fixed; protecting `settings.json` is a separate decision.

**(b) The `settings.json` concurrency limit.** This is a **distinct limit from (a)** — the two are not the same claim and must not be read as one: (a) is a security claim about who can write the file, this is a reliability claim about writers colliding — and `settings.json` has **six-plus independent whole-document writers and no shared lock**. The relay's own write is now **atomic** (a temp file in the config dir plus a rename, with the existing file's mode preserved on unix so the write does not silently tighten `settings.json` from 0644 to 0600), and its read-modify-write window is **narrowed** to one function call that re-reads immediately before the overwrite. Narrowed, **not closed**. The concrete lost update: you click "Always allow this directory", the relay appends the rule, and a Settings-page **Save** composed from a document snapshot taken *before* that click then overwrites the whole file and **silently drops the rule** — and because the relay's write is best-effort-logged and already returned, the loss surfaces to no one. The recorded follow-up is a settings-write lock or a save-version/merge at the store boundary. Practical mitigation today: don't leave a Settings dialog open in another window while answering a permission prompt.

**(c) Trust suppresses the guard.** A Trusted **Space** permits silent self-modification, and at the shipped defaults that silent proceed is the ORDINARY state — there is no default-deny rule whose deletion had to happen first, because the four dirs are a membership set. Mitigations: `trust-space` is gone from the guard's own prompt (the one-click self-protection disable is closed), and the trust copy says what trust now buys. If you want a Trusted Space to still be asked, add a `deny` rule for those paths — a rule `deny` is trust-immune.

**(d) `home: None`.** With no resolvable home directory, a `~`-named rule expands against nothing and therefore **matches nothing** — a silent no-op, never a wider reading. And the default rule set is empty, which is its state at all times by design, so the footprint is the same as an empty protected list: the posture select decides everything. Recorded, not fixed. (On unix `home_dir()` falls back to the passwd database, so a genuinely unresolvable home is practically unreachable; the reachable consequence is the empty rule set.)

**(e) Per-turn effectiveness**, as above: five prompts on first use of a directory.

**(f) The advertisement drop only narrows a list the resolver PRODUCED.** A whole-tool `deny` removes its name from the child's `tools` list — but where a definition has **no `tools:` key**, the resolver produced no list at all, there is nothing to filter, and the tool is still advertised to the child. The gate is then the **only** layer that can refuse it, which is exactly the shape `a_whole_tool_bash_deny_refuses_at_the_gate_when_the_tool_is_still_offered` pins, and it is why the gate half of this feature could not be traded for the drop half. (And this is the leg the motivating file sits on — see `## The motivating file still refuses nothing`.) The drop also runs over the list that came from the explicit `subagent({tools: […]})` param, which is deliberate: a file may only make a child *more* restricted, so dropping a denied name from the explicit list narrows rather than grants, and an emptied explicit list means zero tools — still narrower than the parent's set.

**(f.1) The defect that came within one review of shipping, recorded because it is the instructive part.** The drop was first written reusing [ADR 0067](../decisions/0067-an-agent-override-never-speaks-by-being-empty.md)'s emptied-means-ABSENT rule, cited from `narrow` a few lines above. The citation was **wrong in that position**, and the consequence was inverted: `None` does not mean "no tools", it means *"the parent's list minus the guard"* — so `tools: [bash]` + `bash: deny` yielded `None`, and **the file that denied the most handed the child the MOST tools.** Strictly worse than the case 0067 guards against, because there the accident needs a typo and here it needed the most restrictive file a user could write. 0067's rule exists to stop a *typo or a stale name* accidentally zeroing a child — **unintended** narrowing — and a deliberate `deny` is the opposite case, so its rationale does not travel. An emptied list now stays `Some(vec![])`, which every downstream reads as zero tools (`subagent_flow`, `worker/core.rs`, `advertised_tool_specs`, `is_tool_enabled` — the `[]`-means-ALL expansion lives in the `None` arm, reading a *different* input, `parent_enabled_tools`).

**How it was caught, stated exactly, because the run's own status log got this wrong.** It was found **in review, before the commit existed** — measured, not remembered: `git log --all -S '(!names.is_empty()).then_some(names)'` returns nothing on any ref, and the buggy drop plus the test that asserted it (`a_deny_that_empties_the_advertised_list_falls_back_to_absent`) survive only in a **dangling stash-commit** — reachable from no ref, local to one machine, and pruned by `git gc`'s default two-week window, so the hash is already dead. **ADR 0084 carries both the drop site and the wrong assertion quoted verbatim**; that quotation, not a commit id, is the evidence. The single commit that ever touched the drop shipped the `map` form and the renamed pin `a_deny_that_empties_the_advertised_list_yields_zero_tools_not_the_parent_set`, whose doc comment records that it used to assert the opposite. So the claim *"this shipped green and passing its own test"* is **not supported by the object database** — it never shipped. The lesson survives intact and is the reason the pin's doc comment is written as a history note: **a test that asserts the current behaviour of a widening is a pin on the defect, and a green suite will defend it** — that WIP test passed, and it passed *because* it pinned the inversion. What made it catchable by reading rather than by running is that the fallback was justified by a citation to a real ADR, which is the most dangerous kind of wrong comment.

## Trust and the guard

The trust toggle's copy is the corrected one:

> New Spaces start trusted (skip permission prompts). A trusted Space's agent can also write its own instruction directories without asking — deny those paths with a rule above if you want that to still prompt.

Deliberate trust — from Space settings — silences the guard. **At the shipped defaults a Trusted Space proceeds silently**, and that IS the promise the copy makes: there was no default-deny rule whose removal this depended on. The guard's own prompt carries **no `trust-space`** option, so a recurring prompt can no longer be ended with one click on the very protection it exists to provide; trust is something you configure, not something you reach by reflex.

Trust never widens a `deny`. That sentence survived the whole change intact, and it is the reason (c) above has a fix.

**Trust does not silence a definition either — it only silences its prompts.** A child's definition `deny` refuses on a Trusted Space exactly as on an untrusted one, and its `ask` still turns the verdict into an `Ask` that Trust then auto-approves. That is the definition layer's half of the same sentence: Trust is a suppressor of prompts and never a grant, in either direction — it cannot widen a user `deny`, and it cannot undo a definition's narrowing.

## Where it lives in Settings

**Settings → Permissions** holds it all, because prompts belong where prompts are explained:

- the three **posture** rows (`Reads` / `Writes` / `Shell`), moved out of General with their Linux-without-Landlock handling intact;
- the **Trust new Spaces by default** toggle, moved out of General for the same reason, carrying the copy above;
- the **rules list** — one row per rule (path, direction, decision, edit, remove) with an add/edit dialog of three fields and no Test action, plus the empty-state copy naming all three defaults and the **"Add default rule"** button;
- the **scope copy** the `bash` decision requires, as a row rather than a footnote.

**The definition layer has no Settings surface, on purpose.** There is no `settings.json` `permission` key and no rule-authoring control; a definition's block is authored in its markdown file and is **displayed** in the **Agents modal** (the row's `Permission` line, its layer tag, one line per pattern row in file order, and one line per announcement). That split is the honest one: Settings is where *your* policy is written; the Agents modal is where *a file's* policy is reported.

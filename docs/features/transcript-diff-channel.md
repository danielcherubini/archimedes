# The `kind:"diff"` / `ToolCallContent` channel — a retention record, not a feature spec

## Why this file exists

Two facts about the transcript's diff channel sit next to each other in this tree and nothing said they were one decision.

- **The Rust side emits nothing on it.** `grep -rn '"type": *"diff"' src-tauri/src/` prints **nothing**, and `agent/normalize.rs`'s `compute_display_rows` doc-comment states the reason outright: the ACP `content: ToolCallContent[]` diff channel *"has no RPC input in Phase 1 — pi's tool results carry no diff-structured content"*, and the `has_diff` branch that once consumed it *"is gone with the crate types"*.
- **The frontend side is wired end to end.** `reducer.ts`'s `extractDiffs` pulls every `ToolCallContent` item spelling `type === "diff"` into a `DiffRef` (path plus a unified patch built by `unifiedPatch`); `reducer.ts`'s `tool_call` and `tool_call_update` arms call it and append the result as standalone `diff` messages; `identity.ts`'s `mergeDedupeKey` carries a `diff` arm so a diff participates in the resume merge like any other message; `unitKeys.ts` keys a rendered diff by path and timestamp; and the renderers are ordinary production components — `DiffBlock` is the leaf, reached from `ToolCallCard` (which `ChangesGroupCard` also routes its rows through) and from `MessageBubble`'s standalone-diff branch and `SubagentTranscript`'s `diff` branch; `FileSummaryCard` reads the *standalone* diff messages and deliberately not the `tool-call`'s own `diff` ref, because summing both counts every file twice; and `ChatStream` and `subagentActivity.ts` both read the standalone `diff` messages for their own summaries.

So this is **not dead code**. It is **forward-compat surface**: a wire shape the desktop's own native producer does not emit yet, whose consumer half is complete, typed, keyed, rendered, and tested. The honest problem — the one this file exists to close — is that **no document said so.** An auditor grepping for a `"diff"` producer finds none and reasonably deletes the pipeline; an auditor grepping the frontend finds a working feature and reasonably assumes the Rust side emits it somewhere they have not looked. Both readings are wrong, and the tree gives neither of them anything to check against.

## The producer state, plainly

`compute_display_rows`'s kind fan-out is `agent_thought_chunk`, `agent_message_chunk`, `message_retracted`, `tool_call`, `tool_call_update`, plus the fall-through arm that yields no row. **No arm produces a `kind: "diff"` display row**, so no `diff` row ever crosses from Rust, and the `tool-call` rows that do cross carry whatever `content` the harness put there — which today's producers never populate with a `Diff` item. The `has_diff` branch is gone with the crate types it read.

`MessageRow.kind` in the TypeScript mirror still lists `diff` among its spellings, and `sessionTypes.ts` still carries the standalone `{ kind: "diff", path, patch, at }` member of the `Message` union. Those are the surviving half of the contract, kept on purpose.

## The retention decision

**Keep the channel exactly as it is.** Not "keep it and wire it up", and not "keep it until someone cleans it" — the state on disk is the decided state.

**The bound that makes keeping it safe.** Every `messages` row carries `created_at`: the display insert is `INSERT INTO messages (session_id, kind, message_key, payload_json, created_at)`, with `now_ms()` supplied at write time and the conflict clause re-stamping it on an update. That is what makes an old-format row harmless rather than unbounded: a `kind:'diff'` row, if one exists in anyone's database, **can only pre-date the migration that removed the Rust producer** — nothing alive can write a new one — so its age is bounded by history rather than accumulating. Keeping it therefore costs nothing that grows, while deleting it would silently discard a real, still-displayable piece of a user's pre-migration history. This is the same lesson ADR 0025's crash-log amendment learned about the *other* kind of retained record, applied to the display table: **a record whose production has stopped is bounded, and a bounded record is cheap to keep.**

**A resume does NOT clear the display table — and the next reader will get this wrong.** `agent/harness/store.rs`'s `clear_messages` forwards to `Db::clear_native_messages`, which is `DELETE FROM native_messages WHERE session_id = ?1`. `native_messages` is the **provider transcript** — what gets replayed to the model — and it is the only table a resume clears. The `messages` **display** rows survive a resume untouched, and `harness/store.rs`'s own module doc says so in those terms. So a stored `kind:'diff'` row does come back into a resumed session; the resume is not a sweep that would have made retention self-cleaning.

**A `kind:'diff'` row is a display row like any other.** It is keyed by the display store's existing upsert — `UNIQUE(session_id, kind, message_key)`, `ON CONFLICT … DO UPDATE SET payload_json = excluded.payload_json, created_at = excluded.created_at` — so it needs no special handling: rows persist, only `native_messages` is cleared on resume, and nothing here adds a retention mechanism or promises one.

**One honest asymmetry, recorded because it is what "inert" actually means.** The rehydration path `rowToMessages` has arms for `user`, `agent-text`, `agent-thought` and `tool-call`, and its doc-comment states that a tool-call row re-derives its standalone diff messages because *diffs are stored inside the tool call's content, not as separate rows*; there is **no `diff` arm**, so a bare `kind:'diff'` row falls to the arm that yields nothing. The live pipeline reaches `diff` messages from a `tool_call` frame's `content`, not from a row of its own kind. So a hypothetical pre-migration `kind:'diff'` row is **inert at the display boundary** (it renders nothing) while still being a well-formed, age-bounded row the store keeps — which is precisely the combination that makes retention the cheap choice and deletion the risky one: the deletion would be irreversible and would buy nothing.

## What this record is NOT

`docs/roadmap/frontend-component-extraction-follow-ups.md` §4 is the nearest retention record in this repo and **it does not govern this surface.** §4 records `SubagentDelegatingCard`'s `details.progress` / `details.results` — fields of a `ToolResult.details` **envelope**, read off a tool result, whose reader chain is dead against today's transport and whose *removal* wants its own decision. That is a different object entirely: a field on a tool result, not a `messages` row kind.

The two cases also differ in kind, and the difference is the reason neither decision transfers:

- **This channel's producer is absent by design** — forward-compat surface, a wire shape kept because the desktop may one day emit diff-structured tool content. Nothing drifted.
- **§4's producer is *retired*** — the backend once emitted an envelope and stopped, so what survives there is a drift the §4 record deliberately leaves standing pending a removal decision.

§4's decision does not authorise deleting this pipeline, and this record does not authorise deleting that reader chain. If §4's roadmap file has been deleted on ship by the time you read this, its content survives in the review's own inventory of the same wave; the substance you need is unchanged — **the two surfaces stay distinct, and neither one's retention decision is the other's.**

## Do not delete the pipeline

The decision, in the review's own words: **do not delete the pipeline.** Concretely, nothing in this record removes a `messages` column, the `diff` spelling of `MessageRow.kind`, the `ToolCallContent` union member, the `DiffRef` type, the `diff` arms in `identity.ts` or `unitKeys.ts`, or any of the diff components. The surface stays exactly as shipped.

Written as plainly as a `docs/features/` page allows, since this is not a glossary entry: the channel is **never "dead code"** — its consumer half is live, typed and rendered, and only its producer is absent. It is **never "a leak"** — the rows that could exist in it are bounded in age by `created_at` and by the fact that nothing alive writes them. And its decision is **not follow-ups §4's** — that record covers a retired envelope field, and applying it here (or applying this one there) is the mistake this page was written to prevent.

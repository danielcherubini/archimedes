## Deliverable A — ADR 0083 (new): `docs/decisions/0083-the-self-modification-guard-is-an-ask-when-no-rule-matches.md`

H1 (use this verbatim):

> # The self-modification guard is an ASK when no rule matches — the protected agent-definition dirs are a guard-membership set, not a rule set

Front matter: the house template (§Conventions) with `date:` = implementation date. Body sections, in this order (each heading REQUIRED — the acceptance criteria check for them):

### `## The decision`
The four user-level agent-definition dirs — `~/.agents/skills`, `~/.pi/agent/skills`, `~/.agents/agents`, `~/.pi/agent/agents` — cease to be refused unconditionally. They become a **guard-membership set that is NOT a rule set**: `boundary::protected_dirs()` stays the plain four-dir list (its ADR 0081 lenient construction preserved), feeding two consumers — the gate's guard arm (row 3's membership test) and `sandbox.rs`'s Landlock subtraction, which is thereby UNCHANGED. `policy::default_rules()` returns **EMPTY**: the spec's three pre-filled defaults (`~` read/write `allow`, `/` read `allow`, `~/.pi/agent` read `deny`) are written by the USER via the Settings panel's **"Add default rule"** button (T06), never by code, so there is nothing left for a code default to emit (T03's round-3 decision, D1; T01's `default_rules().len() == 4` count pin is corrected to `0`). `FilePolicy` gains `rules: Vec<AccessRule>` of `{path, direction, decision ∈ {allow, deny}}` — **USER rules only** — with `#[serde(default)]` so an old `settings.json` parses to the new empty default (T01). Gate and executor consult the ONE shared resolver `rule_for` (ADR 0029/0030's one-canonicalizer rule) over the concatenated list `default_rules() (empty) ++ per-turn user rules`. Precedence for a path-param tool, over the landed model: (1) a USER rule `deny` → tool-result error, **trust-immune** — at the shipped defaults, with no user rules, row 1 cannot fire at all; (2) a USER rule `allow` → proceed silently; (3) no rule AND the target under one of the four agent-definition dirs → **ASK** (the self-modification guard, **Write-only** — a read of an agent-definition file is not an ask at any posture and falls to row 4), suppressible by Trust; (4) no rule → the posture select, as today. **Step 3 is the only behavioural change in this spec**: today's unconditional deny becomes an ask when no rule matches; rows 1, 2 and 4 are additive. **The relaxation, stated exactly:** at the shipped defaults, with no user rules at all, an **untrusted Space gets the guard ask, and a Trusted Space proceeds silently** — that silent proceed is the actual relaxation of ADR 0030's "refused in every policy" security claim, not a residual default. Rules apply only to `read` / `write` / `edit` / `grep` / `glob`, never to `bash`.

### `## Why a rule deny stays trust-immune and the guard ask does not`
Record: a `deny` — at the shipped defaults, a **user** `deny` — is a tool-result error (`deny_tool_result`) that never reaches the UI in any configuration; trust's whole meaning is *suppress prompts*, and a deny is never a prompt, so trust cannot touch it (ADR 0030's precedence sentence stays true). The guard's row-3 ask IS a prompt; trusting a Space suppresses it — consistent with the precedence table, and now possible because a guard prompt can appear on a TRUSTED Space (trust suppresses the ask by definition; the old "a prompt only ever appears for an untrusted Space" assumption is gone). This asymmetry is the point: **deliberate trust still silences the guard; nothing lets a deny be silenced.**

### `## The guard prompt: `trust-space` is deliberately absent`
Record: the guard prompt's options are exactly `allow` ("Allow once"), `allow-directory` ("Always allow this directory" — appends one `allow` rule via the Supervisor relay), `reject` ("Block"). The old third option of the boundary prompt — "Don't ask again for this Space", which persisted `set_space_trusted(cwd, true)` — is REMOVED from the guard prompt. The one-click path it closes: the prompt that exists to protect the agent's own instructions contained a one-click, permanent way to disable that protection — the most likely click when a prompt recurs. Deliberate trust stays available from Space settings; accidental trust does not. (The boundary prompt keeps its own three options unchanged.) The `allow-directory` option echoes a `path` (the nearest existing ancestor of the resolved target, via `canonicalize_lenient` — canonical, never a `~` residue, so the persisted rule is matchable).

### `## bash is not policed by rules — the OS-permission principle`
Record: rules never apply to `bash`; the shell keeps its own posture select and its Landlock confinement under `Sandboxed`. The principle: *bash runs with the user's own OS-level permissions — if the user cannot write a path, neither can the shell; that is a user-level concern, not app policy.* Parsing a shell command for redirect targets was considered and rejected: base64, heredocs and interpreted scripts make it bypassable in a dozen ways while looking like enforcement. Same reasoning as ADR 0030's "a guard-rail, not a security boundary", expressed as something a user can act on. **Subtraction stays on `protected_dirs()`'s plain four-dir guard-membership list:** a user `allow` rule can never widen confined `bash` (Landlock is add-only; the four-dir list is NOT rule-derived and no user rule ever reaches it — T03's DD2). A confined command stays stricter than the path tools under an allow rule: that is the chosen posture.

### `## protected_dirs() stays the plain four-dir guard-membership list — ADR 0081's leniency is load-bearing on the guard set and on user rules`
Record: `default_rules()` carries NOTHING, so ADR 0081's leniency has exactly TWO anchor points, and this ADR must attach it there rather than to a default rule set:
